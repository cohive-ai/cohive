## 问题一：Claude Code 自带的遥测能导出什么？能否注入 Cohive 问题单编号？

### 要点
Claude Code 原生支持 OpenTelemetry 指标和事件（以日志信号导出），链路追踪处于测试阶段。事件里带会话编号、提示编号、工具调用编号、每次模型请求的 Token 和估算费用，基本能满足“统计每个任务的轮次、Token、费用、工具执行”的需求。可以用 `OTEL_RESOURCE_ATTRIBUTES` 注入自定义属性（例如问题单编号），这些属性会出现在所有指标和事件上。在无界面模式（`claude -p`）和智能体开发包里，还能通过 `TRACEPARENT` 把 Claude Code 的链路挂到 Cohive 的链路下面；交互式会话会忽略外部传入的 `TRACEPARENT`。

### 引用的事实
- 开启方式：`CLAUDE_CODE_ENABLE_TELEMETRY=1`；`OTEL_METRICS_EXPORTER`（otlp/prometheus/console/none）、`OTEL_LOGS_EXPORTER`（otlp/console/none）、`OTEL_TRACES_EXPORTER`（测试阶段）；协议支持 grpc、http/json、http/protobuf；没有默认协议，必须显式设置 —— [Claude Code 监控文档](https://code.claude.com/docs/en/monitoring-usage)
- 默认导出间隔：指标 60000 毫秒，日志 5000 毫秒，链路 5000 毫秒；指标默认按增量（delta）上报 —— [同上](https://code.claude.com/docs/en/monitoring-usage)
- 指标：`claude_code.session.count`、`claude_code.lines_of_code.count`、`claude_code.pull_request.count`、`claude_code.commit.count`、`claude_code.cost.usage`（美元，属性含 `model`、`query_source`、`agent.name`、`skill.name`、`mcp_server.name`、`mcp_tool.name` 等）、`claude_code.token.usage`（`type` 取 input/output/cacheRead/cacheCreation）、`claude_code.code_edit_tool.decision`、`claude_code.active_time.total` —— [同上](https://code.claude.com/docs/en/monitoring-usage)
- 事件（以日志信号导出，名称都带 `claude_code.` 前缀），与 Cohive 相关的有：
  - `user_prompt`：`prompt_length`；提示正文默认脱敏，需 `OTEL_LOG_USER_PROMPTS=1` 才会导出
  - `tool_result`：`tool_name`、`tool_use_id`、`success`、`duration_ms`、`error_type`、`tool_input_size_bytes`、`tool_result_size_bytes`；`tool_parameters`、`tool_input` 需 `OTEL_LOG_TOOL_DETAILS` 才会导出
  - `tool_decision`：`decision`（accept/reject）、`source`（config、hook、user_permanent、user_temporary、user_abort、user_reject）
  - `api_request`：`model`、`cost_usd`、`cost_usd_micros`、`duration_ms`、`input_tokens`、`output_tokens`、`cache_read_tokens`、`cache_creation_tokens`、`request_id`
  - 另有 `api_error`、`api_retries_exhausted`、`permission_mode_changed`、`hook_execution_start/complete`、`compaction`、`subagent_completed`、`mcp_server_connection`、`managed_settings_resolved` 等
  - 关联字段：`prompt.id`（把同一次提示产生的所有事件串起来）、`event.sequence`（进程内顺序）、`request_id`、`tool_use_id`、`message.uuid`
  —— [同上](https://code.claude.com/docs/en/monitoring-usage)
- 标准属性：`session.id`、`user.id`（安装级匿名编号）、`user.email`、`user.account_uuid`、`organization.id`、`terminal.type`；`vcs.repository.url.full` 等仓库属性需 `OTEL_METRICS_INCLUDE_REPOSITORY` 开启（默认关，v2.1.269 起） —— [同上](https://code.claude.com/docs/en/monitoring-usage)
- 用 API 密钥直连或走 Bedrock 等云平台时，只有 `user.id` 和 `session.id`，文档建议用 `OTEL_RESOURCE_ATTRIBUTES` 自行附加用户身份 —— [同上](https://code.claude.com/docs/en/monitoring-usage)
- `OTEL_RESOURCE_ATTRIBUTES="department=engineering,team.id=platform"`：这些属性会加到所有指标和事件上（不只是资源块）；值不能含空格，字符集受限；自定义键不能覆盖 `user.id`、`session.id` 等标准属性（`vcs.*` 例外）；每个键都会成为指标标签，高基数会增加存储成本 —— [同上](https://code.claude.com/docs/en/monitoring-usage)
- 费用：`cost_usd` 和 `claude_code.cost.usage` 被标注为**估算值**，文档未说明计算方法 —— [同上](https://code.claude.com/docs/en/monitoring-usage)
- Claude Code 不设置 `gen_ai.usage.*` 属性；文档给出了与 GenAI 语义约定的映射：`cache_read_tokens` 对应 `gen_ai.usage.cache_read.input_tokens`，`cache_creation_tokens` 对应 `gen_ai.usage.cache_write.input_tokens` —— [同上](https://code.claude.com/docs/en/monitoring-usage)
- 隐私开关（默认都关）：`OTEL_LOG_USER_PROMPTS`、`OTEL_LOG_ASSISTANT_RESPONSES`、`OTEL_LOG_TOOL_DETAILS`（工具参数、Bash 命令）、`OTEL_LOG_TOOL_CONTENT`、`OTEL_LOG_RAW_API_BODIES`（包含整段对话历史）；内容截断上限约 60KB（`CLAUDE_CODE_OTEL_CONTENT_MAX_LENGTH`） —— [同上](https://code.claude.com/docs/en/monitoring-usage)
- 仓库里的 `.claude/settings.json` 不能设置导出变量或开启遥测，只能关闭某个信号；托管设置可以锁定导出目标 —— [同上](https://code.claude.com/docs/en/monitoring-usage)
- `otelHeadersHelper`：用脚本动态生成导出请求头（适合短期令牌），启动时执行一次，之后默认每 29 分钟执行一次，只对 http 协议生效，不支持 grpc —— [同上](https://code.claude.com/docs/en/monitoring-usage)
- 链路追踪（测试阶段）：需要 `CLAUDE_CODE_ENABLE_TELEMETRY=1` 加 `CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1`。层级为 `claude_code.interaction`（每次提示一个根节点）→ `claude_code.llm_request` / `claude_code.tool`（下分 `tool.blocked_on_user`、`tool.execution`）/ 子智能体的节点 —— [同上](https://code.claude.com/docs/en/monitoring-usage)
- **在智能体开发包和 `-p` 无界面会话中，Claude Code 会从自身环境读取 `TRACEPARENT` 和 `TRACESTATE`，`claude_code.interaction` 成为调用方节点的子节点；即使没有配置链路导出，事件日志记录也会带上 `trace_id`、`span_id`。交互式会话会忽略外部传入的 `TRACEPARENT`，以免误继承持续集成或容器环境里残留的值** —— [同上](https://code.claude.com/docs/en/monitoring-usage)
- 开启链路时，Bash 子进程会继承 `TRACEPARENT`；但 Claude Code 不会把 `OTEL_*` 变量传给它启动的子进程（Bash 工具、钩子、MCP 服务） —— [同上](https://code.claude.com/docs/en/monitoring-usage)
- 文档明确说明 Claude Code 只输出原始事件流，异常检测、跨会话关联、告警都由后端负责 —— [同上](https://code.claude.com/docs/en/monitoring-usage)

### 推断
- **注入问题单编号的可行性：** 在第三阶段的自动执行里（`claude -p` 由本机小助手启动），可以在启动时设置 `OTEL_RESOURCE_ATTRIBUTES=cohive.issue_id=...,cohive.workspace=...,cohive.correlation_id=...`，同时传入 `TRACEPARENT`，归属是精确的。
- **交互式会话（第一、二阶段的主要场景）有归属难题：** 环境变量在进程启动时就固定了，一个会话可能先后处理多张问题单，`OTEL_RESOURCE_ATTRIBUTES` 只能注入“人、机器、工作空间”这类稳定属性，不适合注入问题单编号；交互式会话又忽略 `TRACEPARENT`。可行做法是在 Cohive 里维护一张“会话 ↔ 问题单”的时间区间表：钩子（会话开始、每次提交提示词时）和 `cohive_claim_issue` / `cohive_update_issue` 调用时上报当前会话编号，事后按 `session.id` 加时间窗口把遥测归到问题单上。钩子输入里含会话编号这一点本次未重新核实（见缺口）。
- 费用应当被当作估算值展示，不能作为计费凭证。
- 默认不开 `OTEL_LOG_TOOL_DETAILS`，因为 Bash 命令里可能带密钥；Cohive 需要的“工具执行证据”最好由智能体通过 MCP 主动提交，并在 Cohive 端做密钥扫描。

### 缺口
- Claude Code 钩子输入的 JSON 里有 `session_id`、MCP 请求里能否拿到调用方会话编号：本次没有重新抓取钩子文档核实。
- 无界面模式下 `--output-format stream-json` 的最终结果消息含 `total_cost_usd`、`num_turns`、`usage` 等字段，这是训练知识，本次未重新核实。
- 链路追踪何时正式发布，文档没有给出时间表。

## 问题二：Codex 的 OpenTelemetry 和日志导出能力

### 要点
Codex（Apache-2.0）在 `~/.codex/config.toml` 的 `[otel]` 段支持把日志事件、链路、指标导出到 OTLP（http 或 grpc），事件带会话编号、模型、Token 数、工具调用耗时，但**没有费用字段**。源码显示它读取 `TRACEPARENT`/`TRACESTATE` 环境变量，也支持 `otel.span_attributes` 自定义链路属性；资源构造方式意味着大概率也认 `OTEL_RESOURCE_ATTRIBUTES`，但官方文档没有写。`codex exec --json` 会输出逐事件的 JSON 流，`turn.completed` 里带 Token 用量。

### 引用的事实
- `openai/codex` 仓库许可证 Apache-2.0，约 12.9 万星，2026-10-14 仍有推送 —— [GitHub API](https://github.com/openai/codex)
- `[otel]` 配置项：`environment`（默认 `"dev"`）、`exporter`（`none` 为默认，另有 `otlp-http`、`otlp-grpc`，可配 `endpoint`、`protocol`、`headers`）、`log_user_prompt`（默认 false，提示正文默认脱敏）；导出为异步批量，退出时刷新 —— [Codex 高级配置文档](https://learn.chatgpt.com/docs/config-file/config-advanced)（原地址 developers.openai.com/codex/config-advanced 已 308 跳转到此）
- 日志事件：`codex.conversation_starts`（模型、推理设置、沙箱与审批策略）、`codex.api_request`、`codex.sse_event`（在 `response.completed` 上带 Token 数）、`codex.websocket_request/event`、`codex.user_prompt`（只有长度）、`codex.tool_decision`（批准或拒绝，来自配置还是用户）、`codex.tool_result`（耗时、成功与否、输出片段）；事件元数据含会话编号、模型、版本等 —— [同上](https://learn.chatgpt.com/docs/config-file/config-advanced)
- 指标（前缀 `codex.`）：`api_request`、`api_request.duration_ms`、`sse_event`、`tool.call`、`tool.call.duration_ms`、`turn.token_usage`（`token_type` 取 total、input、cached_input、output、reasoning_output）；默认标签 `auth_mode`、`originator`、`session_source`、`model`、`app.version` —— [同上](https://learn.chatgpt.com/docs/config-file/config-advanced)
- `[analytics] enabled = false` 会关闭向 OpenAI 发送的匿名使用数据，**同时也会关闭自定义 OTLP 指标导出** —— [同上](https://learn.chatgpt.com/docs/config-file/config-advanced)
- 源码里指标导出默认值是 `OtelExporterKind::Statsig`，链路导出默认 `None` —— [codex-rs/core/src/config/otel.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/config/otel.rs)
- 本地历史：默认写到 `CODEX_HOME` 下的 `history.jsonl`，可用 `[history] persistence = "none"` 关闭 —— [Codex 高级配置文档](https://learn.chatgpt.com/docs/config-file/config-advanced)
- 源码中的设置结构有 `trace_exporter`、`metrics_exporter`、`span_attributes`、`tracestate`；`[otel.span_attributes]` 中配置的属性会加到导出的链路节点上 —— [codex-rs/otel/README.md](https://github.com/openai/codex/blob/main/codex-rs/otel/README.md)
- `codex.agent_response` 事件需 `otel.log_agent_responses = true`；事件含 `conversation.id`、`turn.id`、`agent.type`（main/subagent），以及 `parent.conversation.id` 等父子关系字段；`codex.skill_invocation` 含 `conversation.id`、`turn.id` —— [同上](https://github.com/openai/codex/blob/main/codex-rs/otel/README.md)
- 源码 `trace_context.rs` 定义了 `TRACEPARENT_ENV_VAR = "TRACEPARENT"`，读取到合法值时日志为“continuing trace from parent context” —— [codex-rs/otel/src/trace_context.rs](https://github.com/openai/codex/blob/main/codex-rs/otel/src/trace_context.rs)
- 资源由 `Resource::builder()` 构造（`provider.rs` 的 `make_resource`） —— [codex-rs/otel/src/provider.rs](https://github.com/openai/codex/blob/main/codex-rs/otel/src/provider.rs)；Rust OTel SDK 文档说明 `Resource::builder()` 默认包含 `EnvResourceDetector`（即读取 `OTEL_RESOURCE_ATTRIBUTES`），只有 `builder_empty()` 不含 —— [docs.rs opentelemetry_sdk Resource](https://docs.rs/opentelemetry_sdk/latest/opentelemetry_sdk/resource/struct.Resource.html)
- `codex exec --json` 事件类型：`thread.started`（含 `thread_id`）、`turn.started`、`turn.completed`、`turn.failed`、`item.*`（智能体消息、推理、命令执行、文件修改、MCP 工具调用、网页搜索、计划更新）、`error`；`turn.completed` 的用量字段有 `input_tokens`、`cached_input_tokens`、`output_tokens`、`reasoning_output_tokens`；**没有费用字段** —— [Codex 无界面模式文档](https://learn.chatgpt.com/docs/non-interactive-mode)
- Langfuse 的 Codex 集成走的是 Codex 插件钩子（每轮触发 Stop 事件），要求 Node 22+、Codex 0.128+ —— [Langfuse 编程智能体追踪指南](https://langfuse.com/resources/engineering/coding-agent-tracing)

### 推断
- Codex 端的问题单编号注入有两条路：`OTEL_RESOURCE_ATTRIBUTES`（按源码推断可行，未实测）或在启动 `codex exec` 时用 `-c otel.span_attributes...` 之类的命令行覆盖（命令行覆盖语法本次未核实）。交互式会话同样有“一个会话处理多张单”的归属问题，解决方法与 Claude Code 相同：按 `conversation.id` 加时间窗口关联。
- Codex 没有费用字段，Cohive 需要自己维护模型价格表，用 Token 数乘单价估算。可选的开源价格表：LiteLLM 仓库的 `model_prices_and_context_window.json`（约 2.8MB；仓库主体 MIT，`enterprise/` 目录另有许可证） —— [BerriAI/litellm LICENSE](https://github.com/BerriAI/litellm/blob/main/LICENSE)。
- 两个工具的事件命名、字段名都是各自私有的（`claude_code.*`、`codex.*`），都没有采用 GenAI 语义约定的 `gen_ai.*` 属性；Cohive 需要一层自己的归一化映射。
- 第三阶段自动执行时，`codex exec --json` 的事件流本身就够做轮次、Token 统计，不一定要依赖 OTel。

### 缺口
- 官方文档没有提到 `OTEL_RESOURCE_ATTRIBUTES` 和 `codex exec` 下的 OTel 行为，以上是读源码的推断，未实测。
- `codex.tool_result` 的“输出片段”是否会带出密钥、能否关闭，文档没有说明。
- `thread_id` 与 OTel 事件里的 `conversation.id` 是否同一个值，文档没有明说。

## 问题三：OpenTelemetry 生成式 AI 语义约定在 2026 年的状态

### 要点
截至 2026-10-14，GenAI 语义约定已经从主仓库拆到独立仓库 `open-telemetry/semantic-conventions-genai`（2026-05-05 创建），**整体状态仍是“开发中”（Development）**，尚无稳定版，也还没有发布任何版本。已覆盖模型调用、智能体（`create_agent`、`invoke_agent`、`invoke_workflow`、`execute_tool`）、事件、指标、MCP 和各厂商约定。Claude Code 和 Codex 目前都没有采用它。

### 引用的事实
- 独立仓库 `open-telemetry/semantic-conventions-genai`，Apache-2.0，创建于 2026-05-05，约 439 星；README 写着用 Weaver 管理对核心约定的依赖，“Schema URL”一节为 TODO —— [GitHub 仓库](https://github.com/open-telemetry/semantic-conventions-genai)
- 该仓库 CHANGELOG 只有“Unreleased”，尚无正式发布 —— [CHANGELOG.md](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/CHANGELOG.md)
- `docs/gen-ai/README.md` 标注 **Status: Development**；包括客户端推理、事件、异常、指标、Token 指标、模型节点、智能体节点，以及 Anthropic、AWS Bedrock、Azure AI Inference、OpenAI 的厂商约定和 MCP 约定 —— [docs/gen-ai/README.md](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/README.md)
- 智能体节点文档中 `gen_ai.operation.name` 的取值 `create_agent`、`execute_tool`、`invoke_agent`、`invoke_workflow` 均为 Development；`gen_ai.agent.id/name/version/description` 也都是 Development —— [gen-ai-agent-spans.md](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md)
- 主仓库最新版本 v1.44.0（2026-08-04 发布），智能体节点文档引用的是 v1.44.0 的错误记录规范 —— [semantic-conventions releases](https://github.com/open-telemetry/semantic-conventions/releases)
- Claude Code 文档明确说不设置 `gen_ai.usage.*` 属性，并提示缓存写入属性名在新旧版本约定中不同（`cache_write` 与旧名 `cache_creation`） —— [Claude Code 监控文档](https://code.claude.com/docs/en/monitoring-usage)
- Langfuse 的 OTLP 接入会读取 `gen_ai.request.model`、`gen_ai.usage.*`、`gen_ai.usage.cost` 等属性，并说明这些约定“仍在演进” —— [Langfuse OpenTelemetry 文档](https://langfuse.com/integrations/native/opentelemetry)

### 推断
- Cohive 不宜把内部数据模型直接绑在 `gen_ai.*` 属性名上；可以在导出给外部系统时按当时版本映射。属性名已经在变（缓存写入的命名就是一例）。
- Cohive 自己的智能体操作如果要发链路，可以参考 `invoke_agent` / `execute_tool` 的结构，再加 `cohive.*` 命名空间的业务属性。

### 缺口
- 稳定化路线图和预计时间：没有找到官方说明。
- 拆仓的官方公告日期和原因：本次没有找到，只确认了仓库创建时间。

## 问题四：开源大模型/智能体可观测平台对比

### 要点
没有一个平台能“开箱即用”同时接住 Claude Code 和 Codex 的原生遥测：Langfuse、Phoenix、Opik、Laminar 都以接收 OTLP **链路**为主，而两个编程智能体的主力数据是**指标和日志事件**（Claude Code 的链路还在测试阶段）。Langfuse 靠钩子插件读会话记录来接 Claude Code 和 Codex。从许可证看，Opik、Laminar、OpenLLMetry 是 Apache-2.0；Langfuse 和 SigNoz 是“核心 MIT + `ee/` 目录商业许可”；Phoenix 是 Elastic License 2.0（不是开源许可证，禁止作为托管服务提供）。从依赖看，除 Phoenix（可只用 Postgres 或 SQLite）外，都需要 ClickHouse，Langfuse 还需要 Redis 和对象存储。它们都不适合嵌入 Cohive，只适合作为“可选外接”。

## 问题五：通用可观测栈（OTel Collector + Grafana / SigNoz / Jaeger）是否更合适

### 要点
对“统计时长、Token、费用、按人按工具聚合”这类需求，通用栈比大模型专用平台更对口，因为它能同时接住指标、日志、链路三种信号。OTel Collector（Apache-2.0）在其中价值最大：脱敏处理器可以在入库前去掉密钥，GitHub/GitLab 接收器能把流水线事件转成链路。但所有后端都会增加部署组件，Cohive 本身不应捆绑，只提供“可选外接”的配置样例。

### 引用的事实
- `opentelemetry-collector-contrib`：Apache-2.0 —— [GitHub API](https://github.com/open-telemetry/opentelemetry-collector-contrib)
- 脱敏处理器（redaction processor）：日志、指标为 alpha，链路为 beta；支持 `allowed_keys`（白名单，为空则全部删除，“设计为失败即关闭”）、`blocked_key_patterns`、`blocked_values`（正则屏蔽值）、`hash_function`（以哈希代替删除）、URL 清洗 —— [redactionprocessor README](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/processor/redactionprocessor/README.md)
- 转换处理器（transform processor）：链路、指标、日志均为 beta —— [transformprocessor README](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/processor/transformprocessor/README.md)
- GitHub 接收器：指标和链路为 alpha，通过 webhook 接收 `workflow_run`、`workflow_job` 事件并转成链路 —— [githubreceiver README](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/receiver/githubreceiver/README.md)
- GitLab 接收器：链路为 alpha，通过 webhook 接收流水线事件并转成链路；`include_user_attributes` 默认 false（开启后会带提交作者姓名、邮箱等） —— [gitlabreceiver README](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/receiver/gitlabreceiver/README.md)
- Grafana 与 Loki、Tempo：AGPL-3.0；Prometheus：Apache-2.0；`grafana/docker-otel-lgtm`（一体化开发镜像）：Apache-2.0 —— [GitHub API](https://github.com/grafana/grafana)
- Jaeger：Apache-2.0，23293 星 —— [GitHub API](https://github.com/jaegertracing/jaeger)
- VictoriaLogs：Apache-2.0 —— [GitHub API](https://github.com/VictoriaMetrics/VictoriaLogs)
- SigNoz：核心 MIT，`ee/` 和 `cmd/enterprise/` 目录另行许可；README 提到可用 ClickHouse SQL 写查询、有大模型可观测（Token、费用、工具调用）；企业版功能含合规、RBAC、自定义保留期等 —— [signoz LICENSE](https://github.com/SigNoz/signoz/blob/main/LICENSE)、[signoz README](https://github.com/SigNoz/signoz)
- Claude Code 文档对后端的建议是：指标用时序库，事件用日志聚合或列式存储，链路用分布式追踪系统；需要统计日活/周活时选择支持高效去重查询的后端 —— [Claude Code 监控文档](https://code.claude.com/docs/en/monitoring-usage)

### 推断
- **Grafana LGTM（Loki + Grafana + Tempo + Mimir/Prometheus）：** 能同时接三种信号，社区已有 Claude Code 看板。AGPL 对“公司内部部署使用”没有问题；Cohive 只是给出 Collector 配置样例、不分发也不修改它们，因此不会受 AGPL 传染。缺点是组件多。
- **SigNoz：** 单一产品覆盖三种信号，但依赖 ClickHouse，对小团队偏重。
- **Jaeger：** 只管链路，接不了 Claude Code 的指标和事件，单独用不够。
- **最关键的是 Collector 本身：** 让各开发者的智能体都把遥测发到团队的一个 Collector，由它统一脱敏、加属性，再分发到 Cohive 和（可选的）Grafana/Langfuse。
- **另一条路：** Cohive 服务端直接实现一个精简的 OTLP/HTTP 日志接收接口（用 Go 官方的 `go.opentelemetry.io/proto/otlp` 解码），只抽取 `api_request`、`tool_result`、`tool_decision`、`codex.sse_event`、`codex.tool_result` 等少数事件写入 Postgres 汇总表。这样不需要任何外部组件就能做到“按任务统计 Token、费用、轮次、时长”。这是基于协议的推断，具体实现成本未评估。
- GitHub/GitLab 接收器都还是 alpha，而 Cohive 本来就要接代码平台的 webhook（适配器），流水线事件直接由 Cohive 的适配器处理更直接，不必经 Collector 绕一圈。

### 缺口
- SigNoz 当前自部署的确切组件清单（ClickHouse 之外是否还需 ZooKeeper 或 ClickHouse Keeper、元数据库用什么）：仓库的 compose 文件路径已变，本次未查到。
- Grafana 栈的最小资源占用：未查到权威数字。

## 问题六：审计日志有没有现成的开源组件（Go），还是 Postgres 追加写表即可

### 要点
Go 生态里没有成熟、被广泛采用的“通用审计日志库”。能查到的都是零星的小项目（个位数或零星标），不宜作为依赖。透明日志类的成熟项目（Trillian、Tessera）能提供密码学防篡改，但对第一版明显过重。**结论：Postgres 追加写表加哈希链，自己实现，代码量很小**；密钥脱敏用 gitleaks（MIT，可作为 Go 库）的规则做写入前扫描。

### 引用的事实
- `gourdian25/graudit`：MIT，0 星，2026-09 有推送；提供追加写、哈希链和 `Verify()`，README 承认无法防御能直接改库并重算整条链的特权攻击者 —— [pkg.go.dev graudit](https://pkg.go.dev/github.com/gourdian25/graudit)、[GitHub API](https://github.com/gourdian25/graudit)
- `kisom/auditlog`：ISC，2 星，最后推送 2014-10，已停止维护 —— [GitHub API](https://github.com/kisom/auditlog)
- `google/trillian`：Apache-2.0，3759 星；`transparency-dev/tessera`：Apache-2.0，251 星，均在活跃维护 —— [GitHub API](https://github.com/transparency-dev/tessera)
- `pgaudit/pgaudit`（Postgres 扩展）：1716 星，记录的是数据库语句级审计，不是业务审计 —— [GitHub API](https://github.com/pgaudit/pgaudit)
- 搜索结果总结的设计要点：哈希链能发现局部篡改，但防不住掌握数据库的人整体重写；要更强保证需对链头签名或定期把链头锚定到库外；并发追加会让链分叉，需用 advisory lock 或单写者串行化；哈希字段要带版本号，以免日后改表结构误报篡改 —— [搜索结果综述，涉及 graudit 与 waxseal 等](https://pkg.go.dev/github.com/gourdian25/graudit)（此条为搜索工具对多个来源的归纳，非单一权威来源）
- `gitleaks/gitleaks`：MIT，29920 星；`trufflesecurity/trufflehog`：AGPL-3.0 —— [GitHub API](https://github.com/gitleaks/gitleaks)
- `riverqueue/river`（方案里选的 Postgres 队列）：MPL-2.0 —— [GitHub API](https://github.com/riverqueue/river)

### 推断
- 审计表设计（建议）：`audit_events(id bigserial, ts, workspace_id, actor_type[人/智能体/系统], actor_user_id, actor_tool[claude-code/codex/...], actor_token_id, action, target_type, target_id, issue_id, correlation_id, trace_id, payload jsonb, payload_redacted bool, prev_hash, hash)`；数据库层面只授予应用账号 INSERT 和 SELECT，用触发器拒绝 UPDATE/DELETE；同事务内与业务状态变更一起写入（与 river 的“同事务入队”思路一致）。
- 哈希链按工作空间分链，用 `pg_advisory_xact_lock(workspace_id)` 串行化；定期把链头写进 Git 标签或对象存储作为外部锚点即可，不必上 Trillian。
- 密钥防泄露分三层：①源头不收（不开 `OTEL_LOG_TOOL_DETAILS`、`OTEL_LOG_RAW_API_BODIES`）；②经 Collector 时用脱敏处理器的 `blocked_values` 正则；③Cohive 写入审计和证据前用 gitleaks 规则扫描，命中则替换为 `[REDACTED:规则名]` 并记录 `payload_redacted=true`。trufflehog 是 AGPL，不适合嵌入。
- river 是 MPL-2.0（文件级弱传染），作为依赖引入不影响 Cohive 自身选什么许可证，只要不修改 river 源文件。

### 缺口
- gitleaks 作为 Go 库嵌入的接口稳定性（它主要是命令行工具）：本次未核实其库用法文档。
- 是否存在专门的 Go 业务审计库被大型项目采用：没有找到。

## 问题七：推荐方案，以及 Cohive 自己存什么、交给外部系统存什么

### 要点
**第一阶段：不引入任何外部可观测组件。** Cohive 用 Postgres 存业务事件、审计事件（追加写加哈希链）和“会话 ↔ 问题单”关联；Token 和费用先从智能体主动上报和（可选的）精简 OTLP 日志接收中获取。**后期：** 加一个团队级 OTel Collector 做脱敏和分发，Grafana LGTM 或 Langfuse 作为可选外接，第三阶段自动执行时用 `TRACEPARENT` 加 `OTEL_RESOURCE_ATTRIBUTES` 实现精确归属。

### 引用的事实
- Claude Code 在 `-p` 模式下接受 `TRACEPARENT`，交互模式忽略；支持 `OTEL_RESOURCE_ATTRIBUTES` —— [Claude Code 监控文档](https://code.claude.com/docs/en/monitoring-usage)
- Codex 读取 `TRACEPARENT`、支持 `otel.span_attributes` —— [codex-rs/otel](https://github.com/openai/codex/blob/main/codex-rs/otel/README.md)
- Claude Code 的费用是估算值；Codex 没有费用字段 —— [Claude Code 监控文档](https://code.claude.com/docs/en/monitoring-usage)、[Codex 无界面模式文档](https://learn.chatgpt.com/docs/non-interactive-mode)
- GenAI 语义约定仍为 Development —— [semantic-conventions-genai](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/README.md)
- Langfuse 自部署需要 Postgres、ClickHouse、Redis、对象存储 —— [Langfuse 自部署文档](https://langfuse.com/self-hosting)

### 推断

**第一阶段最小可行方案（只用 Postgres）**
1. `issue_events`：问题单状态流转、指派、审批、验证结果，每条带操作者（人 + 工具 + 令牌编号）。它本身就是业务数据，也是审计的主体。
2. `audit_events`：追加写加哈希链（见问题六），覆盖所有经 MCP 和看板发生的写操作、审批、拉闸、令牌签发与吊销。
3. `agent_sessions`：`(tool, session_id/conversation_id, user, machine, started_at, ended_at)`，由 Claude Code 钩子和 Cohive 命令行上报；`session_issue_links(session_id, issue_id, from_ts, to_ts)` 在认领、更新、请求验证时更新。
4. `vcs_events`：GitLab/GitHub webhook 原文摘要（合并请求、流水线），按问题单编号或关联编号挂接（从分支名、合并请求描述、提交信息里解析 `COHIVE-123` 之类的编号）。
5. Token 和费用：第一阶段先不做全自动。可选做法是在 Cohive 服务端实现精简的 OTLP/HTTP 日志接收接口，开发者把 `OTEL_LOGS_EXPORTER=otlp` 指向 Cohive（`cohive init` 可以写进用户级配置，因为项目级 `.claude/settings.json` 不能开遥测），只保留 `api_request`、`tool_result`、`tool_decision` 等事件的数值字段，按 `session.id` 加时间窗口归到问题单，汇总成 `issue_usage_rollup`。原始事件保留期短（例如 30 天）。
6. 防泄露：不收提示正文和工具参数；证据文本写入前用 gitleaks 规则扫描。

**后期方案**
- 第二阶段：提供团队级 OTel Collector 配置样例（Apache-2.0，脱敏处理器加属性处理），一份发给 Cohive 的精简接收接口，一份可选发给 Grafana LGTM（看整体用量趋势）或 Langfuse（看对话细节）。Cohive 只存汇总和指向外部系统的链接。
- 第三阶段：自动执行时由本机小助手启动 `claude -p` / `codex exec`，注入 `TRACEPARENT`（Cohive 为每次执行生成的链路）和 `OTEL_RESOURCE_ATTRIBUTES=cohive.issue_id=...,cohive.run_id=...`，归属精确；同时直接解析 `stream-json` / `--json` 事件流，得到每次执行的轮次、Token、时长，不依赖 OTel 后端。费用用 Cohive 内置价格表（可参考 LiteLLM 的 MIT 价格文件）重新计算，并标注“估算”。
- 审计加强：链头定期锚定到外部；如有合规要求再评估 Tessera。

**存储边界**
- Cohive 必须自己存（真相来源，长期保留）：问题单与状态流转、审批与决策、审计事件、会话与问题单关联、每个问题单的用量汇总（Token、估算费用、轮次、时长）、代码平台事件摘要、证据的引用（提交号、合并请求、流水线链接、复现脚本运行结果）。
- 交给外部系统（可选，短期保留，可丢）：原始遥测明细（每次模型请求、每次工具调用）、链路瀑布图、对话全文、按时间序列的用量看板。
- 原则：Cohive 的成功指标（交接耗时、闭环时长、升级率等）全部能从 Cohive 自己的 Postgres 算出来，不依赖外部系统是否部署。

**需要提醒决策者的风险**
- 交互式会话的“会话 ↔ 问题单”归属天然是近似的（一个会话可能同时处理多件事），用量统计应标注为“估算归属”。
- 让每个开发者的 Claude Code、Codex 把遥测发到团队服务器，涉及隐私和同事接受度（`user.email` 等身份字段默认就在事件里），需要事先说明收集范围，且 `cohive init` 默认不开启。
- 智能体执行所用额度归属（方案第 11 节第 4 项）会影响费用统计口径：订阅制下 `cost_usd` 只是折算值，不是真实支出。

### 缺口
- 精简 OTLP 接收接口的工作量、与 Collector 方案的取舍，本次只做了原理推断，未做原型验证。
- Claude Code 与 Codex 钩子能否稳定拿到会话编号并上报给 Cohive，需要实测确认。
