# 任务与问题单系统

> 调研日期：2026-10-14。仓库星数、最后推送时间、许可证等元数据均于当日通过 `gh api repos/OWNER/REPO` 实查。
> 评估对象：Cohive 方案 V0.1 第 5 节的“问题单存储与状态机”（状态 `OPEN → ROUTED → ACCEPTED → FIXING → READY_FOR_VERIFICATION → VERIFIED`，含 `REOPENED`、`ESCALATED`；字段含 `expected`、`actual`、`repro`、`commit`、`correlation_id`、`deadline` 等；每次状态变化记录“哪个人的哪个工具”）。
> 许可证判断仅为工程视角的一般理解，不构成法律意见。

## 一、面向编程智能体的任务/问题单工具（Beads、Backlog.md、Task Master 及其他）

### Takeaway
Beads 是这一类里最成熟、最接近 Cohive 需求的（Go、MIT、原子认领、可自定义状态、已有 GitLab/GitHub/Jira 双向同步），但它的存储是“每个仓库一个 Dolt 数据库、靠 git 远端推拉同步”，定位是单仓库/单团队内的智能体任务图，不是跨仓库、跨人的中心化服务端，不适合直接当 Cohive 的后端；Backlog.md 是仓库内 Markdown 文件、本地优先，同样无中心服务；Task Master 许可证带“公共条款（Commons Clause）”且活跃度明显下降，应排除。它们最大的价值是“可借鉴的设计”，而不是“可直接依赖的存储层”。

### Cited Findings

**Beads（仓库已从 steveyegge/beads 迁到 gastownhall/beads）**
- 元数据（2026-10-14 实查）：约 27.9k 星，许可证 MIT，主语言 Go，最后推送 2026-10-14，最新发布 v1.3.2-rc.2（2026-10-10），未归档。— [gastownhall/beads](https://github.com/gastownhall/beads)
- 定位：自述为“面向 AI 智能体的分布式图式问题追踪器，基于 Dolt”，用依赖图替代 Markdown 计划。— [Beads README](https://github.com/gastownhall/beads)
- 存储：使用 Dolt（版本化 SQL 数据库，单元格级合并、原生分支）。默认“嵌入模式”数据在 `.beads/embeddeddolt/`、**单写入者**；“服务器模式”连接外部 `dolt sql-server` 支持多并发写入。跨机同步靠 `bd dolt push / pull` 推拉 git 远端上的 `refs/dolt/data`；`.beads/issues.jsonl` 只是导出物，不是真源。— [Beads README](https://github.com/gastownhall/beads)
- Dolt 本身许可证 Apache-2.0（约 24.6k 星）。— [dolthub/dolt](https://github.com/dolthub/dolt)
- 数据模型与智能体友好特性：哈希 ID（如 `bd-a1b2`）避免多分支合并冲突；层级 ID 表示史诗/任务/子任务；`bd ready` 列出无阻塞可领任务；`bd update <id> --claim` **原子认领**（同时设负责人和进行中）；依赖类型含 blocks/related/parent-child，图链接含 relates-to、duplicates、supersedes、replies-to；有“消息”类型与线程；JSON 输出；`bd prime` 输出给智能体的工作流上下文；对旧的已关闭任务做语义压缩。— [Beads README](https://github.com/gastownhall/beads)
- 状态机：内置 open、in_progress、blocked 等，可用 `status.custom` 增加自定义状态，并给状态归类为 active / wip / done / frozen，类别决定是否出现在 `bd ready`。— [bd statuses 文档](https://github.com/gastownhall/beads/blob/main/docs/cli-reference/statuses.md)
- 外部系统同步：有 `bd gitlab`（支持自建 GitLab URL、项目级与组级同步，push/pull/sync）、`bd github`（支持 `GITHUB_API_URL` 指向 GitHub Enterprise）、以及 jira、linear、ado（Azure DevOps）、notion 等子命令。— [bd gitlab 文档](https://github.com/gastownhall/beads/blob/main/docs/cli-reference/gitlab.md)；[bd github 文档](https://github.com/gastownhall/beads/blob/main/docs/cli-reference/github.md)；[命令清单目录](https://github.com/gastownhall/beads/tree/main/docs/cli-reference)
- 多工作空间：`bd federation` 让多个工作空间各自维护 Dolt 库并通过远端共享更新，需要 CGO 构建。— [bd federation 文档](https://github.com/gastownhall/beads/blob/main/docs/cli-reference/federation.md)
- MCP：另有 Python 包 `beads-mcp`（`uv tool install beads-mcp`），官方文档明确说“有命令行时优先用命令行 + 钩子，更省上下文”，MCP 主要给 Claude Desktop 等无命令行环境。— [Beads MCP 文档](https://github.com/gastownhall/beads/blob/main/docs/integrations/mcp-server.md)
- 接入方式：`bd init` 默认写入 `AGENTS.md`，`bd setup claude / codex / cursor` 等安装钩子和指令。— [Beads README](https://github.com/gastownhall/beads)
- 升级涉及模式迁移时，需要“恰好一个指定克隆”执行 `bd migrate schema` 并推送，其余克隆 `bd bootstrap`。— [Beads README](https://github.com/gastownhall/beads)

**Backlog.md**
- 元数据：约 7.0k 星，MIT，TypeScript，最后推送 2026-10-14，最新发布 v1.53.0（2026-09-24）。— [MrLesk/Backlog.md](https://github.com/MrLesk/Backlog.md)
- 存储：任务是项目内 `backlog/`（可配置）目录下的人类可读 Markdown 文件；“本地优先，无服务器、无账号、无遥测”，git 可选（`--no-git`）。任务 ID 前缀可配置（如 `TASK-1`）。— [Backlog.md README](https://github.com/MrLesk/Backlog.md)
- 字段：描述、验收标准、完成定义（DoD）清单、计划/笔记/最终总结、依赖链接；可配置最终状态。— [Backlog.md README](https://github.com/MrLesk/Backlog.md)
- 多人同步：靠 git；配置项 `checkActiveBranches`、`remoteOperations`、`activeBranchDays` 用于跨分支读取任务状态。— [Backlog.md README](https://github.com/MrLesk/Backlog.md)
- MCP：`backlog mcp start`，支持 Claude Code、Codex、Gemini CLI、Kiro、Cursor；但作者把“命令行指令”设为默认接入方式，MCP 为可选。网页看板 `backlog browser` 只监听 127.0.0.1。— [Backlog.md README](https://github.com/MrLesk/Backlog.md)

**Task Master（eyaltoledano/claude-task-master）**
- 元数据：约 28.2k 星；GitHub 识别许可证为 NOASSERTION；最新发布 task-master-ai@0.43.1（2026-03-31），最后一次提交 2026-04-23（内容是替换已下线的 task-master.dev 网址），之后近 6 个月无推送。— [claude-task-master](https://github.com/eyaltoledano/claude-task-master)
- 许可证：MIT 加 **“Commons Clause” 许可条件 v1.0**，不授予“销售”权利，“销售”包括以收费方式提供托管、咨询、支持等、且产品价值主要来自本软件。— [Task Master LICENSE](https://github.com/eyaltoledano/claude-task-master/blob/main/LICENSE)
- 存储：任务存在 `tasks.json`，字段 id、title、description、status、dependencies、priority、details、testStrategy、subtasks、metadata；状态示例有 pending、in-progress、done、deferred；文档未描述多人同步。文档站已迁到 tryhamster.com（Hamster 商业平台）。— [Task Master 任务结构文档](https://tryhamster.com/docs/taskmaster/capabilities/task-structure)；[README](https://github.com/eyaltoledano/claude-task-master)

**其他面向智能体的工具**
- CCPM（automazeio/ccpm）：MIT，约 8.4k 星，最后推送 2026-03-18；以 **GitHub Issues 为真源**，PRD → 史诗 → GitHub 议题/子议题 → 工作树并行。— [automazeio/ccpm](https://github.com/automazeio/ccpm)
- Vibe Kanban（BloopAI/vibe-kanban）：Apache-2.0，约 28.4k 星，README 明确写“Vibe Kanban is sunsetting”（正在停止维护）。— [BloopAI/vibe-kanban](https://github.com/BloopAI/vibe-kanban)
- Shrimp Task Manager（MIT，约 2.1k 星，最后推送 2025-08-21）、ATLAS MCP（Apache-2.0，Neo4j，约 0.5k 星，最后推送 2025-07-22）：均已一年以上无更新。— [mcp-shrimp-task-manager](https://github.com/cjo4m06/mcp-shrimp-task-manager)；[atlas-mcp-server](https://github.com/cyanheads/atlas-mcp-server)

### Inferences
- 这一类工具的共同假设是“任务住在仓库里（或仓库旁的版本化数据库里）”，同步靠 git。Cohive 的问题单天然是**跨仓库**的（A 的前端仓库发现、B 的订单服务仓库修复），存在 A 的仓库还是 B 的仓库都不对，必须有一个中心化的工作空间级存储——这与 Beads/Backlog.md 的基本假设冲突。
- Beads 的嵌入模式单写入者、服务器模式需另起 `dolt sql-server`，加上模式迁移要“指定一个克隆执行”，作为中心服务后端会引入第二个数据库（Dolt），与“Go + Postgres 单数据库、单可执行文件发布”的技术选型相冲突。
- Beads 值得直接借鉴的设计：原子认领（`--claim`）、状态分类（active/wip/done/frozen 决定是否进入“可领”队列）、`ready` 队列、哈希 ID、`prime` 式的智能体上下文注入、JSON 输出，以及“命令行 + 钩子优先、MCP 兜底”的接入策略（与 Cohive 方案第 4.2 节一致）。
- 一个可能的协作点：开发者本机已用 Beads 管理自己仓库内任务时，Cohive 可提供“把 Cohive 问题单落成本仓库的一个 bead”的单向投递，而不是替代它。
- Task Master 的 Commons Clause 使其不是 OSI 认可的开源许可证：公司内部自用一般不受影响，但 Cohive 若开源且有人提供收费托管，依赖它会带来许可证风险；加之活跃度下降，建议排除。
- Backlog.md 适合单仓库内的人机共读任务清单，不适合 Cohive 的跨人路由与验证闭环。

### Gaps
- 未逐条核实 Beads 的 GitLab/GitHub 同步是否支持自定义状态与议题字段的映射（例如把 `READY_FOR_VERIFICATION` 映射为标签），文档只列出了命令与配置项。
- 未核实 Beads 是否提供可被 Go 程序直接嵌入调用的稳定库接口（README 只描述命令行）。
- 未系统检索 2026 年新出现的其他智能体任务工具（如各家编程工具自带的任务系统），本节只覆盖用户点名及检索到的几个。

## 二、通用开源项目管理系统作为后端（Plane、Huly、OpenProject、Taiga、Vikunja、Focalboard）

### Takeaway
没有一个能“直接拿来当 Cohive 问题单后端而不增加负担”：Plane 功能最全且有官方 MCP，但社区版为 AGPL-3.0，结构化字段（工作项类型、自定义属性）属于付费档；Vikunja 是 Go + AGPL、最轻量，但只有通用任务模型、无官方 MCP；OpenProject 为 GPL-3.0 的 Ruby 系统，官方 MCP 只读且是企业附加功能；Huly 无公开 REST API；Taiga 活跃度低；Focalboard 已无人维护。任何一个都意味着让 Cohive 用户额外部署和运维一整套系统，违背“接入成本压到最低、单可执行文件发布”的原则。

### Cited Findings
- 元数据（2026-10-14 实查）：
  - Plane：约 60.8k 星，AGPL-3.0，TypeScript（后端为 Python，见下方 MCP 服务依赖 plane-sdk），最后推送 2026-10-14，最新发布 v1.4.3-rc1（2026-10-06）。— [makeplane/plane](https://github.com/makeplane/plane)
  - Huly：约 27.9k 星，EPL-2.0，TypeScript，最后推送 2026-10-14。— [hcengineering/platform](https://github.com/hcengineering/platform)
  - OpenProject：约 16.4k 星，GPL-3.0，Ruby，最后推送 2026-10-14。— [opf/openproject](https://github.com/opf/openproject)
  - Taiga 后端：约 0.86k 星，MPL-2.0，Python，最后推送 2026-09-28。— [taigaio/taiga-back](https://github.com/taigaio/taiga-back)
  - Vikunja：约 5.7k 星，AGPL-3.0，Go，最后推送 2026-10-14，最新发布 v2.7.0（2026-10-02）。— [go-vikunja/vikunja](https://github.com/go-vikunja/vikunja)
  - Focalboard（独立版）：约 26.5k 星，README 顶部声明“此仓库当前无人维护”，最后推送 2026-05-18。— [mattermost-community/focalboard](https://github.com/mattermost-community/focalboard)
- Plane 官方 MCP 服务：MIT，Python 3.10+（基于 FastMCP 与官方 plane-sdk），支持 stdio、托管远程 HTTP（`https://mcp.plane.so/http/mcp`）和自建 HTTP；可用 `PLANE_BASE_URL` 指向自建 Plane；30 个工具覆盖 207 个操作，列表/搜索支持 Plane 查询语言。— [makeplane/plane-mcp-server](https://github.com/makeplane/plane-mcp-server)
- Plane 工作项类型（Bug、需求等自定义类型，各带自定义属性）在官方文档中标为 Pro 功能；定价页显示免费档无自定义属性，Pro 有项目级自定义属性，企业档有工作空间级属性。— [Plane 工作项类型文档](https://docs.plane.so/work-item-types)；[Plane 定价](https://plane.so/pricing.md)
- Plane 的“自动化规则发送 Webhook”步骤：定价表显示“触发与动作”在 Pro 不可用、Business 可用；第三方评测称社区版提供 REST API 与 Webhook。两者说法未能互相印证。— [Plane 定价](https://plane.so/pricing.md)；[第三方评测](https://www.besthub.dev/articles/plane-58k-star-open-source-jira-alternative-for-self-hosted-project-management-111d0eb21153)
- OpenProject 17.2 加入官方 MCP 服务，暴露 API v3 中的项目、工作包、用户等；当前版本**不提供写入**；作为企业附加功能，从 Professional 档起提供；社区有多个可写的第三方 MCP（基于 API v3）。— [heise 报道](https://heise.de/-11209316)；[Glama 收录](https://glama.ai/mcp/servers/eps0sxfj9p)
- Huly 没有公开 REST API，程序化访问只能通过经 WebSocket 连接的 JavaScript SDK；只有社区 MCP 服务（如 @firfi/huly-mcp），且有分支作者称上游在自建版上部分写操作会静默失败。— [huly-mcp（Glama）](https://glama.ai/mcp/servers/@dearlordylord/huly-mcp)；[jokeks2023/huly-mcp](https://hub.docker.com/r/jokeks2023/huly-mcp)
- 有 MCP 收录页称“Huly 托管版即将关闭、自建不受影响”，但无法确认年份与原始出处。— [huly-mcp-server（Glama）](https://glama.ai/mcp/servers/bgx4k3p/huly-mcp-server)
- Vikunja：提供按资源授权的每用户 API 令牌（任务、项目、标签各自可设读/建/改/删）；无官方 MCP，社区有多个 MCP（其中一个 FastMCP 版本含 Webhook 操作、约 71 个工具，并透传调用者令牌以保留审计链）。— [vikunja-mcp（Glama）](https://glama.ai/mcp/servers/TadMSTR/vikunja-mcp)；[vikunja-mcp（mcp.so）](https://mcp.so/servers/vikunja-mcp?tab=tools)

### Inferences
- **AGPL 对集成的影响**：Cohive 若只通过网络 API 调用独立部署的 Plane / Vikunja，通常不会使 Cohive 自身代码受 AGPL 约束；但如果把它们修改后打包进 Cohive 镜像一起分发、或以修改版对外提供服务，就需要公开对应源码。对“可能开源、希望以单镜像发布”的 Cohive 来说，把 AGPL 系统作为必需依赖会让许可证说明和部署形态都变复杂。公司内部自用无问题。
- GPL-3.0（OpenProject）同理，网络调用不传染；EPL-2.0（Huly）为文件级弱著佐权，问题主要在“没有公开 API”。MPL-2.0（Taiga）最宽松，但活跃度低。
- **数据模型不匹配**：Cohive 问题单的核心是“期望/实际/复现脚本/提交号/验证结果/轮次/升级原因/操作者是哪个人的哪个工具”，通用项目管理系统大多只有标题、描述、标签、负责人，结构化字段要么收费（Plane 自定义属性在 Pro）、要么只能塞进描述文本或标签，状态机约束（例如只有发起方能 `verify`、`REOPENED` 只能回到 `FIXING`）需要 Cohive 在外层自己实现。
- **运维负担**：要求每个 Cohive 用户另起一套 Plane（多组件）或 OpenProject（Ruby 栈），与方案第 2 节“新人接入三步”、第 7.1 节“单可执行文件 / 单镜像发布”直接冲突。Vikunja 是 Go 单程序，是其中最轻的，但仍是第二套系统、第二套用户与权限体系。
- 这类系统的合理位置是“可选的外部视图/同步目标”，不是 Cohive 的真源。

### Gaps
- 未实测 Plane 社区版（自建 Community Edition）是否包含 Webhook 与 API 令牌，资料相互矛盾。
- 未核实 Plane 自建所需的具体组件清单与资源占用。
- 未逐个核实 Vikunja 原生 Webhook 的事件类型与负载格式（检索结果均来自社区 MCP 收录页）。
- 未核实 Taiga 是否已转向新一代项目（检索未覆盖）。

## 三、直接用代码托管平台议题（GitLab Issues、GitHub Issues）当问题单

### Takeaway
技术上可行、并且有现成先例（CCPM 以 GitHub Issues 为真源、Beads 内置 GitLab/GitHub 同步），两家官方 MCP 服务也都已具备议题读写能力。但关键限制是：**GitLab 的作用域标签、可配置状态、自定义字段全部是 Premium/Ultimate 付费功能**，如果公司私有化 GitLab 是免费版，就只能用普通标签模拟状态，互斥性和合法流转全靠 Cohive 自己保证；同时议题无法原生表达“验证闭环、轮次、超时升级、操作者是哪个工具”，两平台的结构化字段能力和 MCP 部署形态差异也很大。适合做“镜像与通知面”，不适合做状态机真源。

### Cited Findings

**GitLab**
- 作用域标签（`key::value`，同键互斥，可嵌套如 `workflow::backend::review`，看板拖动时自动替换）可用于建模工作流状态和“自定义字段”，但该功能 **Tier: Premium, Ultimate**，免费版没有。— [GitLab 标签文档](https://docs.gitlab.com/user/project/labels/)
- 可配置工作项状态（Work item status）：**Premium、Ultimate**；对议题与任务在 18.2 引入、18.4 正式可用；生命周期（Lifecycles）18.5 引入、18.6 正式可用；默认状态 To do / In progress / Done / Won't do / Duplicate，状态类别有 Triage、To do、In progress、Done、Canceled，Done 与 Canceled 会自动关闭议题；文档称它可以替代用标签管理生命周期。— [GitLab 工作项状态文档](https://docs.gitlab.com/user/work_items/status/)
- 自定义字段：**Premium、Ultimate**；17.11 引入、18.0 正式可用；类型仅有单选、多选、数字、文本四种；每个顶层组最多 50 个活跃字段，每种工作项类型最多 10 个，文本值最长 1024 字符。— [GitLab 自定义字段文档](https://docs.gitlab.com/user/work_items/custom_fields/)
- GitLab 官方 MCP 服务：Free/Premium/Ultimate 均可用，覆盖 GitLab.com、自建（Self-Managed）、Dedicated；版本历史为 18.3 实验、18.6 测试（新增 HTTP 传输）、19.2 成为独立设置并下放到免费版、19.5 正式可用并支持工具集选择。需要管理员（自建为实例级）允许访问。认证只接受带 `mcp` 范围的 OAuth 令牌或带 MCP 执行权限的细粒度个人令牌；**传统个人/项目/组令牌即使有 `api` 范围也会被 403 拒绝**。默认工具集含 core、merge_requests、work_items、repository、ci；GitLab.com 免费版每用户每分钟 60 次调用，付费 600 次；动态客户端注册每 IP 每小时限 10 次；官方提醒防范提示注入。— [GitLab MCP 服务文档](https://docs.gitlab.com/user/model_context_protocol/mcp_server/)

**GitHub**
- 官方 MCP 服务（github/github-mcp-server）：MIT，Go，约 33.6k 星，最后推送 2026-10-13。— [github/github-mcp-server](https://github.com/github/github-mcp-server)
- 远程服务地址 `https://api.githubcopilot.com/mcp/`；**GitHub Enterprise Server 不支持远程服务**，只能本地运行并设置 `GITHUB_HOST`；GHES 上用 OAuth 需自建 OAuth 应用或 GitHub App。— [github-mcp-server README](https://github.com/github/github-mcp-server)
- 议题工具：`issue_read`（含评论、子议题、父议题、标签）、`issue_write`（标签、负责人、里程碑、议题类型、父链接）、`sub_issue_write`、评论增改、`list_issues`/`search_issues`、标签管理；支持**自定义议题字段**（`issue_write` 可设值，`list_issues` 可按字段过滤，`list_issue_fields` 列出字段）；另有 projects 工具集（读写项目、字段、条目、状态更新）。— [github-mcp-server README](https://github.com/github/github-mcp-server)

**先例**
- CCPM 明确以 GitHub Issues 为真源，理由是让多个智能体会话之间有共享状态；仅支持 GitHub。— [automazeio/ccpm](https://github.com/automazeio/ccpm)
- Beads 提供 `bd gitlab` / `bd github` 推拉同步，支持自建 GitLab 地址与 GitHub Enterprise API 地址。— [bd gitlab](https://github.com/gastownhall/beads/blob/main/docs/cli-reference/gitlab.md)；[bd github](https://github.com/gastownhall/beads/blob/main/docs/cli-reference/github.md)

### Inferences
- **免费版 GitLab 的状态机困境**：没有作用域标签时，“`cohive::fixing` 与 `cohive::ready-for-verification` 同时存在”在平台层面是合法的；多个智能体并发改标签没有比较并交换（CAS）语义，可能出现状态竞争。必须由 Cohive 服务端做唯一写入者并负责纠偏，这实际上已经是“自建状态机”。
- **结构化字段**：期望、实际、复现脚本、证据等只能放在议题描述（议题模板 / GitHub Issue Forms 生成的 Markdown 段落）里，读回来要解析文本，可被人手工改坏；GitLab 自定义字段即使付费也只有 4 种类型、文本 1024 字符上限，放不下复现脚本。
- **两平台差异**：状态（GitLab 工作项状态 vs GitHub 议题只有 open/closed + 项目字段）、自定义字段（GitLab 组级付费 vs GitHub 组织级议题字段）、层级（GitLab 任务/史诗 vs GitHub 子议题）、MCP 形态（GitLab 实例内置 vs GHES 只能本地跑）都不一样。抽象成本主要在“状态与字段映射”，而这正是 Cohive 想自己掌控的部分。
- **跨仓库问题单归属**：议题必须挂在某个项目/仓库下；Cohive 的问题单是从 A 仓库发现、路由到 B 的服务，挂在哪个仓库、B 不在该仓库有无权限、跨 GitLab 与 GitHub 的问题（前端在 GitHub、后端在 GitLab）如何表示，都没有自然答案。
- **“哪个人的哪个工具”的审计**：平台议题只记录账号，不记录是 Claude Code 还是 Codex 操作；若所有写入都经 Cohive 服务账号代发，则平台侧审计失真。
- **好处仍然明显**：开发者本来就在看议题和合并请求，议题与合并请求、流水线的天然关联（`Closes #123`）正是 Cohive 第二阶段“合并请求与流水线联动”需要的；两家官方 MCP 都可让智能体直接读议题，无需 Cohive 再包一层。
- **对公司 GitLab 的前置检查**：需确认公司私有化 GitLab 的版本（MCP 服务 19.2 起才进免费版、19.5 才正式可用）与授权档位（免费版无作用域标签/状态/自定义字段）；还要确认实例管理员是否愿意开启 MCP 访问、是否允许细粒度个人令牌。

### Gaps
- 未核实公司私有化 GitLab 的实际版本与授权档位（会直接决定第三条路线的可行度）。
- 未核实 GitHub 自定义议题字段、议题类型的正式可用状态与套餐要求（只看到 MCP 服务已支持读写）。
- 未逐条列出 GitLab MCP 服务 `work_items` 工具集的具体工具（官方文档链接到单独的工具页，本次未抓取）。
- 未核实 GitLab/GitHub Webhook 的投递重试语义（至少一次、失败重试次数），这对用 Webhook 驱动状态机很关键。

## 四、四条路线对比与推荐

### Takeaway
推荐“**自建薄状态机作为真源 + 代码平台议题作为镜像与入口 + 借鉴 Beads 的智能体交互设计**”：问题单表与状态机自建在 Cohive 的 Postgres 里（这是 Cohive 的核心领域，任何现成系统都要大量外层逻辑才能表达），通过 GitLab/GitHub 适配器把问题单单向（或有限双向）镜像为议题、关联合并请求与流水线；不引入 Plane/Vikunja 等第二套系统，不依赖 Beads/Task Master 作存储。所谓“不重复造轮子”应体现在：状态机用成熟的 Go 库/约定、队列用 river、平台交互用官方 MCP 与官方 API 客户端，而不是把核心领域模型外包。

### Cited Findings
- 智能体专用工具的存储均为仓库内或仓库旁（Beads 用 Dolt + git 远端同步、嵌入模式单写入者；Backlog.md 用仓库内 Markdown；Task Master 用 `tasks.json`）。— [Beads README](https://github.com/gastownhall/beads)；[Backlog.md README](https://github.com/MrLesk/Backlog.md)；[Task Master 任务结构](https://tryhamster.com/docs/taskmaster/capabilities/task-structure)
- Beads 已有 GitLab/GitHub/Jira/Linear 同步、原子认领、状态分类等能力，是同类中最成熟的开源实现（Go、MIT、活跃）。— [gastownhall/beads](https://github.com/gastownhall/beads)；[bd statuses](https://github.com/gastownhall/beads/blob/main/docs/cli-reference/statuses.md)
- 通用项目管理系统中 Plane、Vikunja 为 AGPL-3.0，OpenProject 为 GPL-3.0，Plane 结构化字段属付费档，OpenProject 官方 MCP 只读且为企业附加功能，Huly 无公开 REST API，Focalboard 无人维护。— 见第二节各引用
- GitLab 状态与字段相关能力（作用域标签、工作项状态、自定义字段）均需 Premium/Ultimate；GitLab MCP 服务 19.5 正式可用、免费版可用；GitHub MCP 远程服务不支持 GHES。— 见第三节各引用

### 对比表（基于上述引用的综合判断）

| 维度 | A. 智能体专用工具（以 Beads 为代表） | B. 通用项目管理系统（以 Plane/Vikunja 为代表） | C. 代码平台议题（GitLab/GitHub） | D. 自建（Postgres 表 + 状态机） |
|---|---|---|---|---|
| 跨仓库、跨人中心存储 | 弱：按仓库存储，靠 git 推拉 | 强 | 中：议题必须挂在某仓库下 | 强 |
| 期望/实际/复现脚本等结构化字段 | 中：有描述、元数据，需约定 | 弱到中：自定义属性多为付费 | 弱：只能放描述文本；GitLab 字段付费且有长度上限 | 强：按需建模 |
| 状态机约束与原子认领 | 中：有原子认领、自定义状态，无角色约束 | 弱：外层自己做 | 弱：免费版无互斥状态，无 CAS | 强：事务 + 行锁/版本号 |
| 验证闭环、轮次、超时升级 | 无 | 无，需外层 | 无，需外层 | 按需实现（river 定时任务） |
| “人 + 工具”审计 | 无 | 账号级 | 账号级 | 原生支持 |
| 与合并请求/流水线联动 | 经同步间接 | 需额外集成 | 原生最强 | 经适配器 |
| 部署负担 | 每仓库一个 Dolt 库 | 多一套系统 | 无（已有平台） | 无（Cohive 自身） |
| 许可证风险 | Beads MIT 无风险；Task Master 有 Commons Clause | AGPL/GPL，需分开部署 | 无 | 无 |
| GitLab 私有化 + GitHub 双支持 | Beads 已支持两者同步 | 需各自集成 | 需适配器抽象两平台差异 | 需适配器（本来就要做） |

### Inferences
- **为什么不是 A**：Cohive 的问题单是工作空间级、跨仓库的对象，Beads 的仓库内存储与单写入者模式不合适；引入 Dolt 也违背“单 Postgres”。但应在设计文档中显式借鉴：`ready` 队列 + 原子 `claim`、状态分类、哈希或带前缀的短 ID、JSON 输出、`prime` 式上下文注入、“命令行 + 钩子优先、MCP 兜底”。
- **为什么不是 B**：多一套系统、多一套账号权限、AGPL/GPL 依赖、核心字段与状态约束仍要外层实现，投入产出比最差。
- **为什么不是 C 作真源**：免费版 GitLab 无法表达互斥状态；结构化字段与验证闭环无处安放；跨平台差异正好落在 Cohive 最核心的状态与字段上；智能体并发写标签有竞态。
- **为什么是 D + C 镜像**：问题单表本身不是“轮子”而是 Cohive 的产品本体（路由、闭环、升级、审计都围绕它），自建成本实际很小（一张主表 + 一张状态变更事件表 + 一张评论/证据表，状态迁移在单事务里校验）；真正耗时的“看板、通知、与合并请求联动”可以复用平台：
  1. 真源：Postgres 中 `issues` 主表 + `issue_events`（只追加的状态变更日志，记录操作者“人 + 工具”）；状态迁移用显式迁移表校验，认领用 `UPDATE ... WHERE status = 'ROUTED' AND owner_claimed IS NULL` 或版本号实现原子性（思路同 Beads `--claim`）。
  2. 平台镜像：适配器接口只抽象最小集合——“创建/更新镜像议题、写评论、读合并请求与流水线状态、接收 Webhook”；镜像议题上用普通标签（如 `cohive:fixing`）展示状态，由 Cohive 作为唯一写入者，平台上被人手改的标签视为“请求”，经 Cohive 校验后回写或纠正。这样免费版 GitLab 也能用，付费版可选映射到原生工作项状态。
  3. 智能体入口：仍走 Cohive 自己的远程 MCP（方案第 4.1 节），因为它要承载路由、验证、审计；平台官方 MCP 只作为智能体读取合并请求/流水线细节的补充，不作为写入问题单的通道（避免绕过状态机）。
  4. 与 Beads 的可选互通：后期可提供“把分给我的 Cohive 问题单投递为本仓库的一个 bead”的导出，服务已用 Beads 的开发者。
- **提醒（方案框架之外）**：
  - 方案第 5.1 节的状态多达 8 个，建议参考 Beads/GitLab 的“状态 + 类别”两层设计（例如类别：待处理 / 进行中 / 待验证 / 已结束 / 已冻结），后续加状态不影响路由、收件箱等按类别工作的逻辑。
  - `ESCALATED` 设计为“任意状态 → ESCALATED”会丢失升级前所处的状态；建议把“升级”做成与状态正交的标记（`escalated_at`、`escalation_reason`），否则处理完升级后不知道回到哪个状态。
  - 复现脚本“必填”在跨仓库场景下会遇到“脚本依赖发起方仓库环境”的问题；建议字段里区分“脚本内容”“运行环境/镜像”“预期退出码”，否则第 5 步“自动重跑”难以实现。
  - 若坚持“不造轮子”，最有价值的复用点其实是**状态机之外**：任务队列与定时升级用 river、平台交互用官方 Go 客户端（GitLab 的 Go 客户端、GitHub 的 go-github），以及让智能体读平台细节时直接用两家官方 MCP。

### Gaps
- 公司私有化 GitLab 的版本与档位未知，若为 Premium 及以上，C 路线中“原生工作项状态 + 自定义字段”的镜像体验会明显更好，需复核。
- 未实测 Beads `bd gitlab` 同步在自定义状态下的映射行为，若映射可配置，可作为“镜像层”的参考实现或在开发者本机侧复用。
- 未核实 Go 生态中可直接复用的状态机库的现状（如 looplab/fsm 等）的活跃度与许可证，本次调研范围未覆盖。
- 未评估 Linear、Jira 等商业系统（不在“可自托管开源”范围内）。
