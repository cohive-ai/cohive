> 调研日期：2026-10-14。仓库数据（星标数、许可证、是否归档、最近推送时间）均为当天用 `gh api repos/...` 实查。本机版本：Claude Code 2.1.288、Codex 命令行 0.154.0，命令行参数均来自本机 `--help` 输出（未执行任何会产生费用的任务）。

## 问题一：统一驱动编程智能体的协议与适配器（ACP 覆盖度、Codex 的替代接入方式、权限请求能否对接人工审批）

### Takeaway
智能体客户端协议（ACP）已成为驱动多种编程智能体的事实标准：官方注册表收录 40 多个智能体（含 Claude Code、Codex、Gemini CLI、OpenCode、Goose、Cursor、Copilot 命令行等），协议本身有标准的 `session/request_permission` 权限请求，可直接映射为 Cohive 的人工审批；而且有 Apache-2.0 的 Go 软件开发包（coder/acp-go-sdk）。Codex 的 ACP 适配器已从 zed-industries 迁到 agentclientprotocol 组织，新版改为基于 Codex 应用服务器（app-server）实现。主要短板：ACP 的远程传输（HTTP / WebSocket）仍是草案，目前稳定的只有本机标准输入输出。

**权限请求与人工审批**
- ACP 中由智能体向客户端发送 `session/request_permission`；选项类型有 `allow_once`、`allow_always`、`reject_once`、`reject_always`；客户端返回 `selected`（带所选 optionId）或 `cancelled`；“如果当前轮次被取消，客户端必须返回 cancelled”；客户端“可以按用户设置自动允许或拒绝” — [ACP 工具调用规范](https://agentclientprotocol.com/protocol/tool-calls)
- Codex app-server 的服务端→客户端审批请求：`item/commandExecution/requestApproval`（决定：accept、acceptForSession、decline、cancel）、`item/fileChange/requestApproval`、`item/permissions/requestApproval`、`item/tool/requestUserInput`（可带 `autoResolutionMs` 超时自动处理）、`mcpServer/elicitation/request` — [Codex App Server 文档](https://learn.chatgpt.com/docs/app-server)

**远程传输现状**
- ACP 于 2026-04-22 成立传输工作组，正在起草“可流式 HTTP 与 WebSocket 传输”RFD：单一 `/acp` 端点，HTTP 方式用 SSE 长流 + POST（要求 HTTP/2），或 WebSocket 升级；复用现有标准输入输出传输的 JSON-RPC 格式与生命周期 — [传输工作组公告](https://agentclientprotocol.com/announcements/transports-working-group)；[RFD 草案](https://agentclientprotocol.com/rfds/streamable-http-websocket-transport.md)
- Rust 软件开发包 2.0.0（2026-07-23）已包含 HTTP/SSE 与 WebSocket 传输相关的破坏性变更；Dart、Java 有早期实现 — [Rust crate CHANGELOG](https://docs.rs/crate/agent-client-protocol/2.0.0/source/CHANGELOG.md)

**已废弃的同类方案**
- coder/agentapi（以 HTTP API 控制 Claude Code、Goose、Aider、Gemini、Codex 等，MIT）已归档，README：“AgentAPI 已弃用且不再维护” — [coder/agentapi](https://github.com/coder/agentapi)

### Inferences
- Cohive 的本机小助手（Go）可以作为 **ACP 客户端**，通过 coder/acp-go-sdk 以子进程方式拉起 `claude-agent-acp` / `codex-acp` / `gemini --acp` 等，一套代码覆盖多种工具，避免逐个适配 stream-json 与 app-server 两套私有协议。这与方案文档第 2 节“不深度适配任何一个工具的内部机制”一致，且 ACP 适配器由社区和厂商维护，工具升级的适配成本外包出去。
- ACP 的 `session/request_permission` 可直接映射为 Cohive 看板里的“待审批”卡片：小助手收到请求→推给协作服务→看板/系统通知让人点允许或拒绝→回填 optionId。超时可回 `reject_once`。
- ACP 远程传输尚未定稿，因此第三阶段的“服务器端执行节点”也应让执行节点本地拉起 ACP 子进程，节点与协作服务之间仍用 Cohive 自己的 WebSocket 通道，不要依赖 ACP 远程传输。
- codex-acp 新版建在“实验性、非生产”的 app-server 之上，这是一个依赖风险；需要在 Cohive 里保留 `codex exec --json` 作为降级路径。

### Gaps
- `codex mcp-server` 的移除时间与官方说明未查到：本机 0.154.0 子命令列表中没有它，但没有在发布说明中找到对应条目，未核实是“移除”还是“改名/隐藏”。
- 未逐一核实每个注册表条目（如 Gemini CLI 的 ACP 启动参数是否已从 `--experimental-acp` 转正）。
- 未核实 coder/acp-go-sdk 对应的 ACP 协议版本是否覆盖最新的子智能体会话、AIR 扩展等能力。

## 问题二：各工具的非交互执行、事件流与钩子能力

### Takeaway
两家都有成熟的无界面执行与结构化事件流：Claude Code 用 `claude -p --output-format stream-json`（可配 `--input-format stream-json` 双向流、`--resume`、`--worktree`、`--max-budget-usd`、`--permission-prompts none`），Codex 用 `codex exec --json`（可配 `--worktree`、`--sandbox`、`--output-schema`、`resume`）。两家的钩子都能在会话开始/提交提示词时注入额外上下文，Claude Code 钩子还支持直接 HTTP 回调，非常适合 Cohive 采集事件和注入待办。Claude Agent SDK 只有官方 TypeScript / Python 版，没有官方 Go 版。

### Cited Findings
**Claude Code 无界面执行（本机 2.1.288）**
- 本机帮助列出：`-p/--print`、`--output-format text|json|stream-json`、`--input-format text|stream-json`（实时流式输入）、`--include-hook-events`（在输出流中包含所有钩子生命周期事件）、`--include-partial-messages`、`--json-schema`、`--max-budget-usd`、`--permission-mode acceptEdits|auto|bypassPermissions|manual|dontAsk|plan`、`--permission-prompts host|none`、`--resume`、`--session-id <uuid>`、`--fork-session`、`--no-session-persistence`、`-w/--worktree [name]`、`--bare`、`--mcp-config`、`--strict-mcp-config`、`--restricted`、`--bg/--background`（后台会话，配合 `claude attach/logs/stop/rm/agents`） — 本机命令行帮助
- 官方文档：`--output-format stream-json` 输出换行分隔 JSON，最后一行是 `result` 消息（含最终文本、费用、会话元数据）；`system/init` 事件报告模型、工具、MCP 服务器、插件；`--resume <session_id>` 可继续指定会话，会话 ID 可从 json 输出中取得 — [Run Claude Code programmatically](https://code.claude.com/docs/en/headless)
- 官方文档：“`--bare` 是脚本与 SDK 调用的推荐模式，未来会成为 `-p` 的默认值”；bare 模式“从不读取 OAuth 凭据或系统钥匙串”，需设置 `ANTHROPIC_API_KEY` — 同上
- 官方文档：不加 `--bare` 时，“`-p` 会话会运行项目 `.claude/settings.json` 中的钩子并连接其 `.mcp.json` 中的服务器，即使是从未信任过的文件夹”；`-p` 不显示工作区信任对话框 — 同上
- `--permission-prompts none`：无人可答时，凡是会弹出权限询问的操作一律拒绝（除非 PermissionRequest 钩子放行），在 stream-json 中以 `permission_denied` 系统消息出现，最终 result 列出 `permission_denials`；需 v2.1.259 及以上 — 同上
- 使用 SIGTERM 停止时退出码 143，进行中的轮次不记录结果；要正常结束轮次应先发 SIGINT 或调用 SDK 的 `interrupt()` — 同上

**Claude Agent SDK**
- 官方仅提供 Python 与 TypeScript；“要从其他语言驱动同样的智能体循环，请以 `-p` 和 `--output-format json` 把命令行作为子进程运行”；SDK 本质是“运行 Claude Code 二进制的库” — [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)
- 许可：TypeScript 版仓库 LICENSE 为“保留所有权利，受 Anthropic 商业条款约束”（本机 gh 实查）；Python 版仓库 GitHub 显示 MIT，但官方文档称“Claude Agent SDK 的使用受 Anthropic 商业服务条款约束，除非某组件的 LICENSE 文件另有说明” — [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)；本机 `gh api repos/anthropics/claude-agent-sdk-python`（MIT，约 8276 星）
- 没有官方 Go 版；社区 Go 移植有 panbanda/claude-agent-sdk-go、chai-rs/go-claude（v0.2.0）、next-bin/claude-agent-sdk-golang、tggo/claude-agent-go 等，多为包装命令行子进程、版本均在 1.0 以前 — [pkg.go.dev 搜索结果](https://pkg.go.dev/github.com/panbanda/claude-agent-sdk-go)；[chai-rs/go-claude](https://pkg.go.dev/github.com/chai-rs/go-claude)

**Codex 无界面执行（本机 0.154.0）**
- `codex exec` 参数：`--json`（以 JSONL 向标准输出打印事件）、`-o/--output-last-message <FILE>`、`--output-schema <FILE>`、`-s/--sandbox read-only|workspace-write|danger-full-access`、`--approve-for-me`（审批请求交给自动审查）、`--dangerously-bypass-approvals-and-sandbox`、`--worktree`（在新的受管 Git 工作树中运行）、`-C/--cd`、`--ephemeral`、`--ignore-user-config`、`--ignore-rules`、`--skip-git-repo-check`；子命令 `resume`、`fork`、`review` — 本机命令行帮助
- `codex app-server`：传输支持 `stdio://`（默认）、`unix://`、`ws://IP:PORT`；非回环监听可配 `--ws-auth capability-token|signed-bearer-token`；子命令 `daemon`、`proxy`、`generate-ts`、`generate-json-schema`（可生成协议的 TypeScript 绑定与 JSON Schema） — 本机命令行帮助
- app-server 原语：线程（thread）、轮次（turn）、条目（item）；方法 `initialize`、`thread/start`、`thread/resume`、`thread/fork`、`turn/start`、`turn/steer`、`turn/interrupt`；通知 `thread/started`、`turn/started`、`turn/completed`、`item/started`、`item/completed`、`item/agentMessage/delta` 等 — [Codex App Server 文档](https://learn.chatgpt.com/docs/app-server)
- 官方建议：“如果是自动化作业或在 CI 中运行 Codex，请使用 Codex SDK” — 同上（Codex SDK 页面本次抓取 404，语言支持未核实）

**钩子**
- Claude Code 钩子事件共 32 种；可注入 `additionalContext` 的包括 SessionStart、UserPromptSubmit、PreToolUse、PostToolUse、Stop、SubagentStart/Stop 等；处理器类型有 `command`、`http`、`mcp_tool`、`prompt`、`agent`；`http` 类型“把事件 JSON 作为 HTTP POST 请求发送到某个 URL”；PermissionRequest 钩子可通过 `decision.behavior` 返回 allow/deny；所有事件都带 `session_id`、`transcript_path` — [Claude Code Hooks](https://code.claude.com/docs/en/hooks)
- Codex 钩子事件：SessionStart、SessionEnd、SubagentStart、UserPromptSubmit、PreToolUse、PermissionRequest、PostToolUse、PreCompact、PostCompact、SubagentStop、Stop、Interrupt；SessionStart、UserPromptSubmit、PreToolUse、PostToolUse、SubagentStart 可通过 `hookSpecificOutput.additionalContext` 注入上下文（默认上限约 2500 个令牌）；配置在 `~/.codex/` 或 `<repo>/.codex/` 的 `hooks.json` 或 `config.toml` 的 `[hooks]`；“非受管钩子运行前，Codex 要求你审阅并信任该钩子的确切定义”，信任绑定在钩子哈希上，修改后需重新信任；受管（MDM、requirements.toml 等）钩子由策略信任 — [Codex Hooks 文档](https://learn.chatgpt.com/docs/hooks)
- 本机 `codex features list` 显示 `hooks` 为 stable 且默认开启 — 本机命令行
- 本机 Codex 有 `--dangerously-bypass-hook-trust` 参数（“仅用于已审核钩子来源的自动化”） — 本机命令行帮助

### Inferences
- 方案文档里“不支持钩子的工具由指令文件要求先调 `cohive_inbox`”的前提已变化：**Codex 现在也有 SessionStart / UserPromptSubmit 钩子并能注入上下文**，两家都可用钩子做会话内待办提示。但 Codex 项目级钩子需要用户逐个信任（哈希绑定），`cohive init` 写入后要提示用户在 `/hooks` 中确认，或走受管配置。
- Claude Code 的 `http` 类型钩子可以直接 POST 到本机小助手的本地端口，省去写 shell 脚本；采集“会话开始/结束、工具调用、权限请求”事件做看板动态很合适。
- 第三阶段自动执行若直接调命令行，Claude Code 建议用 `--bare` + API 密钥 + `--mcp-config` 显式注入 Cohive MCP + `--permission-prompts none` + `--max-budget-usd`；Codex 用 `codex exec --json --sandbox workspace-write --worktree --ignore-user-config`。两者都能结构化输出（`--json-schema` / `--output-schema`），可要求智能体按固定格式回报修复结果。
- Go 后端没有官方 Agent SDK 可用，但这不是阻碍：要么走 ACP（coder/acp-go-sdk），要么直接解析 stream-json / JSONL；Codex app-server 可用 `generate-json-schema` 生成 Go 类型。

- Codex SDK 的语言支持与实现方式（包装 `codex exec` 还是 app-server）本次未能核实（文档页面 404）。
- `codex exec --json` 事件类型清单未逐条核实。
- 未核实 Codex 旧的 `notify` 配置项在 0.154.0 是否仍存在。

## 问题三：往运行中的会话推送消息

### Takeaway
三条路：（1）Claude Code 的「频道」（channels）可以把 MCP 服务器的事件推进正在运行的会话，但仍是研究预览、只认官方或组织白名单插件、团队版需管理员开启；（2）Claude Code 的远程控制只支持 claude.ai 订阅、不支持 API 密钥，且只能从 claude.ai / 手机应用操作，不是给第三方程序用的接口；（3）Codex 新增了 `codex queue`（给已有会话排队一条消息）和 app-server 的 `turn/steer`，但依赖实验性的 app-server 守护进程。对 Cohive 而言，最可靠的仍是“钩子在下一次提示词时注入待办 + 系统通知”，推送进会话只作可选增强。

### Cited Findings
- 频道：“频道处于研究预览。需要通过 claude.ai 或 Console API 密钥进行 Anthropic 鉴权，不支持 Amazon Bedrock、Google Cloud、Microsoft Foundry。Team 与 Enterprise 组织必须显式开启” — [Channels 文档](https://code.claude.com/docs/en/channels)
- 频道是“把事件推送进正在运行的 Claude Code 会话的 MCP 服务器”，可双向；“事件只会在会话打开时到达” — 同上
- 研究预览期间，`--channels` 只接受 Anthropic 维护的白名单插件或组织管理员设置的 `allowedChannelPlugins`；自建频道测试需用 `--dangerously-load-development-channels`；`--channels` 不出现在 `claude --help` 中，参数语法与协议约定可能变化 — 同上
- 频道支持“权限转发”能力：会话遇到权限询问时可把询问转发到频道远程批准；“任何能通过频道回复的人都能批准或拒绝你会话中的工具调用” — 同上
- 团队版组织默认屏蔽频道，需 Owner 在组织设置中开启；Console API 密钥鉴权默认允许；个人 Pro / Max 用户无需组织检查 — 同上
- 远程控制：“适用于 Pro、Max、Team、Enterprise 方案。**不支持 API 密钥**。Team 与 Enterprise 需 Owner 先开启”；本机会话只发起出站 HTTPS 请求、不开入站端口；从 claude.ai/code 或 Claude 手机应用操作 — [Remote Control 文档](https://code.claude.com/docs/en/remote-control)
- 远程控制服务器模式有 `--spawn worktree`（每个按需会话一个独立工作树） — 同上
- `claude -p --input-format stream-json` 支持“实时流式输入”，即一个持续运行的 `-p` 进程可以从标准输入陆续接收多条用户消息 — 本机命令行帮助
- Codex：`codex queue --thread <会话ID或名称> --message <文本>`（“给已有会话排队一条消息”），可配 `--remote ws://...` 连远程 app-server — 本机命令行帮助
- Codex app-server 的 `turn/steer`：“向活动轮次追加输入；需要 `expectedTurnId`”，不会触发新的 `turn/started` 通知 — [Codex App Server 文档](https://learn.chatgpt.com/docs/app-server)
- Codex `agents` 子命令：“浏览共享本地 app-server 守护进程上的所有智能体会话”；`remote-control` 子命令：“管理开启远程控制的 app-server 守护进程”（实验性） — 本机命令行帮助

### Inferences
- 方案文档第 7.2 节对频道的判断（研究预览、可选增强）仍成立，并可补充两条新限制：插件须在白名单内（Cohive 自建频道插件要么走组织白名单，要么只能用 dangerously 开发参数）；公司若是 Team/Enterprise 方案，需 Owner 开启。
- 若 Cohive 自己用 `claude -p --input-format stream-json` 拉起的会话（第三阶段自动执行），则可以随时往里写消息，这比频道可靠得多——前提是会话由 Cohive 托管，而不是开发者手里正在用的交互会话。
- Codex 的 `codex queue` 依赖共享 app-server 守护进程；只有开发者的 Codex 会话本身跑在该守护进程上时才有效，覆盖面有限，适合作为“可选增强”。

### Gaps
- 频道的实际可靠性（消息丢失、会话空闲时的行为）没有找到可信的第三方测评，未核实。
- `codex queue` 的官方文档未找到，行为（是否要求会话由守护进程托管）仅依据本机帮助推断。

## 问题四：执行隔离与沙箱方案（本机 / 服务器端、许可证、自托管）

### Takeaway
本机侧：Claude Code 与 Codex 自带操作系统级沙箱（macOS Seatbelt、Linux bubblewrap），再配合两家都支持的 `--worktree`，足以支撑第三阶段本机自动修复；更强隔离可用 Docker Sandboxes（微虚拟机，命令行免费含商用，但非开源）。服务器侧：E2B（Apache-2.0、Firecracker 微虚拟机、可 Terraform 自托管，需 Linux + KVM）与 kubernetes-sigs/agent-sandbox（Apache-2.0）最适合；Daytona 开源仓库已于 2026 年 6 月停止维护且为 AGPL-3.0，不建议依赖；Dagger container-use 为 Apache-2.0 但仍标“实验性”、发布停在 2025-08。

## 问题五：通用开源编程智能体平台能否直接当“执行节点”

### Takeaway
OpenHands 已转型为「Agent Canvas」——自托管的编程智能体控制中心，可在本机、Docker、虚拟机或公司基础设施上运行 OpenHands、Claude Code、Codex、Gemini、OpenCode 及任意 ACP 智能体，并支持按 Webhook / 定时触发自动化，MIT 许可（企业目录除外）。它在功能上与 Cohive 第三阶段高度重叠，是最值得评估的“现成执行节点”，但目前标为 beta，技术栈为 Node + Python，不是 Go。SWE-agent / mini-swe-agent 是自带智能体的研究型修复器，Goose / OpenCode 是智能体本身，都不是“驱动别人家智能体”的执行平台。CI 自托管运行器（GitHub Actions、GitLab Runner）有官方集成，可作为最省事的服务器端执行方式。

### Cited Findings
- OpenHands/OpenHands：MIT，约 9.09 万星，活跃；README 标题为“Agent Canvas”，“面向编程智能体与自动化的自托管开发者控制中心”，“在本地、远程与云后端上运行 OpenHands、Claude Code、Codex、Gemini、Pi、OpenCode 或任何 ACP 兼容智能体”；“默认在你本机运行，但可以连接多个智能体后端，例如在 Docker 容器、虚拟机或公司基础设施中运行智能体”；可创建与 Slack、GitHub、Linear 集成、按计划或 Webhook 事件触发的自动化；状态徽章为 beta；安装 `npm install -g @openhands/agent-canvas`，需 Node.js 24+ 与 uv — [OpenHands README](https://github.com/OpenHands/OpenHands)
- README 还提示“无沙箱”模式下“智能体将拥有对你文件系统的完全访问权限” — 同上
- OpenHands 组织中另有 software-agent-sdk（MIT，约 1254 星）、automation（MIT）、OpenHands-CLI（MIT）、enterprise（许可证 NOASSERTION）、OpenHands-Cloud（NOASSERTION） — 本机 `gh api orgs/OpenHands/repos`（2026-10-14）
- SWE-agent/SWE-agent：MIT，约 2.06 万星，“接收 GitHub issue 并尝试用你选择的模型自动修复”；SWE-agent/mini-swe-agent：MIT，约 8513 星，“100 行的 AI 智能体……在 SWE-bench verified 上得分超过 74%” — 本机 `gh api`
- Goose 仓库现为 aaif-goose/goose（原 block/goose 重定向），Apache-2.0，约 5.53 万星；OpenCode 现为 anomalyco/opencode（原 sst/opencode 重定向），MIT，约 21.3 万星；两者都在 ACP 注册表中 — 本机 `gh api`
- Gemini CLI：Apache-2.0，约 10.7 万星 — 本机 `gh api repos/google-gemini/gemini-cli`
- CI 集成：anthropics/claude-code-action（MIT，约 9507 星）、openai/codex-action（Apache-2.0，约 1266 星）；Claude Code 官方文档有 GitHub Actions 与 GitLab CI/CD 两页集成说明 — 本机 `gh api`；[headless 文档“Next steps”](https://code.claude.com/docs/en/headless)
- Codex 官方：“对 CI/CD 作业等程序化 Codex 命令行工作流，使用 API 密钥鉴权”；“不要在不受信任或公开的环境中暴露 Codex 执行” — [Codex 鉴权文档](https://learn.chatgpt.com/docs/auth)

### Inferences
- **OpenHands Agent Canvas 是 Cohive 必须正视的相邻产品**：它已经覆盖“多后端执行节点 + ACP 接入任意智能体 + Webhook 自动化”。Cohive 的差异化应聚焦在“多人之间的问题单路由、归属、验证闭环”，而执行层可以考虑直接对接 Agent Canvas 的后端（agent server）作为可选执行节点，而不是重写一套。需要进一步评估其 agent server 的 API 是否稳定、能否被 Go 服务调用。
- **GitLab Runner / GitHub Actions 自托管运行器**是最便宜的服务器端执行节点：Cohive 只需触发流水线（传入问题单 ID、仓库、提交号），流水线里跑 `claude --bare -p` 或 `codex exec`，并用 API 密钥计费。公司本就用 GitLab，复用现有 Runner 与隔离（Docker executor），审计也在 CI 里。缺点是交互与审批回路弱、冷启动慢。
- SWE-agent / mini-swe-agent 适合做“无订阅、用任意模型的兜底修复器”或评测基线，不适合作为驱动 Claude Code / Codex 的执行节点。

### Gaps
- Agent Canvas 的 agent server API（协议、鉴权、多租户）未深入核实；enterprise 目录许可（NOASSERTION）具体条款未查。
- 未核实 GitLab CI 中运行 Claude Code 的官方文档细节（是否有官方 GitLab 组件）。

## 问题六：用个人 Claude 订阅以无界面方式执行他人派发的任务是否合规；团队应如何选择额度

### Takeaway
不合规风险很高。Anthropic 明确：OAuth（claude.ai 订阅登录）仅用于“Claude Code 及其他原生 Anthropic 应用的普通使用”；第三方开发者不得在自己的产品中提供 claude.ai 登录，也不得“代表其用户通过 Free/Pro/Max 凭据转发请求”，不得收集或中转 claude.ai 凭据；Pro/Max 的额度“假定为普通的个人使用”；消费者条款还禁止“除通过 API 密钥或经明确许可外，以机器人、脚本等自动化方式访问服务”。因此 Cohive 的自动执行应使用团队 API 密钥（Console）或云厂商凭据；OpenAI 同样建议自动化使用 API 密钥。

### Cited Findings
- “OAuth 鉴权仅面向 Claude Free、Pro、Max、Team、Enterprise 订阅方案的购买者，用于支持 Claude Code 及其他原生 Anthropic 应用的普通使用” — [Claude Code Legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)
- “构建与 Claude 能力交互的产品或服务的开发者，包括使用 Agent SDK 的，应通过 Claude Console 或受支持的云提供商使用 API 密钥鉴权。Anthropic 不允许第三方开发者在自己的应用中提供 Claude.ai 登录，或代表其用户通过 Free、Pro、Max 方案凭据转发请求。此外，开发者不得收集、存储或中转 Claude.ai 凭据或会话令牌” — 同上
- 同页也写明：这不妨碍“最终用户用自己的 Claude 订阅登录未经修改的 Claude Code 二进制，包括平台托管 Claude Code 的情形”；客户自行在开发环境、密钥管理器中配置自己的 API 密钥供其授权用户使用也允许，前提是费用记在密钥所有者名下且不转售 — 同上
- “Pro 与 Max 方案公布的用量额度假定为对 Claude Code 与 Agent SDK 的普通、个人使用”；“Anthropic 保留在不事先通知的情况下采取措施执行这些限制的权利” — 同上
- 在产品中预装或运行 Claude Code 需同意商业条款，且“不得修改 Claude Code 二进制”“不得代最终用户付费、转售或中转 Claude 用量，每个最终用户须用自己的 API 密钥、订阅凭据或云厂商凭据鉴权” — 同上
- Agent SDK 文档：“除非事先获批，Anthropic 不允许第三方开发者为其产品（包括基于 Claude Agent SDK 构建的智能体）提供 claude.ai 登录或订阅额度，请改用 API 密钥鉴权” — [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)
- 消费者条款（生效日期 2025-10-08）第 3 节：除通过 Anthropic API 密钥或经明确许可外，不得“通过机器人、脚本等自动化或非人工方式访问服务”；第 2 节：不得与他人共享账号登录信息或使账号供他人使用 — [Anthropic Consumer Terms](https://www.anthropic.com/legal/consumer-terms)
- Claude Code 的条款适用：Team、Enterprise 与 API 用户适用商业条款；Free、Pro、Max 用户适用消费者条款 — [Legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)
- `claude --bare` 模式不读取 OAuth，只认 `ANTHROPIC_API_KEY` 或 `apiKeyHelper` — [headless 文档](https://code.claude.com/docs/en/headless)；本机帮助另有 `claude setup-token`（“设置长期鉴权令牌，需要 Claude 订阅”） — 本机命令行帮助

### Inferences
- **第一阶段（人确认后在自己工具里处理）**：开发者在自己的交互会话里用自己的订阅登录、自己发起处理，属于“普通个人使用”，合规；Cohive 通过 MCP / 钩子提供上下文，不碰凭据，没有问题。
- **第三阶段（自动执行他人派发的任务）**：由 Cohive 小助手在无人值守时用开发者个人 claude.ai 订阅跑 `claude -p` 处理别人派来的问题单——这属于“脚本化自动访问”且可能构成“为他人使用账号”，同时 Cohive 作为第三方产品也不得以订阅额度驱动 Agent SDK。结论：**自动执行必须使用 API 密钥（公司 Console 组织下按项目/成员分配密钥，或 Bedrock / Vertex 凭据）**，并用 `--bare` 保证不会意外读到 OAuth。
- 团队建议：公司版用 Anthropic Console 组织 + 每个执行节点或每个工作空间一把可吊销的 API 密钥（配合方案文档第 8 节“凭证短期有效、可随时吊销”），开发者日常交互可继续用 Team 方案席位。Codex 同理用 OpenAI API 密钥；若公司用 ChatGPT Enterprise，可评估“工作区访问令牌”用于受信任的本机非交互流程。
- 开源发行时，Cohive 不应内置任何 claude.ai 登录流程，也不应打包 Claude Code 二进制；文档里要求用户自备 API 密钥。

### Gaps
- “用自己的订阅在自己电脑上自动处理同事派发的任务”这一精确场景，官方没有逐字表述；上面的结论是基于条款的推断，若需确定应咨询 Anthropic 销售/法务。
- OpenAI 关于 ChatGPT 方案凭据用于无人值守自动化的明确禁止条款，本次未找到原文（只找到“推荐 API 密钥”的表述）。

## 问题七：推荐——自己写执行器还是基于现成项目；第一、三阶段分别用什么

### Takeaway
不要自写“智能体驱动层”，也不要一开始自建沙箱平台。建议：执行器由 Cohive 用 Go 自写一层很薄的“任务编排器”（拉工作树、起进程、收事件、回写问题单），向下统一通过 ACP（coder/acp-go-sdk + claude-agent-acp / codex-acp）驱动智能体，保留 `claude -p stream-json` / `codex exec --json` 作为降级路径；隔离先用“工作树 + 工具自带沙箱”，服务器端优先复用 GitLab Runner，后续可选 E2B 自托管或 OpenHands Agent Canvas 作为执行后端。

### Cited Findings
- ACP 有 Apache-2.0 的 Go 软件开发包（coder/acp-go-sdk v0.13.5）和覆盖 40 余个智能体的注册表 — 见问题一，[ACP 注册表](https://github.com/agentclientprotocol/registry)
- 两家命令行都原生支持 `--worktree`，且有沙箱参数 — 本机命令行帮助（见问题二、四）
- ACP 远程传输仍为草案 — [RFD 草案](https://agentclientprotocol.com/rfds/streamable-http-websocket-transport.md)
- Codex app-server “实验性、不支持生产工作负载” — [Codex App Server 文档](https://learn.chatgpt.com/docs/app-server)
- OpenHands Agent Canvas 已支持多后端执行与 ACP 智能体，状态 beta — [OpenHands README](https://github.com/OpenHands/OpenHands)
- 自动化场景官方均要求 API 密钥 — [Claude Code Legal](https://code.claude.com/docs/en/legal-and-compliance)；[Codex 鉴权](https://learn.chatgpt.com/docs/auth)

### Inferences
**第一阶段（人确认后在自己工具里处理）**
- 接入层：只用 MCP（远程 MCP 服务）+ 指令文件 + 钩子。Claude Code 用 SessionStart / UserPromptSubmit 钩子（可用 `http` 类型直接回调本机小助手）注入待办；**Codex 也改用 SessionStart / UserPromptSubmit 钩子**（新事实，方案文档需更新），指令文件兜底。
- 不引入 ACP、不跑任何无界面执行；本机小助手只做长连接、系统通知、钩子回调端点。
- 不涉及额度问题（开发者自己的交互会话）。

**第三阶段（自动执行）**
- 本机执行器（Go，自写，约千行量级）：认领→`git worktree add`→通过 ACP 拉起 claude-agent-acp / codex-acp（或降级为 `claude --bare -p --output-format stream-json --permission-prompts none --max-budget-usd` / `codex exec --json --sandbox workspace-write`）→事件流写回问题单→权限请求转人工审批（ACP `session/request_permission` 或 Codex `requestApproval`）→产出分支与合并请求。凭据一律 API 密钥。
- 隔离：默认“工作树 + 工具自带沙箱”；可选 Docker Sandboxes（免费商用，非开源，仅作为用户可选）。
- 服务器端执行节点：第一选择是复用公司 GitLab Runner（Docker executor）跑无界面命令；规模化或多租户开源用户再接 E2B 自托管（Apache-2.0）或 Kubernetes agent-sandbox；同时评估把 OpenHands Agent Canvas 作为可插拔执行后端。
- 依赖许可判断（是否适合被可能开源的 Cohive 依赖）：
  - 可直接依赖：ACP 规范与各 SDK（Apache-2.0）、coder/acp-go-sdk（Apache-2.0）、claude-agent-acp（Apache-2.0）、codex-acp（Apache-2.0）、openai/codex（Apache-2.0）、sandbox-runtime（Apache-2.0）、E2B（Apache-2.0）、agent-sandbox（Apache-2.0）、OpenHands 主仓（MIT）、container-use（Apache-2.0）。
  - 只能作为用户自行安装的外部工具、不可打包分发：Claude Code 本体与 Claude Agent SDK（TypeScript 版为专有许可、受商业条款约束）；Docker Sandboxes（免费商用但非开源）。
  - 不建议依赖：Daytona（AGPL-3.0 且停更）、coder/coder（AGPL-3.0，如需仅作外部服务调用）、coder/agentapi（已弃用）。
- 需要更新方案文档的点：7 节“自动执行”行补充 ACP 方案与 `--bare`/API 密钥要求；7.2 节频道限制补充白名单与组织开关；4.2 节 Codex 已支持钩子；11 节第 4 项可直接定为“自动执行用团队 API 密钥”。

### Gaps
- 未实际跑通 coder/acp-go-sdk + claude-agent-acp / codex-acp 的端到端示例，稳定性与事件完整性待原型验证。
- OpenHands Agent Canvas 作为执行后端的接口与运维成本未验证。
