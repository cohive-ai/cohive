# 记忆与共享知识层：开源方案调研

> 调研日期：2026-10-14。仓库星标数、许可证、最近推送时间均为当日用 `gh api repos/OWNER/REPO` 查询所得。未能核实的内容一律放在「Gaps」里。
> 背景：Cohive 方案见 `docs/plan-v0.1.md`。第 6 节把「共享约定库」列为第三阶段能力，第 4.1 节的 `cohive_who_owns` 依赖「接口归属表」，第 7 节规定后端为 Go + Postgres、可自托管，接入方式只依赖 MCP、项目指令文件、命令行三者。

## 一、主流开源记忆方案的现状（架构、许可证、自托管、MCP、多用户）

### Takeaway
2026 年的主流记忆系统几乎全是 Python 技术栈，写入时依赖大模型做抽取，许可证多为 Apache-2.0，可以商用。但能当「团队事实来源」的一个都没有：mem0 开源版已移除图谱，并改为只追加；Graphiti 必须配图数据库；Cognee 的「全部跑在 Postgres 上」只是演示功能；Letta 已转型为智能体运行框架；Basic Memory 是 AGPL，团队版要付费上云。

### Cited Findings

### Inferences
- 这些系统都没有 Go 实现。接入 Cohive 只能作为一个独立的 Python 服务，部署件随之增加，违背第 7 节「一个可执行文件或一个 Docker 镜像」的目标。
- mem0 开源版 v3 改为「只追加、不更新」，把冲突留到检索时按排序解决。这适合个人偏好类记忆，不适合「接口负责人是谁」这种必须唯一、可纠正的事实。
- 几家厂商的商业模式都是「开源核心 + 云版高级功能」（mem0 的图谱、Cognee 的 Postgres 图存储、Basic Memory 的团队版、graphify 的跨仓库）。团队协作真正需要的那部分功能，恰好都在付费墙后面。

## 二、为什么图谱记忆在个人使用中可能被放弃，团队场景是否不同

### Takeaway
图谱记忆的代价有四项：写入时要调用大模型、要多部署一个图数据库、抽取结果不透明、不能像代码一样审查。对「一人一智能体」而言收益不抵成本，Zep 自己也承认这一点。到了团队场景，Zep 列出的痛点（并发写、来源追溯、事实随时间变化、权限隔离）确实会变得突出，但这些痛点用「git + 合并请求 + 结构化字段」大多能解决，而且可审计性更好。

### Cited Findings
- Zep 官方博客（2026-06-23，作者 Jack Ryan）原文：「Markdown memory is a legitimate pattern.」文章认为 Markdown 记忆适用于「一个智能体服务一个用户、有本地事实来源、没有合规要求」的情况，并以 Claude Code 为主要例子 — [Zep 博客](https://www.getzep.com/blog/markdown-is-not-agent-memory)
- 同一篇文章列出的失效场景：文件数量变多后难以选择；事实变化时覆盖会丢历史、追加会留下矛盾；git 只能说明谁改了哪一行，说明不了这条事实来自哪里、何时成立；并发写会冲突；文件权限无法隔离不同用户的数据。原文：「A file records what was written, not what it replaced or why.」（注意：这是厂商观点，结论是推销其时序图谱）— [Zep 博客](https://www.getzep.com/blog/markdown-is-not-agent-memory)
- 图谱的写入成本：一条记录要依次经过节点抽取、去重、边抽取、逐边消解、时间戳标注等多次大模型调用 — [codemyspec 博客](https://codemyspec.com/blog/graph-structured-memory)（来自搜索摘要，二手来源）
- Graphiti README 专门有一节讲大模型服务商的 429 限流问题，所以默认并发设得很低 — [README](https://github.com/getzep/graphiti)
- mem0 已把图谱从开源版移除，只在云平台保留 — [迁移文档](https://github.com/mem0ai/mem0/blob/main/docs/migration/oss-v2-to-v3.mdx)
- Claude Code 自动记忆会在每次会话开始时自动加载 `MEMORY.md` 的前 200 行或前 25KB，不需要智能体主动调用任何工具 — [Claude Code 文档](https://code.claude.com/docs/en/memory)
- 各厂商的基准测试互相矛盾：Zep 称在 LongMemEval 的时序子任务上为 63.8% 对 mem0 的 49.0%，而 mem0 对这个数字有异议；Cognee 自己发布的基准测试结论是 Cognee 和 Graphiti 优于 mem0 — [Cognee 基准](https://www.cognee.ai/knowledge-graph-memory-benchmarks)；有一篇对比文章认为「没有哪个系统在八个维度中赢下超过三个」— [Medium 对比](https://medium.com/@wasowski.jarek/i-compared-5-ai-agent-memory-systems-across-6-dimensions-none-wins-6a658335ed0a)（均为搜索摘要，未全文核实）

### Inferences
- 用户个人放弃 graphiti-memory 的可能原因（推断，未经用户确认）：
  1. **召回靠智能体主动调用**：MCP 记忆要智能体自己想起来去 `search`，而原生文件记忆在会话开始时自动注入，命中率高得多。
  2. **写入不透明**：抽取出来的实体和边错了很难发现，也没法像改一行 Markdown 那样纠正。
  3. **运维和成本**：多一个 Neo4j，每次写入都要调用大模型；断网或限流时记忆功能直接失效。
  4. **没有版本管理**：不能跟随代码分支和提交，也没法在合并请求里审查。
- 团队场景确实有所不同，但不同点并不指向「图谱」：
  - 并发和来源问题，可以用「智能体提议 → 合并请求 → 人审批合入」解决。这比图谱的自动消解更可审计，正好符合 Cohive 第 2 节「先让智能体可靠地传话」和第 8 节的安全红线。
  - 事实随时间变化的问题，可以在 Markdown 头部信息里加 `status: active|superseded`、`superseded_by`、`valid_from` 字段解决，不需要双时序图。
  - 权限隔离需求出现在「工作空间」这一级，这由 Cohive 服务端的 Postgres 负责，不需要记忆系统承担。
- 团队场景还有一个新风险：一个智能体写入的「记忆」会被其他人的智能体当作上下文读取。这正是第 8 节第 1 条防范的「借数据下指令」通道。自动抽取、无人审核的记忆系统会放大这个风险，经过人审合入的 git 文件能降低它。

### Gaps
- 没有找到具体讨论「个人弃用图谱记忆」的 Hacker News 帖子，本节的相关判断属于推断。
- 没有独立第三方、可复现的编程智能体记忆基准，现有数字都是厂商自测。

## 三、编程智能体原生记忆：Claude Code 与 Codex，能否团队共享

### Takeaway
两家都把「需要团队遵守的规则」放在纳入版本管理的指令文件里（`CLAUDE.md` / `AGENTS.md`），把「自动生成的记忆」放在本机、不共享。Codex 官方文档明确要求团队必须遵守的规则写进 `AGENTS.md` 或检入仓库的文档，不能依赖自动记忆。所以 Cohive 应该借指令文件这一层分发团队知识，而不是去同步各家的自动记忆目录。

### Cited Findings

**Claude Code**（[文档：How Claude remembers your project](https://code.claude.com/docs/en/memory)，2026-10-14 抓取）
- 指令文件分层：组织托管策略（macOS 为 `/Library/Application Support/ClaudeCode/CLAUDE.md`，不能被排除）、项目级 `./CLAUDE.md` 或 `./.claude/CLAUDE.md`（「通过版本管理与团队共享」）、`CLAUDE.local.md`（个人，加入 gitignore）、用户级 `~/.claude/CLAUDE.md`、`.claude/rules/`（可以按路径生效）。
- 支持 `@path` 导入，最多递归四层。导入工作目录之外的文件时，首次会弹窗请求批准。
- 建议每个 `CLAUDE.md` 控制在 200 行以内。
- `AGENTS.md`：从 v2.1.277 起可以直接读取，但**默认只在没有 `CLAUDE.md` 时才读**。可以设置为 `claude-md-and-agents-md` 同时读取，也可以在 `CLAUDE.md` 里用 `@AGENTS.md` 导入。
- 自动记忆：分为 `user` / `feedback` / `project` / `reference` 四类，存放在 `~/.claude/projects/<project>/memory/`，「Auto memory is machine-local … Files are not shared across machines or cloud environments.」`MEMORY.md` 每次加载前 200 行或 25KB，主题文件按需读取。
- 存放位置可以用 `autoMemoryDirectory` 改到别处，用户级、项目级、托管策略级设置都能配；在项目设置里配置时要受「工作空间信任」规则约束。
- 自动记忆会跳过能从代码推导出的内容（架构、文件路径、调试修复）。

**Codex**（[官方文档：Memories](https://learn.chatgpt.com/docs/customization/memories?surface=app)，由 developers.openai.com/codex/memories 308 跳转而来，页面未标注日期）
- 记忆存放在 `~/.codex/memories/`，属于「生成的状态」，不建议手工编辑；**默认关闭**，需要设置 `[features] memories = true`。
- 配置项包括 `memories.generate_memories`、`memories.use_memories`、`memories.disable_on_external_context`（用过 MCP 或联网搜索的会话不参与记忆生成）等。
- 文档要求把团队必须遵守的规则写进「AGENTS.md or checked-in documentation」，记忆只是「a helpful recall layer」。没有提到跨机器或团队同步。
- `AGENTS.md` 的查找规则：从 git 根目录走到当前目录，每级目录最多一个文件，合计上限 `project_doc_max_bytes` 默认 32 KiB — [第三方汇总](https://codex.danielvaughan.com/2026/04/19/openai-codex-cli-official-documentation-guide/)（二手来源，未在官方页面核实）

### Inferences
- **把团队知识放进 git，现成的通道是指令文件和导入机制**：`cohive init` 写入的协作说明可以只放一段很短的指引（例如「约定与决策见 `@.cohive/knowledge/INDEX.md`，查询负责人请调用 `cohive_who_owns`」），正文由 Cohive 统一维护。
- **兼容性细节**：仓库里如果同时有 `CLAUDE.md` 和 `AGENTS.md`，Claude Code 默认不读 `AGENTS.md`。所以 `cohive init` 要么写两份，要么在 `CLAUDE.md` 里写 `@AGENTS.md` 导入。后者更稳，也只需维护一份。
- **不建议同步各家自动记忆目录**：两家都把它定义为本机生成的状态，格式未承诺稳定（Codex 明确说不要手工编辑）。这违背第 2 节第 1 条「不深度适配任何一个工具的内部机制」。`autoMemoryDirectory` 理论上可以指向 git 仓库，但多人的智能体自动写同一目录，会带来噪声、冲突和注入风险。
- 指令文件有大小上限（Claude Code 建议 200 行以内，Codex 默认 32 KiB），因此团队知识不能全部塞进指令文件，必须「指令文件放索引 + MCP 或文件按需查询」。

### Gaps
- Codex 在 `AGENTS.md` 中是否支持类似 `@path` 的导入：未核实。
- Codex 云端会话的记忆存储方式：官方页面没有说明。

## 四、代码知识图谱与代码索引：谁适合当「跨仓库接口归属与依赖」的事实来源

### Takeaway
代码图谱擅长回答「这段代码被谁调用」，不擅长回答「这个接口归谁负责」。负责人是组织层面的事实，代码里推导不出来。GitNexus 的「仓库组 + 契约登记」功能最贴合需求，但它是 PolyForm 非商业许可；graphify 是 Apache-2.0，但跨仓库能力放在付费云版里；Serena 的应用部分已改为 GPL-3.0；Sourcegraph 主仓库已归档。代码图谱只适合当辅助证据，不适合当权威来源。

### Cited Findings
- **graphify**：仓库已迁到 Graphify-Labs/graphify，约 126,338 星，Apache-2.0，v0.9.90（2026-10-13）。用 tree-sitter 做抽象语法树解析，「deterministic, no LLM」；输出放在 `graphify-out/graph.json`；有 MCP 的 stdio 服务（`graphifyy[mcp]`）、git 钩子（`graphify hook install`）、`merge-graphs` 合并多个图；README 建议把图提交进仓库供团队共享 — [README](https://github.com/Graphify-Labs/graphify)
- graphify 的「monorepo and cross-repo support … plus connectors for Sentry, Jira」属于 **Graphify Cloud** 付费功能（14 天试用）— [README](https://github.com/Graphify-Labs/graphify)
- **GitNexus**：约 47,879 星，许可证为 **PolyForm Noncommercial 1.0.0**（LICENSE 文件已核实），2026-10-14 有推送。提供 19 个 MCP 工具，其中包括 `route_map`（哪些组件请求哪些接口）、`api_impact`、`group_sync`（重建仓库组的契约登记和跨仓库链接），以及资源 `gitnexus://group/{name}/contracts` — [README](https://github.com/abhigyanpatwari/GitNexus)、[LICENSE](https://github.com/abhigyanpatwari/GitNexus/blob/main/LICENSE)
- **Serena**：约 30,256 星。LICENSE 写明按组件分别授权：SolidLSP 部分为 MIT，「the Serena application under GPL-3.0-or-later」。基于语言服务协议，支持 40 多种语言；JetBrains 插件需付费 — [LICENSE](https://github.com/oraios/serena/blob/main/LICENSE)、[README](https://github.com/oraios/serena)
- **Sourcegraph**：`sourcegraph-public-snapshot` 仓库已归档，最后推送 2024-09-02 — [GitHub](https://github.com/sourcegraph/sourcegraph-public-snapshot)；其底层的三元组代码搜索引擎 **Zoekt** 仍在维护，Apache-2.0，Go 实现，约 1,960 星 — [GitHub](https://github.com/sourcegraph/zoekt)
- MCP 官方 servers 仓库正从 MIT 迁移到 Apache-2.0，新贡献按 Apache-2.0 授权 — [LICENSE](https://github.com/modelcontextprotocol/servers/blob/main/LICENSE)

### Inferences
- **许可证判断**（不构成法律意见）：
  - graphify（Apache-2.0）：可以在公司内部商用，也可以作为开源 Cohive 的依赖。
  - GitNexus（PolyForm 非商业）：公司内部商用不被允许，也不能作为开源 Cohive 的依赖或随附组件，这与 `plan-v0.1.md` 第 7.2 节的判断一致。

## 五、接口契约与服务目录：OpenAPI / Protobuf / AsyncAPI / Backstage

### Takeaway
接口契约应以各仓库里的 OpenAPI、Protobuf、AsyncAPI 文件为准，并用 Go 写的 `oasdiff` 和 `buf breaking` 检测破坏性变更，这正好支撑第二阶段的「接口变更广播」。Backstage 的 `catalog-info.yaml` 描述格式已经覆盖负责人、所属系统、提供或消费的接口、依赖关系，可以直接作为 Cohive 的数据模型标准。但部署整个 Backstage（TypeScript 门户）对 Cohive 太重。建议「兼容其文件格式，有现成 Backstage 时对接，没有时 Cohive 自己读文件」。

### Cited Findings
- Backstage：约 34,611 星，Apache-2.0，2026-10-14 有推送，TypeScript — [GitHub](https://github.com/backstage/backstage)
- 描述格式：实体类型包括 Component、API、Resource、System、Domain、Group、User、Location、Template。Component 和 API 都必须填 `spec.owner`；Component 可以声明 `providesApis`、`consumesApis`、`dependsOn`、`dependencyOf`；API 的 `spec.type` 取值为 `openapi`、`asyncapi`、`graphql`、`grpc`，`spec.definition` 必填，可以用 `$text` 引用文件；推荐文件名为 `catalog-info.yaml`；文档原文「there will always be one ultimate owner」— [Descriptor Format 文档](https://backstage.io/docs/features/software-catalog/descriptor-format)
- Backstage 的 MCP 接入：`@backstage/plugin-mcp-actions-backend` 把 Actions Registry 里注册的动作暴露为 MCP 工具，默认端点为 `/api/mcp-actions/v1`；外部访问用静态令牌，被文档标为高度实验性 — [Backstage MCP Actions 文档](https://backstage.io/docs/ai/mcp-actions)（来自搜索摘要，未全文抓取核实）；Red Hat Developer Hub 也基于它做了只读的目录查询 — [Red Hat 文章](https://developers.redhat.com/articles/2025/11/10/mcp-red-hat-developer-hub-chat-your-catalog)（搜索摘要）
- Buf：bufbuild/buf，约 11,487 星，Apache-2.0，Go 实现。`buf breaking --against '.git#branch=main'` 可以直接和 git 分支比对，**不依赖 BSR**；BSR 负责依赖管理、生成 SDK 和集中治理 — [README](https://github.com/bufbuild/buf)
- oasdiff：约 1,412 星，Apache-2.0，Go 实现，「OpenAPI Diff and Breaking Changes」— [GitHub](https://github.com/oasdiff/oasdiff)
- OpenAPI 规范（OAI/OpenAPI-Specification，Apache-2.0）和 AsyncAPI 规范（asyncapi/spec，Apache-2.0）；AsyncAPI CLI 为 Apache-2.0，TypeScript — [OpenAPI](https://github.com/OAI/OpenAPI-Specification)、[AsyncAPI spec](https://github.com/asyncapi/spec)、[AsyncAPI CLI](https://github.com/asyncapi/cli)

### Inferences
- **Backstage 能否直接当「服务注册与负责人」层？** 数据模型能，部署形态不合适：
  - 能：负责人、接口、依赖、接口定义文件引用，它全都有，而且是业界事实标准。
  - 不合适：Backstage 是一个需要自己搭建、带插件体系的 Node 门户，会让 Cohive「一个 Go 二进制」的自托管目标失效；它的 MCP 接入也还处于实验阶段。
  - 结论：Cohive 采用 `catalog-info.yaml` 格式作为服务登记文件（子集即可：Component、API、Group、`owner`、`providesApis`、`consumesApis`、`dependsOn`），由 Cohive 从各仓库读取后落入 Postgres；公司如果已有 Backstage，就写一个适配器从其目录接口导入。这样也符合第 2 节第 5 条「适配器接入」的思路。
- `cohive_who_owns` 的查询链路：接口路径或 proto 服务名 → API 实体 → `spec.owner`（Group 或 User）→ Cohive 成员。如果查不到，就退回给发起人确认，与第 5 节第 2 步一致。
- 接口变更广播（第二阶段）：在合并请求流水线里，对契约文件运行 `oasdiff breaking` 或 `buf breaking`，再按 `consumesApis` 反查下游并通知。两者都是 Go 实现，可以作为库或命令行集成进来。

### Gaps
- BSR 是否提供可自托管的开源版本、价格如何：本次未核实（只确认 buf 命令行是 Apache-2.0，且 `buf breaking` 不依赖 BSR）。
- 是否有 Go 实现的 Backstage 描述文件解析库：没有查到可靠来源，可能需要 Cohive 自己用 YAML 结构体解析（工作量很小）。
- Backstage MCP Actions 插件的版本号和稳定性等级：没有抓取官方页面全文核实。

## 六、结论：现成记忆系统、git 里的 Markdown、服务目录，还是组合

### Takeaway
推荐**组合方案，以 git 文件为权威来源，以 Cohive 的 Postgres 为索引和运行状态，暂不引入任何记忆系统**：
- 服务登记采用 Backstage 的 `catalog-info.yaml` 格式；
- 接口契约用 OpenAPI、proto、AsyncAPI 文件，配合 `oasdiff` 和 `buf breaking`；
- 团队约定与决策用 git 仓库里的 Markdown 决策记录，带结构化头部信息，经合并请求审批后合入；
- 历史问题与修复经验，就是 Cohive 问题单本身加上人审后提炼出的经验条目；
- 代码图谱（graphify）作为可选证据；
- 分发通道是 `AGENTS.md` / `CLAUDE.md` 里的一段索引指引，再加上 Cohive MCP 的查询工具。

### Cited Findings
- 两家工具都把团队规则放在纳入版本管理的指令文件里，自动记忆仅限本机 — [Claude Code 文档](https://code.claude.com/docs/en/memory)、[Codex 文档](https://learn.chatgpt.com/docs/customization/memories?surface=app)
- 主流记忆系统的团队功能和 Postgres 支持，要么在付费版，要么是演示功能（mem0 图谱、Cognee 的 Postgres 图存储、Basic Memory 团队版）— [mem0 迁移文档](https://github.com/mem0ai/mem0/blob/main/docs/migration/oss-v2-to-v3.mdx)、[Cognee README](https://github.com/topoteretes/cognee)、[Basic Memory README](https://github.com/basicmachines-co/basic-memory)
- Backstage 描述格式覆盖负责人、接口和依赖 — [Backstage 文档](https://backstage.io/docs/features/software-catalog/descriptor-format)
- 契约检查工具 buf 和 oasdiff 都是 Go 实现、Apache-2.0 — [buf](https://github.com/bufbuild/buf)、[oasdiff](https://github.com/oasdiff/oasdiff)

### Inferences
**各类知识的权威来源与载体（建议）**

| 知识类别 | 权威来源 | Cohive 的角色 | 可复用的开源组件 |
|---|---|---|---|
| 服务负责人、接口归属、跨仓库依赖 | 各仓库的 `catalog-info.yaml`（Backstage 格式子集） | 拉取 → 校验 → 落入 Postgres；提供 `cohive_who_owns`；已有 Backstage 时走适配器 | Backstage 描述格式；可选 Backstage 目录接口 |
| 接口契约 | 仓库里的 OpenAPI、proto、AsyncAPI 文件 | 变更检测和下游广播（第二阶段） | oasdiff、buf（均为 Go、Apache-2.0） |
| 团队约定与决策 | 一个团队知识仓库（或各仓库 `docs/decisions/`）里的 Markdown 决策记录，头部带 `status`、`superseded_by`、`scope`、`owner` | 建索引（Postgres 全文检索，可选 pgvector）；MCP 只读查询；智能体只能「提议」，经合并请求人审合入 | 无需额外组件；格式可参考常见的架构决策记录写法 |
| 历史问题与修复经验 | Cohive 问题单（Postgres，带提交号和复现脚本） | 闭环后由智能体起草「经验条目」，人审后转为 Markdown | Cohive 自身 |
| 代码结构证据 | 各仓库提交的 `graphify-out/` | 问题单中引用；校验声明的依赖和实际调用是否一致 | graphify（Apache-2.0） |
| 个人偏好与会话经验 | 各工具的原生自动记忆 | **不接管、不同步** | Claude Code 和 Codex 原生功能 |

**理由**
1. **可靠性**：权威事实全部是确定性的文件和数据库记录，写入不依赖大模型，服务断网或被限流也不会丢失事实。
2. **可审计性**：每条约定、每次归属变更都有提交、作者和合并请求审批记录，能精确回答「谁、何时、为什么改的」。这比图谱的自动消解更容易解释，也能回应 Zep 提出的「来源追溯」质疑：用合并请求描述加头部的 `source` 字段，不需要时序图。
3. **多工具兼容**：只用到 MCP、指令文件、命令行这三种通用接入方式，与第 2 节第 1 条一致。Claude Code 和 Codex 都能读文件，都能调 MCP。
4. **技术栈契合**：全部是 Go + Postgres，不引入 Python 服务和图数据库。
5. **安全**：知识进入其他人智能体的上下文之前，必须经过人工审批，从而封堵第 8 节第 1 条所说的「借数据下指令」通道。
6. **许可证干净**：核心链路只用 Apache-2.0 组件。GitNexus（非商业）和 Serena（GPL）只作为开发者本机的可选插件。

**什么时候再考虑引入记忆系统**：如果团队知识增长到「全文检索加 pgvector 找不准」，或者需要从大量问题单里自动归纳模式，可以把 mem0 自托管版（Apache-2.0，Postgres + pgvector）作为可替换的「召回层」。它只读 Cohive 导出的数据，不当权威来源。届时再评估 Python 服务的运维成本。

**提醒用户留意的盲点**
- 真正难的不是存储，而是**过期**。约定和归属表最常见的失效方式是「没人更新」。建议从第一天就做三件事：
  - 每条记录都有 `owner` 和「最后确认时间」；
  - 超期未确认的条目在看板上标黄；
  - 问题单首次路由失败（第 10 节「首次正确路由率」指标）时，反向标记对应的归属条目可疑。
- 第一阶段的路由只需要负责人表，不需要约定库。可以先只落地 `catalog-info.yaml` 子集和 `cohive_who_owns`，约定库按方案留在第三阶段。

### Gaps
- 没有找到「团队用 git 中的 Markdown 做智能体共享知识」的规模化案例数据（多少人、多少条之后开始失效）。上面的阈值判断属于推断。
- 没有实测各记忆系统在中文内容上的抽取质量。
