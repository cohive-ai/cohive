# 编排与持久化执行层选型（Cohive）

> 数据采集日期：2026-10-14。仓库星数、最近推送时间、最新发布版本均由 `gh api repos/...` 当日查询得到；许可证以仓库 LICENSE 文件原文为准。
> 背景：Cohive 草案为 Go + Postgres + river（见 `docs/plan-v0.1.md` 第 7 节），目标是开源后自部署只需"一个可执行文件或一个 Docker 镜像"。

## 问题一：持久化执行 / 工作流引擎（Temporal、Restate、Hatchet、Inngest、DBOS Go、Trigger.dev、Windmill、Conductor）各自适不适合 Cohive

### Takeaway
在"Go 原生、只依赖 Postgres、可嵌进同一个可执行文件、许可证宽松"这四条约束下，只有 **DBOS Go（MIT，库形态，仅依赖 Postgres）** 全部满足；Temporal 的 Go SDK 最成熟但服务端运维最重；Hatchet 许可证友好、只强制依赖 Postgres，但需要额外跑一个引擎服务；Restate（BSL）、Inngest（SSPL）、Windmill（AGPL + 专有）的许可证都不适合被一个准备开源的项目作为必需依赖。

### Inferences
- **许可证对开源依赖的影响**：
  - MIT / Apache-2.0（Temporal、Hatchet、DBOS Go、Conductor、Trigger.dev、go-workflows）：公司内部商用、被开源项目依赖均无障碍。
  - Restate BSL 1.1：公司内部商用可以；Cohive 开源后由用户自部署也基本可以（Cohive 不是"让第三方注册自己服务"的平台），但 BSL 不是开源许可证，会让 Cohive 失去"纯开源依赖"的叙事，部分企业法务会卡 BSL。不建议作为必需依赖。
  - Inngest SSPL：被 OSI 认定为非开源许可证（此为业界共识，本次未单独查证 OSI 页面）；Cohive 若作为托管服务对外提供，SSPL 第 13 条可能要求公开整个服务栈源码。**不适合**。
  - Windmill AGPL + 专有：Cohive 若链接/修改其代码会触发 AGPL；且部分功能专有。**不适合**。
- **"一个可执行文件"约束**：只有库形态（DBOS Go、go-workflows、river）能编进 Cohive 自己的二进制。Temporal、Hatchet、Inngest、Restate 都是独立服务，用户自部署时至少多一个容器；Temporal 还多一个 Elasticsearch（可选但示例默认带）。
- **Go SDK 成熟度排序**（据星数、版本、活跃度推断）：Temporal（服务端本身就是 Go，Cadence 血统）＞ DBOS Go（已到 v1.6，月度发布）≈ Hatchet（服务端 Go，SDK 在主仓库）＞ Inngest Go ＞ Restate Go（69 星，最弱）。
- **长时间等待人工信号**：Temporal（Signal/Update）、DBOS（`Recv` 带超时）、Hatchet（持久事件等待 + 持久睡眠）、Inngest（`waitForEvent`）、Restate（awakeable / 持久 promise）都具备该能力；其中 DBOS 的 48 小时 `Recv` 示例与 Cohive"等待审批几小时到几天"的需求直接对应。Temporal 与 Restate 的具体 API 本次未在官方页面逐一核实，依据为既有知识。
- Conductor 是 Java 服务、依赖较多组件，与"Go + Postgres + 单二进制"方向完全相反，可直接排除。Trigger.dev 只服务 TypeScript 任务代码，排除。

### Gaps
- Temporal 自托管官方页面未列出完整生产组件清单（历史/匹配/前端/工作进程四类服务、Cassandra/MySQL 支持情况）——本次未从官方页面拿到原文。
- Inngest SSPL 转 Apache 2.0 的延迟年限未核实（LICENSE 文件只读到标题部分）。
- Hatchet 仓库是否包含专有的企业目录（`ee/`）未核实；页面提到的"无需 Docker 的嵌入模式"细节未核实。
- Restate 的 awakeable / 持久 promise 未在本次抓取的页面中出现，属既有知识，需复核。
- 未找到任何一家在 Cohive 这种规模（每工作空间每天几十单）下的独立性能基准。

## 问题二：轻量方案（river、Asynq、NATS JetStream、pgmq）加自写状态机是否足够

### Takeaway
足够。Cohive 的"长时间等待"本质上是**问题单实体的状态**（存在业务表里），而不是一个需要挂起几天的进程内工作流；用 river 的"事务内入队 + 定时任务 + 唯一任务 + 自动重试"加一张状态机表，就能覆盖超时升级、至少一次投递、可恢复可重试和拉闸。river 开源版不含"工作流"功能（属付费 Pro），但第一阶段用不到。

### Cited Findings
- river：MPL-2.0，5,776 星，2026-10-14 仍有推送；"基于 Postgres 或 SQLite 的快速事务型任务队列"，自带自动重试、定时调度、唯一任务和网页界面 — [river README](https://github.com/riverqueue/river)
- river 主张任务队列与业务数据共用一个数据库："事务提交则任务一定入队，回滚则任务被移除，提交前对工作进程不可见" — [river README](https://github.com/riverqueue/river)
- river 的"工作流（并行任务、独立重试、崩溃/部署后恢复）、顺序执行、全局并发上限、持久周期任务"**不在开源版**，属 Pro / Enterprise；Pro 价格 125 美元/月；Pro 的许可证条款页面未在抓取内容中给出 — [River Pro](https://riverqueue.com/pro)
- Asynq：MIT，13,759 星，基于 Redis；最新发布 v0.26.0（2026-02-03），最近推送 2026-06-22，活跃度明显下降 — [hibiken/asynq](https://github.com/hibiken/asynq)
- NATS Server：Apache-2.0，20,872 星，活跃 — [nats-io/nats-server](https://github.com/nats-io/nats-server)
- pgmq：PostgreSQL 许可证，5,329 星，"类似 AWS SQS 的 Postgres 消息队列"，以 Postgres 扩展形式提供（仓库主语言 Rust） — [pgmq/pgmq](https://github.com/pgmq/pgmq)
- 现有方案已在 7.2 节排除自建消息中间件（Kafka、NATS），理由是 Postgres 队列足以满足当前规模 — 本地文档 `docs/plan-v0.1.md`

### Inferences
- **需求逐条映射到 river + 状态机**：
  - 状态流转：`issues` 表 + `issue_events` 追加表（谁、哪个工具、何时），状态迁移在同一事务里校验前置状态（乐观锁 / `UPDATE ... WHERE status = $old`）。
  - 超时升级：进入 `ROUTED` / `READY_FOR_VERIFICATION` 时在同一事务里入队一个带 `ScheduledAt = deadline` 的 river 任务；到期执行时先检查状态是否仍未推进，未推进则转 `ESCALATED`。用唯一任务（按问题单 ID + 阶段）防重复。
  - 修复后触发验证：`cohive_request_verification` 的事务里同时写状态和入队"重跑复现脚本"任务——这正是 river 事务入队的强项，天然等价于发件箱模式。
  - 等待人工审批：不需要"挂起的工作流"，状态停在 `READY_FOR_VERIFICATION` 即可，人点按钮就是一次普通的状态迁移；等多久都不占资源。
  - 来回轮次上限：问题单上加 `reopen_count` 字段，`REOPENED` 迁移时 +1，超上限直接 `ESCALATED`。
  - 至少一次投递：river 失败自动重试；推送给本机小助手的 WebSocket 消息另需"未确认消息表 + 重连补发"，这一层与队列选型无关，任何引擎都要自己做。
  - 按工作空间拉闸：工作空间表上加 `halted` 标记，所有任务执行前先检查；river 的队列暂停能力可作为第二道闸（river 队列暂停 API 本次未在官方文档核实）。
- **SQLite 支持**是 river 的额外加分项：开源用户想"一个可执行文件 + 本地 SQLite"试用时也能跑，但 Cohive 业务表本身也要同时兼容 SQLite 才有意义，第一阶段不建议投入。
- **MPL-2.0** 是文件级弱著佐权：内部商用、被 Apache/MIT 项目依赖都没问题，只有修改 river 自身文件才需公开这些文件的改动。
- Asynq 需要 Redis，与"只要 Postgres"冲突，且维护放缓，排除。NATS JetStream 多一个服务，排除。pgmq 需要安装 Postgres 扩展，托管 Postgres（如部分云厂商）未必允许，且只是消息队列不含重试调度语义，不如 river。
- 自写状态机的真正风险不在"能不能做"，而在**多步骤自动执行**（第三阶段：建工作树 → 跑 `claude -p` → 推送 → 建合并请求 → 等流水线 → 请求验证）：这类链路需要步骤级检查点和中途崩溃恢复，用 river 手写就是"一步一个任务、每步把结果写回表"，可行但样板代码多；这正是 DBOS Go 这类嵌入式持久执行库的价值区间。

### Gaps
- River Pro 的许可证条款（是否允许在开源项目中依赖、是否可再分发）未核实。
- river 队列暂停接口与按"工作空间"维度暂停的粒度未核实。

## 问题三：智能体编排框架（LangGraph、Google ADK、OpenAI Agents SDK、Claude Agent SDK、CrewAI、AutoGen / Microsoft Agent Framework、DeepSeek Harness）对 Cohive 是否真有用

### Takeaway
基本没用。这些框架解决的是"在**一个程序里**编排多个模型调用和工具"，而 Cohive 要解决的是"**多个人各自已有的**编程智能体之间的协作"——Cohive 第一阶段根本不调用模型。唯一有潜在价值的是第三阶段的自动执行器：可在"直接调用无界面命令行"之外，把 Claude Agent SDK 作为可选执行器；Google ADK Go 是其中唯一的 Go 原生框架，但同样不必引入。

- **两类问题的区分**：
  - "编排多个模型调用"——LangGraph、ADK、OpenAI Agents SDK、CrewAI、MAF：Cohive 自己是任务路由与状态服务，不是智能体，第一、二阶段不需要任何一个。
  - "协调多个人各自的编程智能体"——这是 Cohive 本身要做的事，现有框架都假设所有智能体由同一个程序托管，无法覆盖"A 的 Claude Code 在 A 的电脑上、B 的 Codex 在 B 的电脑上、人要在中间确认"的场景。
- 这些框架自带的"持久执行 / 人工介入"（如 LangGraph interrupt）是围绕单次智能体运行设计的，粒度远小于 Cohive 跨天、跨人的问题单生命周期；且主流框架都是 Python，与 Go 后端不合。
- **第三阶段自动执行器**：方案已定为调用无界面命令（`claude -p --output-format stream-json`、`codex exec`），这已经是"把编程智能体当黑盒"的正确抽象。Claude Agent SDK 只覆盖 Claude，且没有 Go 版（仅查到 Python 仓库），引入它会让执行器变成多语言；建议仅作为本机小助手内的可选执行器插件，不进服务端。
- DeepSeek Harness 与 Claude Code、Codex 同属"编码智能体运行框架"，与现有方案 7.2 节结论一致：只应作为一种可接入工具（通过 MCP 连 Cohive），不是编排层；且开发者预览、明示会破坏兼容。249k 星数异常高，可能反映热度而非成熟度（推断）。
- Google ADK Go 是唯一 Go 原生、Apache-2.0、发布节奏快的框架，若未来 Cohive 要在服务端做"自动分诊 / 归属推断"之类的模型调用，可以考虑；但同样的事情直接调模型接口也能完成，不建议为此引入框架。

### Gaps
- Claude Agent SDK 是否有官方 Go 版本未核实（仅查询了 Python 仓库）；TypeScript 版仓库元数据未查。
- AutoGen 仓库 GitHub 显示的 CC-BY-4.0 可能只针对文档，代码许可证未逐文件核实。
- DeepSeek Harness 的 249,452 星数据来自 GitHub 搜索接口，未做异常性核查。

## 问题四：A2A（Agent2Agent）在 2026 年的现状，是否适合作为 Cohive 跨智能体消息的标准格式

### Takeaway
A2A 已有稳定规范（1.0 系列）、Linux 基金会治理和 Go SDK，但它假设每个智能体都是一个可被网络访问的服务端；而 Cohive 面对的 Claude Code、Codex 跑在开发者内网电脑上，只能作为 MCP 客户端接入。因此**第一阶段不应把 A2A 当传输协议**，但可以借用它的任务数据模型命名，第三阶段再在协作服务上开一个 A2A 入口，供基于 ADK / MAF 等框架的外部智能体接入。

### Cited Findings
- A2A 主仓库：Apache-2.0，26,142 星，最新发布 v1.0.1（2026-05-28）；README 称其为"Linux 基金会下的开源项目，由 Google 贡献"，通信方式为"基于 HTTP(S) 的 JSON-RPC 2.0" — [a2aproject/A2A](https://github.com/a2aproject/A2A)
- 官方 Go SDK a2a-go：Apache-2.0，482 星，v2.6.0（2026-09-25） — [a2aproject/a2a-go](https://github.com/a2aproject/a2a-go)
- Linux 基金会 2026-04-09 新闻稿：一周年时支持组织超过 150 家，已集成进 Google、微软、AWS 平台，多个行业有生产部署 — [Linux 基金会新闻稿](https://www.linuxfoundation.org/press/a2a-protocol-surpasses-150-organizations-lands-in-major-cloud-platforms-and-sees-enterprise-production-use-in-first-year)
- 1.0 是首个稳定规范，新增多协议支持、多租户、更新的安全流程和早期用户迁移路径，并引入签名智能体名片（Signed Agent Cards） — 据搜索摘要转述 [AIwire 报道](https://www.hpcwire.com/aiwire/2026/04/09/linux-foundation-a2a-protocol-marks-one-year-with-broad-enterprise-and-cloud-adoption/)
- 治理归属存在说法冲突：Enterprise DNA 称 2026-08-20 Google 将 A2A 正式移交 Linux 基金会旗下的 Agentic AI Foundation（AAIF），与 MCP 同处一个治理结构，成员从 2026 年 3 月的 49 家增至 250+ — [Enterprise DNA](https://enterprisedna.co/resources/news/google-a2a-aaif-agent-protocol-open-standard-august-2026/)；另有来源称移交发生在 2025 年 [Eco](https://eco.com/support/en/articles/14845481-a2a-agent-to-agent-protocol-explained) 或 2026 年初 [Paquetlabs](https://paquetlabs.com/blog/what-the-linux-foundation-means-for-google-s-a2a-protocol)。250+ 的数字未找到 Linux 基金会一手来源。
- 谨慎观点：A2A"还活着但范围比宣传窄"；"被支持"不等于深度生产使用；安全（身份、授权、委托、被投毒的产物、审计）是"最大的未解问题"，A2A"本身不是安全架构"；建议先用 MCP，只有存在真实的归属、部署或互操作边界时才加 A2A；分层建议为"智能体之间用 A2A、智能体与工具之间用 MCP" — [Rost Glukhov 2026 分析](https://www.glukhov.org/ai-systems/comparisons/a2a-protocol-2026-adoption/)
- 同文描述的任务流程包括：通过智能体名片发现、发送任务、交换消息、接收状态更新、处理 "input-required"（需要输入）状态、接收产物、跟踪完成/失败/取消 — [Rost Glukhov 2026 分析](https://www.glukhov.org/ai-systems/comparisons/a2a-protocol-2026-adoption/)
- Microsoft Agent Framework 1.0 宣称通过 A2A 和 MCP 实现跨运行时互通 — [AutoGen README](https://github.com/microsoft/autogen)

### Inferences
- **为什么第一阶段不适合当传输层**：A2A 的交互模型是"客户端智能体调用远端智能体的 HTTP 端点"。Claude Code / Codex 不对外提供 A2A 端点，且开发者电脑在内网，服务端无法反向连入（方案 7 节已因此选择本机小助手主动建立 WebSocket）。强行套 A2A 等于给每台开发机再造一个 A2A 服务端，违背"不深度适配工具内部机制"的原则。
- **可以借用的部分**：A2A 的任务状态（已提交 / 处理中 / 需要输入 / 完成 / 失败 / 取消）、消息由多个"部件"组成、产物（Artifact）独立于消息等概念，与 Cohive 问题单状态和证据字段高度相似。问题单的对外 JSON 结构若按 A2A 的 Task / Message / Artifact 命名设计，将来加 A2A 入口时只需做薄转换。
- **第三阶段**：在协作服务上暴露一个 A2A 服务端（用 a2a-go），让外部 A2A 智能体（ADK、MAF 等构建的）可以提交问题单、接收任务；Cohive 的内部模型仍以问题单为准。前提是 1.0 规范在此期间保持兼容。
- 安全风险与 Cohive 第 8 节红线一致："收到的问题单一律当数据不当指令"在 A2A 场景同样必须坚持，A2A 本身不提供这一保护。

### Gaps
- A2A 1.0 规范中完整的任务状态枚举（是否包含 rejected、auth-required 等）本次未从规范原文核实。
- 是否已有 gRPC / REST 绑定（"多协议支持"的具体内容）未从规范原文核实，README 只写了 JSON-RPC 2.0。
- AAIF 移交的确切日期来源冲突，未能确认。
- 未找到"编程智能体之间用 A2A 协作"的实际生产案例。

## 问题五：推荐——第一阶段、第三阶段分别用什么，什么规模才需要 Temporal

### Takeaway
**第一阶段：保持 river + 自写问题单状态机**，不引入任何工作流引擎。**第三阶段：自动执行的多步骤链路引入 DBOS Go（MIT，嵌入同一二进制，只依赖已有的 Postgres）**，问题单生命周期仍由状态机负责。Temporal 只有在"多个团队、上千并发的长链路工作流、需要专门平台团队运维、且不追求开源单二进制交付"时才值得，Cohive 自身在可预见规模内都达不到。

### Cited Findings
- river：事务入队、自动重试、定时调度、唯一任务，MPL-2.0，可嵌入 — [river README](https://github.com/riverqueue/river)
- river 的工作流功能属付费 Pro（125 美元/月） — [River Pro](https://riverqueue.com/pro)
- DBOS Go：MIT 库，仅需 Postgres；持久睡眠可达数天数周；`Recv` 支持 48 小时级超时等待；队列支持并发/限速/去重 — [DBOS Go README](https://github.com/dbos-inc/dbos-transact-golang)、[DBOS 工作流通信](https://docs.dbos.dev/golang/tutorials/workflow-communication)
- DBOS 管理面板 Conductor 自托管为专有许可，生产需许可证密钥 — [DBOS Conductor 自托管](https://docs.dbos.dev/production/hosting-conductor)
- Hatchet：MIT，Postgres 必需、RabbitMQ 可选，Hatchet Lite 单镜像定位低吞吐生产，压测 1 万任务/秒 — [Hatchet README](https://github.com/hatchet-dev/hatchet)、[Hatchet 自托管](https://docs.hatchet.run/self-hosting)
- Temporal 生产自托管需要数据库加（示例中的）Elasticsearch、多个服务、手动管理表结构升级；开发服务器不承担持续负载 — [Temporal 自托管部署](https://docs.temporal.io/self-hosted-guide/deployment)
- DBOS 作者估计 Postgres 上可支撑每秒数千个工作流/步骤（厂商自估） — [HN 评论](https://news.ycombinator.com/threads?id=hmaxdml)

### Inferences
- **第一阶段（2–3 周，跑通一次闭环）**：
  - 用 river（开源版）+ `issues` / `issue_events` 表 + 状态迁移函数。所有"等待"都是表里的状态，所有"超时"都是同事务入队的定时 river 任务。
  - 理由：需求里没有真正的多步骤长链路，引擎带来的确定性重放约束、版本化、额外概念对 2–3 周的目标是净负担；river 已在方案中，零新增依赖。
  - 关键工程点（与选型无关、必须自己做）：WebSocket 推送的确认与重连补发；状态迁移的幂等键（智能体会重试工具调用）；拉闸标记在每个任务入口检查。
- **第三阶段（自动执行、超时升级策略、拉闸）**：
  - 问题单生命周期仍走状态机；**"认领后自动修复"这条链路**（申请短期凭证 → 建工作树 → 跑无界面命令 → 推送 → 建合并请求 → 等流水线 → 请求验证 → 吊销凭证）用 DBOS Go 写成一个持久工作流：每步自动检查点，崩溃后从断点恢复，`Recv` 等待流水线回调或人工审批（带超时），失败可走补偿步骤（吊销凭证、清理工作树）。
  - 选 DBOS Go 而不是 Hatchet 的理由：嵌入同一可执行文件、共用现有 Postgres，开源用户部署形态不变；MIT。代价是放弃 Hatchet 的现成看板（DBOS 的 Conductor 看板是专有的，Cohive 需在自己的看板里展示执行状态，或直接查询 DBOS 的系统表）。
  - 备选：若届时 DBOS Go 不满足（例如需要跨多个服务节点的复杂调度），Hatchet 是 MIT、Postgres 为主的次优选择，代价是多一个容器。go-workflows 是同类嵌入式方案但社区小（529 星），只作备胎。
  - 不选 river Pro 工作流：付费且许可证条款未核实，开源项目依赖付费组件不合适。
- **什么时候才需要 Temporal**（推断，非来源结论）：同时满足以下多数条件时——
  1. 工作流数量到每秒数千步骤以上、且 Postgres 写入成为瓶颈；
  2. 工作流跨多种语言的多个独立部署服务，需要统一的编排中枢；
  3. 有专门平台团队运维数据库 + Elasticsearch + 多服务集群；
  4. 产品以托管服务形式提供，不再要求用户"一个镜像自部署"。
  Cohive 的负载是"每个工作空间每天几十到几百张问题单、几十个自动执行任务"，比上述门槛低若干数量级；对一个开源自部署产品而言，让用户额外运维 Temporal 本身就是最大的推广阻力。
- **对用户问题本身的审视**：
  - "超时升级、等待审批"常被误认为需要工作流引擎，实际上它们是**实体状态 + 定时检查**，引擎反而会把"问题单在哪个状态"藏进引擎内部历史，看板查询和人工改指派变得更难。建议明确原则：**问题单的真实状态只存在业务表里**，引擎（如果有）只负责执行副作用链路。
  - 风险点在"至少一次投递"的最后一公里——推送到开发者电脑和智能体会话——这是任何引擎都不负责的部分，应作为第一阶段的设计重点。

### Gaps
- DBOS Go 在 Cohive 预期负载下的实测数据缺失，建议第三阶段前做一次小规模压测。
- DBOS Go 的工作流版本升级（代码变更后正在运行的工作流如何恢复）机制本次未核实，这对第三阶段自动执行链路迭代很关键。
- 未核实 DBOS Go 是否支持 SQLite（若要支持"单二进制 + SQLite 试用模式"会受影响）。
