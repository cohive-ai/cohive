## 问题一：有哪些开源项目在做“编程智能体之间的消息 / 收件箱 / 协调”？各自现状如何？

### 结论
这个方向已经有大量开源项目，大致分三类：（1）**智能体间消息与代码占用层**：MCP Agent Mail、Concord MCP、claude-peers-mcp，以及 Claude Code 自带的跨会话消息；（2）**单人并行编排器**：Claude Squad、Vibe Kanban、Crystal/Nimbalyst、Sculptor、Conductor、Gas Town；（3）**多人工作空间与任务看板**：Multica（Go 后端 + Postgres + 本机守护进程，架构几乎与 Cohive 方案一致）。纯粹做“多人、跨机器、跨工具、人在环中交接问题单”的项目目前没有找到完全对应的。

**MCP Agent Mail**
- Python 版 README 首行声明已被 Rust 版取代、不再维护，新安装请用 Rust 版 — [mcp_agent_mail README](https://github.com/Dicklesworthstone/mcp_agent_mail)
- 自述为“编程智能体的邮件式协调层”：记忆友好的身份（如 GreenCastle）、收件箱与发件箱、可搜索的线程、对文件或通配路径的“自愿性文件占用租约”；用 git 存放人可审计的文件、用 SQLite 做索引 — [mcp_agent_mail README](https://github.com/Dicklesworthstone/mcp_agent_mail)
- Rust 版：45 个 MCP 工具、25 个只读 MCP 资源、16 屏终端界面；工具分组包括身份、消息、联系人、占用、搜索、宏、“产品总线”、“构建槽位” — [mcp_agent_mail_rust README](https://github.com/Dicklesworthstone/mcp_agent_mail_rust)
- 占用是“建议性租约而非硬锁”：带过期时间，冲突时报告而不是等待，提交前钩子在提交时拦截与他人独占占用冲突的提交，但可被覆盖 — [mcp_agent_mail_rust README](https://github.com/Dicklesworthstone/mcp_agent_mail_rust)
- 写入路径：先写 SQLite 作为实时状态，再把消息、档案、占用以人可读文件写进每个项目的 git 仓库作为持久账本 — [mcp_agent_mail_rust README](https://github.com/Dicklesworthstone/mcp_agent_mail_rust)
- Python 版在真实负载下有三类问题：git 锁文件争用、SQLite 连接池耗尽、大量智能体同时访问时级联故障；Rust 重写用批处理、有界连接池、背压解决 — [mcp_agent_mail_rust README](https://github.com/Dicklesworthstone/mcp_agent_mail_rust)
- 跨仓库协作：同一 `project_key` 共用一条总线；或各仓库独立，通过 `request_contact` / `respond_contact` 建立联系后互发，并用共同的 `thread_id`（如工单号）串起来 — [mcp_agent_mail README](https://github.com/Dicklesworthstone/mcp_agent_mail)
- 网络形态：默认监听 `127.0.0.1:8765`；可 `--host 0.0.0.0` 对外，生产环境用 `HTTP_BEARER_TOKEN`，也支持 JWT；Docker 镜像建议端口只绑本机回环，除非要让远程智能体访问 — [mcp_agent_mail_rust README](https://github.com/Dicklesworthstone/mcp_agent_mail_rust)
- 有“人类监督者”网页发信功能，可绕过联系人策略给任意智能体发高优先级消息 — [mcp_agent_mail README](https://github.com/Dicklesworthstone/mcp_agent_mail)
- 有商业配套（iOS 应用加主机自动化），开源部分为基础服务器 — [mcp_agent_mail README](https://github.com/Dicklesworthstone/mcp_agent_mail)
- 许可证为“MIT（附 OpenAI/Anthropic 附加条款）”：不向 OpenAI、Anthropic 及其关联方或“代表其行事的任何人”授予任何权利，并禁止向它们提供、托管、部署、执行该软件或衍生作品；附加条款与 MIT 冲突时以附加条款为准 — [LICENSE](https://github.com/Dicklesworthstone/mcp_agent_mail/blob/main/LICENSE)

**claude-peers-mcp**
- 让同一台机器上的多个 Claude Code 会话互相发现和发消息；中转进程跑在 `localhost:7899`，用 SQLite；每个会话的 MCP 服务每秒轮询，再通过 Claude Code 的“频道”协议推入会话；“一切仅限本机” — [claude-peers-mcp README](https://github.com/louislva/claude-peers-mcp)
- 启动需要 `--dangerously-load-development-channels` 参数（依赖研究预览中的频道功能），工具只有 `list_peers` / `send_message` / `set_summary` / `check_messages` 四个 — [claude-peers-mcp README](https://github.com/louislva/claude-peers-mcp)
- 最近推送 2026-04-26，近半年未更新 — [GitHub 仓库](https://github.com/louislva/claude-peers-mcp)

**Claude Code 自带：跨会话消息与“智能体团队”**
- 跨会话消息：v2.1.224 起默认开启；同机会话间通过每会话的 Unix 套接字（Windows 为命名管道）投递，不经 Anthropic 服务器；跨机器或云端会话必须通过“远程控制”连接，经 Anthropic 服务器中转，并要求用 claude.ai 账号登录，API 密钥、Bedrock、Vertex、Foundry 均不可用 — [官方文档：跨会话消息](https://code.claude.com/docs/en/cross-session-messaging)
- 作用范围明确是“你自己的会话”（"your other Claude Code sessions"）；同机不同操作系统用户的会话无法互投；容器内外不能互通 — [官方文档：跨会话消息](https://code.claude.com/docs/en/cross-session-messaging)
- 安全模型：收到的消息标注为“来自另一个会话而非用户”，不能代替用户批准权限、不能改配置、消息里的命令不执行；接收方可设 `crossSessionInbound` 为接受 / 暂存 / 拒绝；`isolatePeerMachines` 可要求跨机器发送前人工批准 — [官方文档：跨会话消息](https://code.claude.com/docs/en/cross-session-messaging)
- 限制：只能发纯文本；同机单条约一百万字符上限；接收端最多排队 50 条、暂存最多 100 条；有防消息死循环的限流 — [官方文档：跨会话消息](https://code.claude.com/docs/en/cross-session-messaging)
- 智能体团队：仍是实验功能，需设置 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`；由一个主会话派生队友，共享任务列表（认领用文件锁防竞争）、邮箱为 `~/.claude/teams/{team}/inboxes/{agent}.json`；“每个会话只有一个团队”“不能跨会话共享团队”“不能嵌套”“主会话固定” — [官方文档：智能体团队](https://code.claude.com/docs/en/agent-teams)
- 官方建议避免文件冲突的方法只是“让每个队友负责不同文件集合”，没有占用或租约机制 — [官方文档：智能体团队](https://code.claude.com/docs/en/agent-teams)

**Concord MCP**
- 自述为“开源、本机优先的编程智能体通信与协调层”，支持 Claude Code、Codex、Cursor、Gemini CLI、Grok Build、Goose；功能是跨工具实时消息、编辑前检测重叠工作、共享决策、带证据交接 — [concord-mcp README](https://github.com/Get-Concord-AI/concord-mcp)
- 只有 5 个 MCP 工具：`start_work`（登记在场、认领任务、报告范围重叠）、`inspect_work`、`update_work`（含 prompt / reply 实时互问）、`transfer_work`（指派、接受、拒绝、释放、重新指派、交接、重开）、`finish_work`（记录证据、标记待审 / 完成）— [concord-mcp README](https://github.com/Get-Concord-AI/concord-mcp)
- 生命周期操作带单调递增的 `version`，用 `expected_version` 做乐观并发；能标记“陈旧认领”（拥有者已离开却未交接）；消息用 `idempotency_key` 去重；目标不可达时立即失败、不静默改投 — [concord-mcp README](https://github.com/Get-Concord-AI/concord-mcp)
- 存储为仓库根目录 `.concord/` 下的 SQLite；自述“面向使用同一份本地检出的编程智能体”，明确“不是编排器、不是托管同步服务” — [concord-mcp README](https://github.com/Get-Concord-AI/concord-mcp)
- 默认向 getconcord.ai 发送遥测（不含代码、路径、消息内容），可用 `DO_NOT_TRACK=1` 关闭；README 提到“Concord Cloud”按 git 远程地址命名项目 — [concord-mcp README](https://github.com/Get-Concord-AI/concord-mcp)
- 2026-07-14 创建，贡献者 10 人 — [GitHub 仓库](https://github.com/Get-Concord-AI/concord-mcp)

**Multica**
- 自述为“源码可见”的工作空间：像给同事派活一样把问题单派给编程智能体，智能体认领、汇报进度、提出阻塞、交回评审；可自托管 — [multica README](https://github.com/multica-ai/multica)
- 架构：Go 后端（Chi 路由、sqlc、gorilla/websocket）+ PostgreSQL 17；网页用 Next.js 16，桌面用 Electron，移动端用 Expo；本机守护进程通过 WebSocket 连服务端，拉起本机的编程智能体命令行 — [multica README](https://github.com/multica-ai/multica)
- 支持 26 种智能体命令行，包括 Claude Code、Codex、Cursor、Copilot CLI、OpenCode、Kimi、Qwen Code、DeepSeek Harness 等 — [multica README](https://github.com/multica-ai/multica)
- 触发方式只有四种：指派问题单、评论中 @ 智能体、直接对话、定时任务；“智能体从不自行开始工作” — [Multica 文档：工作原理](https://multica.ai/docs/how-multica-works)
- “小队”：一个领队智能体加若干成员（可以是智能体或人）；领队读问题单后 @ 合适的成员分派；成员 @ 他人即为交接；有防循环规则 — [Multica 文档：小队](https://multica.ai/docs/squads)
- 自托管时可接自建 GitLab、Gitea、Forgejo：按分支名或标题里的问题编号关联合并请求，合并后自动改状态，镜像流水线状态，通过 webhook 接收事件；克隆推送用运行机自己的 git 凭据 — [Multica 文档：自建代码托管](https://multica.ai/docs/vcs-integration)
- 能力还包括：运行日志回放、运行中给智能体追加消息（目前支持 Claude Code、Codex、Grok）、费用统计、评审关口、收件箱、失败重试、角色权限、飞书 / 钉钉 / 企业微信等频道 — [multica README](https://github.com/multica-ai/multica)
- 自托管服务端每天发送一次匿名部署统计，可用 `DO_NOT_TRACK=1` 关闭 — [multica README](https://github.com/multica-ai/multica)
- 2026-01-13 创建，到 2026-10-14 已有 52,789 星，开放问题 1,864 个，当天仍有提交 — [GitHub 仓库](https://github.com/multica-ai/multica)

### 推断
- Claude Code 自带跨会话消息上线后，claude-peers-mcp 这类“同机 Claude 互发消息”的项目价值基本被官方覆盖（其近半年无更新也印证这一点）。
- MCP Agent Mail 是“智能体之间邮件 + 文件占用租约”设计最完整、经过真实负载打磨的项目，但它是单个服务器实例、SQLite 加 git 存储的个人或小团队工具，没有成员 / 工作空间 / 权限模型。
- Concord MCP 的工具设计（5 个粗粒度工具、乐观并发版本号、幂等键、陈旧认领）与 Cohive 的问题单交接非常接近，但范围限定在“同一份本地检出”。
- Cohive 内部 PRD 名叫“ACP”，与 Agent Client Protocol（ACP）以及 IBM 早先的 Agent Communication Protocol 重名，对外开源时容易混淆，建议对外只用 Cohive 这个名字。

## 问题二：商业 / 平台方的先行方案做到哪一步，缺什么？

### 结论
平台方都在做“把问题单 / 合并请求派给云端智能体”的模式（GitHub Agent HQ、GitLab Duo 外部智能体、Linear 智能体委派、OpenAI Symphony），协作中心是**托管平台上的问题单和合并请求**，而不是开发者本机正在交互的会话。它们都没有解决“A 的本机交互会话直接把问题交给 B 的本机交互会话，并闭环验证”这一点，也没有代码占用声明。

- 编排嵌入 GitHub 原有流程（问题单、分支、合并请求、评审），沿用已有权限与审计 — [The New Stack](https://thenewstack.io/github-embraces-the-coding-agent-competition-with-agent-hq/)

### 推断
- 平台方的共性是“智能体是被派活的执行者，协作载体是问题单 / 合并请求”。它们缺的恰好是 Cohive 的核心：开发者本机交互会话之间的直接交接、接口归属路由、复现脚本驱动的验证闭环、代码占用声明。
- GitLab Duo 对公司私有化 GitLab 来说要额外买点数，离线还需附加许可；外部智能体在自管实例上的可用性存疑。Cohive 若只把 GitLab 当代码平台（合并请求、流水线、webhook），不依赖 Duo，可以避开这部分成本。
- Symphony 的“规范优先、任意语言实现”很适合 Cohive 第三阶段的自动执行借鉴：用一份 `WORKFLOW.md` 描述每个仓库的执行规则。

### 缺口
- GitHub Agent HQ 截至 2026-10 是否已正式可用、价格层级，未在官方更新日志中核实。
- GitLab 外部智能体在自管实例上的现状未在 docs.gitlab.com 当前版本核实，需上自家实例验证。
- Devin、Codex 云端在“多人协作”上的具体能力（如多人共享会话）未深入核实。
- Jira 的智能体集成（如 Atlassian Rovo 开发智能体）未检索。

## 问题三：这些方案是“单人多智能体”还是“多人多工具”？跨机器、跨人、跨工具支持如何？

### 结论
绝大多数开源项目是**单人、单机、多智能体**；能跨机器的只有 MCP Agent Mail（单服务器、共享令牌）、Claude Code 远程控制（限本人账号、限 Claude）和 Multica（真正的多成员工作空间，但以“派活给守护进程跑无界面命令”为主）。“多人 + 跨机器 + Claude Code 与 Codex 混用 + 人在交互会话中协作”这一组合，没有现成项目完整覆盖。

### 已核实的数据

| 项目 | 多人 | 跨机器 | 跨工具（Claude Code 与 Codex 混用） | 依据 |
|---|---|---|---|---|
| Claude Code 跨会话消息 | 否，仅本人会话 | 仅经远程控制，需 claude.ai 登录 | 否，仅 Claude Code | [文档](https://code.claude.com/docs/en/cross-session-messaging) |
| Claude Code 智能体团队 | 否 | 否，存本机 `~/.claude/teams` | 否 | [文档](https://code.claude.com/docs/en/agent-teams) |
| claude-peers-mcp | 否 | 否，“仅限本机” | 否，仅 Claude Code | [README](https://github.com/louislva/claude-peers-mcp) |
| MCP Agent Mail | 无成员模型，共享 bearer 令牌 | 可以，服务绑 0.0.0.0 | 是，MCP 通用 | [README](https://github.com/Dicklesworthstone/mcp_agent_mail_rust) |
| Concord MCP | 否 | 否，“同一份本地检出” | 是，6 种工具 | [README](https://github.com/Get-Concord-AI/concord-mcp) |
| Multica | 是，成员与角色 | 是，多运行机 | 是，26 种命令行 | [README](https://github.com/multica-ai/multica) |

| Vibe Kanban | 云端多人功能已随公司关停 | — | 是 | [关停公告](https://vibekanban.com/blog/shutdown) |
| Gas Town | 否（单人“镇”） | 未核实 | 是 | [README](https://github.com/gastownhall/gastown) |
| GitHub Agent HQ / GitLab Duo / Linear | 是（平台成员） | 云端执行 | 是（多家智能体） | 见问题二 |

- MCP Agent Mail 文档提醒：共享同一个 bearer 凭据的客户端彼此可读，无法隔离恶意客户端 — [mcp_agent_mail_rust README](https://github.com/Dicklesworthstone/mcp_agent_mail_rust)
- Multica 的人机交互形态是“问题单 + 评论 + @ 提及”，智能体在守护进程拉起的运行中工作 — [Multica 文档：工作原理](https://multica.ai/docs/how-multica-works)

### 推断
- Cohive 的差异化不在“多智能体”，而在三点：①**跨人**的身份与归属（谁负责哪个服务 / 接口）；②**开发者交互会话**作为一等参与者（而非只派活给后台运行）；③**验证闭环**（复现脚本必填、自动重跑）。
- Claude Code 的跨会话消息证明“消息来自另一智能体，不等于用户授权”的信任模型是业界做法，Cohive 第 8 节第 1 条红线方向正确。

### 缺口
- Multica 是否支持开发者自己的交互式 Claude Code / Codex 会话以 MCP 方式直接读写其问题单（而不是只靠守护进程派运行），未核实。代码中存在大量 MCP 相关文件（如 `server/internal/daemon/remote_mcp_broker.go`、`server/internal/handler/workspace_mcp.go`），但未读代码确认其用途；README 只说“智能体通过同一个命令行驱动 Multica”，并提供了给 Codex / Claude Code 用的命令行技能 [multica-cli](https://github.com/multica-ai/multica-cli)。
- Gas Town 是否支持多机，未核实。

## 问题四：哪个最接近 Cohive 的定位？基于它扩展是否可行？

### 结论
**Multica 最接近**，技术栈（Go + Postgres + WebSocket + 本机守护进程 + 支持自建 GitLab）几乎与 Cohive 方案第 7 节一一对应，而且已经做到 5 万多星、日更。但它的许可证是带附加条件的“源码可见”许可，不适合作为一个打算开源的项目的基础；作为**公司内部自用**则允许。**MCP Agent Mail** 在“消息 + 占用租约”上设计最好，但许可证有针对 OpenAI / Anthropic 的附加限制，且技术栈是 Rust + SQLite 单实例，不宜作为依赖，只宜借鉴设计。**Concord MCP**（MIT）可借鉴工具设计和并发语义。

### 已核实的数据
- Multica 许可证条件 1(a)：未取得商业许可时，不得用其源码向第三方提供托管服务，也不得把 Multica 作为组件嵌入出售、授权或商业分发给第三方的产品；面向本组织以外用户的公开实例即使免费也需要商业许可；“单一组织内部使用（含多个工作空间）不需要商业许可” — [Multica LICENSE](https://github.com/multica-ai/multica/blob/main/LICENSE)
- 条件 1(b)：未获书面豁免，不得移除或修改 Multica 界面上的标志、产品名和版权信息；该限制覆盖从其界面代码派生的任何界面，即使被修改、移动或抽取到其他仓库 — [Multica LICENSE](https://github.com/multica-ai/multica/blob/main/LICENSE)
- 条件 1(c)：只用其后端、守护进程或命令行而不用其界面时，必须保留版权声明，并在面向用户的文档中写明“基于 Multica 构建”并附链接 — [Multica LICENSE](https://github.com/multica-ai/multica/blob/main/LICENSE)
- 条件 2：贡献者同意出品方可以随时把许可证改得更严或更松，贡献代码可被其用于商业云业务 — [Multica LICENSE](https://github.com/multica-ai/multica/blob/main/LICENSE)
- MCP Agent Mail 附加条款：对 OpenAI、Anthropic 及“直接或间接为其利益或受其指使行事的任何人”不授予任何权利，并禁止为其提供、托管、部署或执行该软件及衍生作品；冲突时附加条款优先 — [mcp_agent_mail LICENSE](https://github.com/Dicklesworthstone/mcp_agent_mail/blob/main/LICENSE)
- Concord MCP 为标准 MIT — [concord-mcp README](https://github.com/Get-Concord-AI/concord-mcp)
- Vibe Kanban 为 Apache-2.0，但公司已关停、转社区维护 — [GitHub 仓库](https://github.com/BloopAI/vibe-kanban)、[关停公告](https://vibekanban.com/blog/shutdown)
- Claude Squad 为 AGPL-3.0 — [GitHub 仓库](https://github.com/smtg-ai/claude-squad)

**许可证判断（推断，非法律意见）**

| 项目 | 公司内部商业使用 | 被一个可能开源的 Cohive 依赖或派生 |
|---|---|---|
| Multica | 允许（单一组织内部使用无需商业许可） | 不适合：派生物继承附加条件，对外托管或商业分发需商业许可，界面品牌不可去除，许可证可被单方修改 |
| MCP Agent Mail | 普通公司内部使用大概率允许 | 不适合：非标准许可证；Cohive 本身就是给 Claude Code、Codex 用的，与“不得为 Anthropic/OpenAI 利益执行”的条款边界模糊，开源后无法约束下游用户身份 |
| Concord MCP | 允许 | 适合（MIT），但它是 TypeScript 本机工具，更适合借鉴而非依赖 |

| Claude Squad | 允许内部使用 | 慎用：AGPL 有网络服务传染义务 |
| Beads / Gas Town | 允许 | 适合（MIT），Go 实现 |
| A2A / ACP 协议 | 允许 | 适合（Apache-2.0） |

### 推断
- **方向判断**：Multica 已经覆盖了 Cohive 方案的“看板 + 服务端 + 本机守护进程 + 多工具 + GitLab 联动 + 自动执行（第三阶段）”的大部分。Cohive 若与它正面重叠，很难追上其规模；Cohive 应把差异点压到 Multica 不做的地方：开发者**交互会话之间**的交接（MCP 直接进会话）、接口归属路由、接口变更广播、代码占用租约、复现脚本驱动的验证闭环。
- **整合可选路径**：
  1. 若 Cohive 定位为“公司内部工具”：可以直接自托管 Multica 作为看板与自动执行层，Cohive 只做一个 MCP 服务加问题交接 / 占用 / 广播的“薄层”，通过 Multica 的命令行或接口写入其问题单。代价是数据模型受制于 Multica，且许可证可能被单方收紧。
  2. 若 Cohive 要开源：不要派生 Multica 代码；只借鉴其架构（与 Cohive 现方案本就一致，说明方向被验证），自写 Go 服务端；占用租约与消息模型参照 MCP Agent Mail 和 Concord 的设计自行实现。
  3. 无论哪条路，第三阶段“自动执行”可考虑直接让用户接 Multica（内部）或参考 Symphony 规范，而非自研完整调度器。
- 建议在第一阶段之前，花半天实际自托管一次 Multica，确认它能否满足“问题交接闭环”的大部分需求；如果能，Cohive 第一阶段的工作量会大幅缩小，这是现有方案思考框架之外最值得先做的一步。

### 缺口
- 未取得 Multica 商业许可价格与条款。
- Multica 的数据模型（问题单字段、状态机）能否表达 Cohive 的“接口归属、复现脚本、验证结果、提交号”，未读代码核实。
- 未请法务确认 MCP Agent Mail 附加条款对“使用 Claude Code / Codex 的普通公司”的适用范围。

## 问题五：有哪些值得借鉴的设计？

### 结论
最值得借鉴的是：建议性文件占用租约（带过期时间 + 提交前钩子在提交时拦截）、线程号串联跨仓库对话、粗粒度少量工具 + 乐观并发版本号 + 幂等键、“消息不是授权”的信任模型、git 作为人可审计的账本（但实时状态放数据库）、领队 / 小队 @ 提及路由与防循环规则、依赖感知的任务库。

### 已核实的数据
- **建议性占用租约而非硬锁**：理由是对崩溃或被重置的智能体更稳健，租约到期自动失效，陈旧占用可回收；占用可选独占或共享，冲突时立即报告而不阻塞 — [mcp_agent_mail_rust README](https://github.com/Dicklesworthstone/mcp_agent_mail_rust)
- **提交前钩子**：设置 `AGENT_NAME` 后，钩子拦截与他人有效独占占用冲突的提交 — [mcp_agent_mail README](https://github.com/Dicklesworthstone/mcp_agent_mail)
- **占用原因关联任务号**：占用时把 `reason` 设为任务编号（如 `bd-123`），完成后释放 — [mcp_agent_mail README](https://github.com/Dicklesworthstone/mcp_agent_mail)
- **线程号**：跨仓库协作时保持共同的 `thread_id`（如工单号）以便汇总与审计 — [mcp_agent_mail README](https://github.com/Dicklesworthstone/mcp_agent_mail)
- **联系人审批**：跨项目发消息需先 `request_contact` / `respond_contact` 建立许可；人工确认的“关联项目”也不会自动授权跨项目发信 — [mcp_agent_mail README](https://github.com/Dicklesworthstone/mcp_agent_mail)
- **git 与数据库分工**：实时状态先写 SQLite，再异步把人可读文件写进 git；Python 版曾因 git 锁争用出故障 — [mcp_agent_mail_rust README](https://github.com/Dicklesworthstone/mcp_agent_mail_rust)
- **宏工具**：给较小模型提供 `macro_start_session` 等组合工具，降低调用次数 — [mcp_agent_mail README](https://github.com/Dicklesworthstone/mcp_agent_mail)
- **构建槽位**：`acquire_build_slot` / `renew_build_slot` / `release_build_slot`，用于限制并发构建 — [mcp_agent_mail_rust README](https://github.com/Dicklesworthstone/mcp_agent_mail_rust)
- **少量粗粒度工具 + 乐观并发 + 幂等**：Concord 只暴露 5 个工具；生命周期操作带 `expected_version`；消息带 `idempotency_key`；目标不可达立即失败不改投 — [concord-mcp README](https://github.com/Get-Concord-AI/concord-mcp)
- **陈旧认领检测**：标记拥有者已离开却未交接的认领 — [concord-mcp README](https://github.com/Get-Concord-AI/concord-mcp)
- **安装时写入全局指令文件**：Concord 全局模式会在 `~/.claude/CLAUDE.md`、`~/.codex/AGENTS.md` 等加一段说明，关闭时精确移除所加内容 — [concord-mcp README](https://github.com/Get-Concord-AI/concord-mcp)
- **消息不是授权**：Claude Code 把其他会话来的消息标为非用户输入，不能批准权限、不能改配置、命令不执行；接收方可设接受 / 暂存 / 拒绝 — [官方文档：跨会话消息](https://code.claude.com/docs/en/cross-session-messaging)
- **防消息死循环**：按发送方限流、短时间内相同消息去重、队列上限 50 条 — [官方文档：跨会话消息](https://code.claude.com/docs/en/cross-session-messaging)
- **空闲通知订阅**：`notify_when_idle`，对方下次空闲或退出时回一条通知，12 小时无响应自动取消 — [官方文档：跨会话消息](https://code.claude.com/docs/en/cross-session-messaging)
- **任务认领用文件锁防竞争、任务依赖自动解锁** — [官方文档：智能体团队](https://code.claude.com/docs/en/agent-teams)
- **小队路由与防循环**：领队只做分派不做实现；领队不因自己的评论被重新触发；显式 @ 他人的评论不唤醒领队；排队中的重复触发去重；纯文本 `@name` 不触发 — [Multica 文档：小队](https://multica.ai/docs/squads)
- **人保持主负责人**：Linear 委派时人仍是主负责人，智能体只是协作者 — [Linear 更新日志](https://linear.app/changelog/2025-07-30-agent-interaction-guidelines-and-sdk)
- **合并请求关联与状态联动**：按分支名或标题中的问题编号自动关联合并请求，所有关联合并请求合并后自动改状态，镜像 GitLab 流水线状态 — [Multica 文档：自建代码托管](https://multica.ai/docs/vcs-integration)
- **工作流文件 + 规范优先**：Symphony 用 `WORKFLOW.md`（YAML 头 + 提示词正文）描述执行规则，改动热加载；失败指数退避重试 — [Symphony SPEC](https://github.com/openai/symphony/blob/main/SPEC.md)
- **工作证明**：Symphony 要求智能体交付 CI 状态、评审反馈、复杂度分析、演示视频等证据 — [symphony README](https://github.com/openai/symphony)
- **依赖感知任务库**：Beads 存于 `.beads/issues.jsonl`，提供“就绪工作”选择、优先级、状态 — [mcp_agent_mail README（Beads 章节）](https://github.com/Dicklesworthstone/mcp_agent_mail)

### 推断
- Cohive 的 `cohive_declare_work` 可直接采用“建议性租约 + 过期时间 + 独占 / 共享 + 立即报告冲突 + 可选提交前钩子 + 原因填问题单号”的组合，比硬锁更合适，且可从第二阶段提前到第一阶段末作为低成本功能。
- MCP 工具数量建议参考 Concord 的“少而粗”，而不是 Agent Mail 的 45 个；Cohive 方案第 4.1 节 8 个工具规模合适，可再给问题单状态变更加 `expected_version` 和幂等键。
- “消息不是授权”的信任模型可直接写进 `cohive init` 生成的指令文件。
- git 作为存储的经验教训：实时状态必须放数据库（Cohive 用 Postgres 正确），git 只适合做可审计的导出或归档。
