# Cohive 方案 V0.1

- 状态：方案草案，前端选型已确认，其余待确认项见第 11 节
- 日期：2026-10-14
- 来源：在《ACP 多开发者 AI Agent 协作平台 PRD V0.1》基础上重新制定

## 1. 要解决的问题

多个开发者各自使用不同的编程智能体工具（Claude Code、Codex 等），分别负责不同服务。智能体之间无法直接传话，跨人、跨工具、跨仓库的协作只能靠人工复制上下文、转述、通知，导致：

- 上下文在转述中丢失，对方智能体重复分析
- 问题归属和责任人不清
- 修复后没有人负责通知和验证，闭环断在半路
- 代码版本对不上，说的不是同一个提交
- 两个智能体同时改同一块代码，或改了接口没通知下游

**核心诉求：一个工具，解决多人、多编程工具之间相互协作的问题。**

## 2. 设计原则

1. **做共享协作层，不做智能体控制中心。** 各编程工具共同支持的接入方式只有三种：模型上下文协议（MCP）、项目指令文件（`CLAUDE.md` / `AGENTS.md`）、命令行。Cohive 只依赖这三者，不深度适配任何一个工具的内部机制，工具升级不会把 Cohive 搞坏。
2. **先让智能体可靠地传话，再让智能体自动干活。** 第一版由人确认后才开工，自动执行放到后期。
3. **接入成本压到最低。** 多人工具最大的风险是同事不装。新人接入只需三步：安装命令行、登录、在项目里初始化。
4. **安全只守真正的红线**（见第 8 节），不在第一版堆多级干预机制。
5. **不绑定代码托管平台。** GitLab、GitHub 都通过适配器接入。

## 3. 关键场景的默认答案

| 问题 | 默认答案 |
|---|---|
| 问题交给人还是交给智能体？对方不在怎么办？ | 交给服务负责人。对方不在时排队，并提醒本人；超时升级给工作空间管理员 |
| 自动化到哪一步？ | 第一版由负责人确认后，在自己的工具里处理；自动执行放到第三阶段 |
| 第一版覆盖哪些协作？ | 问题交接闭环（见第 6 节优先级） |
| 修复后在哪验证？ | 验证环境由团队在工作空间里配置，Cohive 只负责记录和触发验证 |
| 先给谁用？ | 先由作者本人在自己的多会话、多项目场景里试用，再推给团队 |

## 4. 产品组成

| 部分 | 作用 |
|---|---|
| **协作服务**（服务端） | 保存工作空间、仓库、服务、成员、问题单、接口约定、代码占用、动态；负责路由、超时升级和实时推送 |
| **MCP 接入** | 由协作服务直接提供远程 MCP 服务，各编程工具配置一次即可调用 |
| **本机小助手**（`cohive` 命令行加后台进程） | 接入本机编程工具、收取推送、系统通知、在会话中提示待办；第三阶段负责自动执行 |
| **看板**（网页） | 人查看全局、改指派、审批、拉闸 |
| **官网与博客** | 项目介绍、文档、开发过程记录 |

### 4.1 MCP 工具清单（初版）

| 工具 | 作用 |
|---|---|
| `cohive_report_issue` | 提交问题单 |
| `cohive_inbox` | 查看分配给自己的待办 |
| `cohive_claim_issue` | 认领问题单 |
| `cohive_update_issue` | 更新状态、补充说明和证据 |
| `cohive_request_verification` | 修复完成，请求发起方验证 |
| `cohive_verify` | 提交验证结果（通过 / 重开） |
| `cohive_who_owns` | 查询某个接口、模块或服务的负责人 |
| `cohive_declare_work` | 声明“我正在改某块代码”（第二阶段） |

### 4.2 接入流程

```
cohive login            # 登录工作空间，为“本人 + 本机工具”签发令牌
cohive init             # 在项目里写入 MCP 配置和一段协作说明（CLAUDE.md / AGENTS.md）
cohive daemon           # 后台进程：保持长连接、收推送、发系统通知
```

会话内的待办提示：Claude Code 通过钩子在会话开始和每次提交提示词时附带待办摘要；不支持钩子的工具，由指令文件要求智能体在开始工作前先调用 `cohive_inbox`。

## 5. 核心流程：问题交接闭环

示例：A 用 Claude Code 写前端，B 用 Codex 写订单服务。

1. A 的智能体联调时发现接口返回不对，调用 `cohive_report_issue`。问题单自动带上仓库、分支、提交号、期望结果、实际结果，以及**一段可直接运行的复现脚本**（必填）。
2. 协作服务按接口归属表把问题路由给订单服务的负责人 B。归属不确定时，退回 A 本人确认。
3. B 的本机小助手弹出系统通知；B 下次与 Codex 对话时，Codex 看到待办，读取完整上下文后认领。
4. B 修复、推送、提交合并请求，调用 `cohive_request_verification`，附上合并请求和部署环境。
5. A 收到待验证，复现脚本自动重跑：通过则关闭，失败则重开并退回 B。
6. 全程在看板可见。超时、来回超过上限轮次、归属争议时，自动升级给人处理。

### 5.1 问题单状态

```
OPEN → ROUTED → ACCEPTED → FIXING → READY_FOR_VERIFICATION → VERIFIED
                                                            ↘ REOPENED → FIXING
任意状态 → ESCALATED（超时 / 超轮次 / 归属争议 / 人工升级）
```

每次状态变化都记录操作者（哪个人的哪个工具）和时间。

### 5.2 问题单字段（最小集）

`id`、`workspace`、`source`（人 + 工具）、`target_service`、`owner`、`severity`、`title`、`expected`、`actual`、`repro`（复现脚本）、`evidence`、`repo`、`branch`、`commit`、`status`、`correlation_id`、`deadline`、关联的合并请求与流水线。

问题单只引用明确的提交号；未提交的工作树改动需单独标注。

## 6. 协作能力优先级

| 优先级 | 能力 | 解决什么 | 阶段 |
|---|---|---|---|
| 第一 | 问题交接闭环 | 人工复制粘贴、修完没人验证 | 一 |
| 第二 | 接口变更广播：接口定义文件变更后自动通知所有下游 | 改完才发现弄坏了别人 | 二 |
| 第二 | 代码占用声明 | 两个智能体同时改同一块代码 | 二 |
| 第三 | 共享约定库：团队决策写一次，所有智能体可查 | 各人的智能体各说各话 | 三 |
| 第三 | 自动执行：认领后在独立工作树中自动修复 | 对方离线时也能推进 | 三 |

## 7. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 服务端 | Go + Postgres；任务队列用基于 Postgres 的 Go 队列库（如 river） | 团队熟悉 Go；一个数据库即可保证至少一次投递，不引入消息中间件 |
| 实时推送 | WebSocket 长连接，由本机小助手主动连服务端 | 开发者电脑在内网，服务端无法反向连入 |
| MCP 接入 | 协作服务直接提供远程 MCP 服务，按“人 + 工具”签发令牌 | 各工具配置一个地址即可；每条消息可追溯到具体的人和工具 |
| 本机小助手 | Go 单文件程序 | 跨平台，安装简单 |
| 看板 | React + Vite，TanStack Router、TanStack Query、shadcn/ui、Tailwind；打包为静态文件嵌入 Go 程序 | 见 7.1 |
| 官网与博客 | Next.js（或 Astro） | 需要搜索引擎收录和服务端渲染，正是 Next.js 的长处 |
| 代码平台 | 适配器模式，先接 GitLab，再接 GitHub | 公司用 GitLab，开源用户多在 GitHub |
| 自动执行（第三阶段） | 无界面命令（`claude -p --output-format stream-json`、`codex exec`），在独立工作树中运行 | 不往开发者正在用的会话里插任务 |
| 代码图谱 | graphify 作为可选证据来源 | 数据随仓库版本管理 |

### 7.1 前端选型决策（已确认）

- **看板不用 Next.js。** 看板是登录后的内部页面，不需要搜索引擎收录；后端已是 Go，不需要 Next.js 的服务端能力。用 Next.js 会多出一个要部署的 Node 服务，还要承担服务端渲染带来的问题（局域网访问白屏、服务端读取浏览器存储报错等）。
- **看板用 React + Vite。** 打包为纯静态文件，通过 Go 的 `embed` 嵌入，整个 Cohive 服务端发布为一个可执行文件或一个 Docker 镜像，开源用户自部署最简单。
- **Next.js 用在官网与博客。** 那里需要搜索引擎收录、服务端渲染和便捷的托管部署。
- 不再使用 Vue。

### 7.2 明确不纳入的选项

| 选项 | 原因 |
|---|---|
| GitNexus 进入核心链路 | 许可证为 PolyForm Noncommercial 1.0.0，只允许非商业使用；只能作为开发者本机的可选插件 |
| DeepSeek Harness 作为编排层 | 它与 Claude Code、Codex 同属编码智能体运行框架，不是编排层；仍处于开发者预览阶段。将来只作为一种可接入的工具 |
| 依赖 Claude Code 频道功能往运行中的会话推消息 | 仍是研究预览，要求 claude.ai 账号登录，第三方报告可靠性一般；作为可选增强，不作为基础 |
| 自建消息中间件（Kafka、NATS 等） | Postgres 队列足以满足当前规模 |

### 7.3 仓库结构（初拟）

```
cmd/cohive-server/   协作服务入口
cmd/cohive/          命令行与本机小助手
internal/            服务端与命令行共享的业务代码
web/                 看板（React + Vite），构建产物嵌入服务端
docs/                方案与设计文档
```

官网与博客放在本仓库的 `site/` 目录，还是独立成仓库，待定。

## 8. 安全红线

1. 收到的问题单、评论一律当数据处理，不当指令执行，防止一个智能体借问题描述指使另一个智能体。
2. 自动执行默认关闭，需工作空间与个人双重开启。
3. 合并请求必须由人审批。
4. 自动化使用的凭证短期有效、只对单个仓库生效、可随时吊销。拉闸即吊销凭证加停止派发。

## 9. 分阶段计划

| 阶段 | 内容 | 目标 |
|---|---|---|
| 一（约 2–3 周） | 协作服务、MCP 接入、命令行、简易看板 | Claude Code 与 Codex 之间完整跑通一次“发现 → 交接 → 修复 → 验证” |
| 二 | 接口变更广播、代码占用声明、会话内待办提示、GitLab 合并请求与流水线联动 | 覆盖主要的日常协作场景 |
| 三 | 自动执行、超时与升级策略、拉闸、图谱证据引用、GitHub 适配 | 对方离线时也能推进，并具备开源条件 |

## 10. 成功指标

跨仓库问题平均交接耗时、人工复制与转述次数、首次正确路由率、问题闭环时长、重复分析次数、自动验证成功率、人工升级率。

先采集基线，再定目标值。基线可在第一阶段上线前，人工记录两周的跨人交接情况获得。

## 11. 待确认事项

1. 第 6 节的能力优先级，尤其是“接口变更广播”和“代码占用声明”是否列入第二阶段。
2. 第一版由人确认后才开工、自动执行放到第三阶段，是否接受。
3. 第一阶段先在作者本人的多会话场景试用，还是直接给团队使用。
4. 智能体执行所用额度：团队 API 密钥，还是开发者个人订阅（涉及计费归属与服务条款）。
5. 与公司内部 ACP 需求的关系：同一产品，还是公司版基于 Cohive 定制。
6. 官网与博客的仓库归属。
