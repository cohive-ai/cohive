## 怎么做的

1. **计时**（第十二号迁移 `0012_overdue_reminder.sql`）
   - 问题单加两列：`status_since`（进入当前状态的时间），`remind_level`（本轮已催到第几档：0 没催，1 已再 @ 当事人，2 已同时 @ 管理员）。
   - 计时起点在存储层更新问题单时自动重置：状态变了，或负责人换了，就重新计时、档位归零（`store.UpdateIssue`）；管理员改派发起人时也一样（`store.SetIssueSource`）。
   - 所以下面几种情况都会重新计时：转交（仍是待接单但换了人）、重开后再进待验证、改派。
2. **时长**：工作空间加两列 `remind_open_hours`（默认 4）、`remind_verify_hours`（默认 24），0 表示关闭，范围 0 到 720 的整数小时。
3. **到点写催办**（`core.QueueReminders`）
   - 投递后台循环大约每分钟调一次，按数据库时间判断，`FOR UPDATE SKIP LOCKED`，没有引入 river。
   - 只看待接单、待验证；“修复中”等状态不计时。
   - 第 1 档：群里再 @ 当事人（待接单是负责人，待验证是发起人）。
   - 第 2 档：再过一个周期，@ 当事人和工作空间的管理员（在册、未停用；当事人本身是管理员时不重复列出），之后不再发。
   - 停机很久后，一次就跳到应到的档位，不会第 1、2 档连发两条。
   - 没配任何机器人时，服务端另起一个只写催办的循环：会话内提醒照发，群催办写进待发记录，设置机器人后照常补发（受 24 小时有效期限制）。
4. **催办属于“要动手”的通知**：写入时记下问题单的状态与负责人，投递前核对，变了就不发（沿用现有的过时判断）。
5. **渲染**：Telegram 和钉钉共用。
   - 第 1 档：“#N 已等待接单超过 4 小时，请 @X 接单、退回或转交”，待验证同理。
   - 第 2 档：“#N 已等待接单超过 8 小时，仍没有动作：请 @X 尽快接单、退回或转交；请管理员 @A @B 协调”；没有别的管理员时只写前半句。
   - 钉钉卡片标题：“#N 催办”“#N 催办（已请管理员协调）”。
   - 内容规则不变：标题、简述按开关显示，正文不发。
   - 时长取工作空间当前的设置；投递前被改成 0 时，不写具体小时数，写“已等待接单较长时间”。
6. **会话钩子提醒：带上了**。两档都给当事人写一条会话内提醒，新种类 `overdue`，钩子显示“#N 等你处理已超时，请尽快处理”。
   - 理由：催办针对的就是当事人，他多半正开着编程工具；工作空间没配群时，这是唯一的催办渠道。
   - 管理员不写会话内提醒，他们在群里被 @ 就够了。
   - 旧版本的 `cohive` 命令行不认识这个种类，会显示成“#N 有新动态”，不报错。
7. **设置入口**
   - 网页“管理 → 工作空间 → 超时催办”两个输入框，前端校验 0 到 720。
   - 命令行 `cohive-server workspace set --name <路径> --remind-open-hours N --remind-verify-hours N`。
   - 两处修改都写“修改工作空间设置”的管理操作记录，记录里会写明改了“待接单催办时长”“待验证催办时长”。

## 迁移在测试服库上是否安全

**安全**：只加带常量默认值的列（PostgreSQL 11 起不重写表）、一个部分索引、两个检查约束（默认值都满足）。没有改写现有数据。

现有问题单的计时从**升级时刻**开始，不拿历史时间补算。因此测试服升级后，最早要过 4 小时（待验证 24 小时）才会出现第一条催办，不会一下子冒出一批。

## 与派活要求的出入

1. **“当事人一换就重新计时”是我补的**：细则只写“状态一变就停止计时”。转交、改派后要动手的人变了，沿用前一个人的等待时间去催新人不合理，所以重新计时。如果要严格只按状态，从 `store.UpdateIssue` 和 `store.SetIssueSource` 里去掉换人的条件即可。
2. **没配群时也计时、也写会话内提醒，档位照走**：这样以后再配群，不会把积压的单子一下子全催一遍。
3. **待验证时管理员改派了发起人，已经写入但还没发出的那条催办仍会发给原发起人**：现有的过时判断只核对状态和负责人，不核对发起人。概率很低（要在写入到发出之间的几秒内改派），没有为此给待发通知表加列。如需要，可以加一列发起人快照。
4. **时长单位是整数小时**，最长 720 小时（30 天）。如果需要半小时这类粒度，要改成分钟存储。

## N-3：群通知不 @ 操作者本人（2026-10-18 lee 定选 B，随 N-2 交回）

**规则**：所有群通知里，操作者本人只写名字、不 @。去掉本人后一个都 @ 不到时照常发消息，只写名字。

**做法**（`internal/notify/render.go`）：渲染时拿通知记录里的操作者编号比对收件人，是操作者就只写名字，也不放进钉钉卡片的 atUserIds。Telegram 和钉钉都覆盖。具体效果：
- 自己发单给自己（发出时 @ 的负责人就是自己）、自己接自己的单、自己验证关闭：只写名字。
- 发起人和负责人是同一人：上一条的各种情况都只写名字。
- 多次重开升级为“需要人介入”：重开的发起人是操作者，不 @；负责人照常 @。
- **超时催办没有操作者**：通知记录里的操作人只是占位，写的是当事人，所以照常 @ 当事人。第 2 档 @ 管理员时，当事人本身是管理员只列一次（N-2 已去重），也就是只 @ 一次。
- **加入通知**原来只有一种，接口里不带操作者，所以拆成两种（`Announcer` 新增 `AnnounceSelfJoined`）：
  - 管理员让人加入（直接加入、批准申请）：照常 @ 新成员；
  - 本人凭个人邀请注册、已有账号接受邀请：操作者是他自己，只写名字。

**改了哪些文件**
- `internal/core/notify.go`：`SystemEvent`，判断是不是没有操作者的催办
- `internal/notify/render.go`
- `internal/notify/hub.go`、`internal/notify/bot.go`：两种加入通知
- `internal/httpapi/public.go`、`internal/httpapi/account.go`：注册、接受邀请这两处改调 `AnnounceSelfJoined`，各一行，外加接口里一个方法
- 用例：`internal/notify/render_test.go`、`internal/notify/hub_test.go`、`internal/server/account_test.go`（假通知器加方法与计数）
- 文档：`docs/guides/group-notify.md`（“怎么 @ 到人”）、`docs/plan.md` 5.3

**用例**
- `TestNoSelfMention`：自己发单、接单、关单、请验证都不 @；需要人介入只 @ 另一方；钉钉 atUserIds 不含操作者；催办照常 @（Telegram、钉钉各一）。
- `TestSelfJoinedNoMention`：管理员让人加入 @，本人加入不 @。
