## 需要你拍板或知悉的取舍

1. **归档时有未结束的单子：选“提示数量并确认”，不选“先处理完”。**
   - 归档可以撤销。如果硬性要求先处理完，管理员为了归档会去批量作废单子，反而污染协作记录。
   - 确认不用勾选布尔值，而是把数量带上：接口参数 `confirm_open` 必须等于当前的未结束数。如果在确认后又有人发了单，数量对不上，返回 409（`open_issues_unconfirmed`，附实际数），网页刷新数字后要求重新勾选。
   - “未结束”的口径：不是草稿，且不是已关闭、已退回、已作废。
2. **草稿在彻底删除时一并删除，不算未结束。**
   - 草稿从没进入过协作，别人也看不到。
   - 归档后草稿不能删。如果把草稿算作未结束，就得先取消归档、删掉草稿、再归档，流程绕。
   - 删了几张草稿记在管理记录的详情里（`drafts`）。
3. **现有的“删除空工作空间”保持不变**：接口 `DELETE /api/v1/server/workspaces/{name}` 和命令行 `workspace remove` 都没改。网页的服务器管理页把原来的“删除”按钮统一换成“彻底删除”对话框，要输入路径确认，空工作空间也走这个对话框。
4. **只能在网页上归档，命令行不做归档。** 命令行进程不带机器人，归档时没法在群里发告知。业务层的归档入口如果没有操作人账号会直接拒绝。
5. **吊销类操作在归档后仍然允许**：吊销令牌、吊销设备、作废邀请。收回权限的操作任何时候都要能做。其余写操作一律返回 `workspace_archived`。
6. **取消归档时，催办重新计时。** 待接单、待验证的单子从取消归档那一刻开始计时，免得一恢复群里就冒出一批积压的催办。归档期间跳过的群通知不补发。
7. **邀请链接页没改。** 已归档工作空间的邀请链接打开后仍显示有效，到注册或接受邀请时才返回 409。要不要在打开链接时就提示，另议。
8. **网页只读横幅的缺口。** 服务器管理员如果不是这个工作空间的成员，看不到“已归档、只读”的横幅（横幅读的是“我”的成员列表）。写操作照样会被后端拒绝；归档状态在管理页和服务器管理页都看得到。

## 做了什么

**数据库**
- 新增迁移 `0015_workspace_archive.sql`：`workspaces` 表加 `archived_at`、`archived_by` 两列。
- **测试服库上执行是安全的**：只加可空、无默认值的列，PostgreSQL 不重写表，有数据的库也能直接执行。

**只读守卫**
- 只读守卫是 `core.writable`，对工作空间行加共享锁（FOR SHARE）读取，放在每个写操作事务里最先加锁的位置，与彻底删除的排他锁互斥，避免死锁。
- 后面还要锁工作空间行的写操作（改设置、改显示名、改语言、改催办、绑定或解除群）改用排他版 `lockWritable`，避免共享锁升级排他锁时互相等待。
- 覆盖的写操作：发单、各种动作（含留言）、作废、删除草稿、改设置、建邀请、审批加入、加成员、改角色、交接、登记服务、签发令牌、群绑定、凭邀请注册和接受邀请、设备审批。
- 设备补签令牌时跳过已归档的工作空间，不报错。命令行 `cohive login` 和 `cohive init` 也跳过已归档的。

**归档 / 取消归档**
- 接口：`POST /api/v1/w/{ws}/admin/archive`（请求体 `{confirm_open}`）、`POST .../unarchive`。只认密码登录的网页会话；工作空间管理员和服务器管理员都能操作。
- 每次操作记一条管理记录：“归档了工作空间 X（当时有 N 张未结束的问题单）”或“取消归档了工作空间 X”。
- 归档的同一事务里，把这个工作空间排队待发的群通知标为不再发送。派发器遇到已归档工作空间的通知也会跳过，作为兜底。
- 归档后跳过催办，会话提醒和收件箱返回空。
- `/me` 返回的工作空间列表多了 `archived` 字段，网页的切换器和默认工作空间都会跳过已归档的。

**群里告知**
- 归档后在绑定的群里发一条：“工作空间 X 已被 Y 归档，现在只能查看，之后不再在本群发通知；取消归档后恢复。”取消归档后再发一条“群通知恢复”。
- 用工作空间的语言发。

**彻底删除**
- 接口：`POST /api/v1/server/workspaces/{name}/purge`，请求体 `{confirm}`，只认密码登录的网页会话。
- 命令行：`cohive-server workspace purge --name X --confirm X`。
- 只限服务器管理员（否则 403）。确认的名字不一致返回 400（`purge_confirm_mismatch`）；还有未结束的单子返回 409。
- 删除范围：问题单（含草稿）、动态、幂等记录、会话提醒、群通知，再加上原来删除空工作空间时就会删的东西。
- `admin_events` 不删，并新增一条“彻底删除了工作空间 X（含 N 张问题单）”，详情里带上草稿数。

**网页**
- 工作空间管理页新增“归档”一栏：有未结束的单子时，必须勾选“还有 N 张未结束”才能提交；已归档时设置表单变为只读。
- 服务器管理页：工作空间列表可以按“全部 / 使用中 / 已归档”筛选。“彻底删除”对话框要输入完全一致的路径才能提交；还有未结束的单子时按钮禁用并说明原因。
- 工作空间内各页面在已归档时显示只读横幅，“作废”和“删除草稿”按钮禁用。

**其他**
- 接口返回的错误码：`workspace_archived`（MCP 报错里也带上）、`open_issues_unconfirmed`、`purge_confirm_mismatch`，已登记在 `httpapi.go` 的错误码表里。
- 文案中英齐全。`docs/guides/group-notify*.md` 加了“归档与彻底删除”一节。

**全量测试**
- 用自建走查库 `cohive_ws1`。
- `go vet ./...` 通过。
- `go test ./...` 全部 22 个包通过。

- 关于网页测试的不稳定：网页子代理在后端测试同时运行时观察到 2 到 7 个网页用例偶发超时。我自己第一次跑 `make build` 时，变异验证正在并行跑测试，网页测试那一步也失败了，但没留下逐条记录，推测是同一原因。机器空闲时重跑全过。这是机器负载问题，不是逻辑问题。

**观察**
- 探针 5 不是被测试里的断言抓住的，而是数据库层的“管理记录只能追加”触发器直接拒绝了删除。这一层保护比测试断言更硬。如果以后去掉这个触发器，需要补一条“彻底删除后管理记录仍在”的断言测试。
- 会话提醒、收件箱、待发跳过这几项都只靠同一个 core 测试保护，HTTP 层测试没有覆盖到。
