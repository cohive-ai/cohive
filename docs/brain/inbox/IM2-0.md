# IM2-0 交回：机器人收件处理抽成与平台无关的一层

## 结论

- 分支：`feature/im2-0-inbound`（从 `origin/main` 1707b5b 开出），已推送，未合入、未动 main，没碰测试服。
- 只改了 `internal/notify` 一个包，没碰 `cmd/cohive`、`internal/skill`、`internal/client`。
- 行为不变：Telegram、钉钉的现有用例全部原样通过；中英文案仍走 `internal/i18n`，没有增删文案键。
- 检查结果：`go vet ./...` 通过；`go test ./...` 全部通过（真实 Postgres，localhost:55432）；`make build` 成功；变异验证 12 个探针全部被拦住，见文末。
- **纠正一处调研结论**：调研报告 5.1 写“表结构不用迁移”，这是错的。`chat_identities`、`workspace_chats` 的 `provider` 列和审计记录的 `via` 列都有取值约束，只允许 telegram、dingtalk（见迁移 0011）。接 Slack 时要加一个小迁移把约束放开。详见“接 Slack 时还要动的地方”。

## 做了什么

1. **新增 `internal/notify/inbox.go`：与平台无关的收件处理**
   - `Inbound`：统一的收件消息，包括通讯工具、群编号、群名、是否私聊、发送者，以及拆好的指令词和参数。除指令外，其余字段都由平台填写。
   - `InboxCaps`：每种通讯工具的三个能力开关：
     - 私聊发码连接账号（`LinkByCode`）；
     - 群里发码绑群（`BindByCode`）；
     - 认不出的消息回用法（`Help`）。
   - `CodeCore`：绑定码的两个业务操作，由原来的 `DingTalkCore` 改名而来，签名不变，仍由 `core.Service` 实现。
   - `Inbox.Handle` 负责四件事：认指令（中英文写法都认）、选回复语言（群里按群所属工作空间，私聊按对方账号，查不到用服务器缺省语言）、调用业务层、把业务错误和内部错误分开。返回的 `Reply` 与格式无关：它只说明回复的种类和要用的数据，比如账号名、工作空间名、角色、错误文字。
   - `parseText`：把“@机器人 加文字”拆成指令，从钉钉通道搬来，以后飞书、Slack 可以直接用。
2. **钉钉**：`handleBot` 只剩两步：把钉钉消息翻译成 `Inbound`，再用 `dtReplyText` 按钉钉的文案和 Markdown 写出回复。原来的 `command`、`who`、`whoami`、`replyLang`、`userErr` 都删掉了，逻辑已进 `Inbox`。钉钉的三个能力开关全开。
3. **Telegram**：`/chatid`、`/whoami` 改成经同一层处理。`tgInbound` 只把这两个命令转进来，`tgReplyText` 按 Telegram 的文案和 HTML 写出回复。原来的 `whoamiExtra` 删掉了，导出的 `HandleCommand` 保留，现在是对新层的简单包装（测试在用）。Telegram 的三个能力开关全关。
4. **`channel.go`**：新增可选接口 `StatusReporter`，表示收件循环是否在线、不在线的原因；Telegram 和钉钉本来就实现了它。另加编译期断言，确认两者都实现了 `Channel` 和 `StatusReporter`。
5. **测试**
   - 新增 `inbox_test.go`：用一个假想的新通讯工具（provider 为 example）直接测 `Inbox`，覆盖以下几类：
     - 私聊发码，以及失效、内部错误两种情况；
     - 群里出现账号绑定码时作废，或改按群绑定码处理；
     - “绑定群”，绑定后按工作空间的语言回复；
     - 能力开关；
     - “我是谁”和“群编号”。
   - `bot_test.go`：补了 Telegram 不回应的写法，包括 `/群编号`、`/我是谁`、`/bindgroup`、裸码、`/ChatID`。
   - `i18n_en_test.go`：补了钉钉私聊里问“群编号”时回私聊用法。

## Telegram 没并进来的部分和原因

- **`/start ln_xxx`（带参数的机器人链接连接账号）**：这是 Telegram 独有的连接方式，打开链接立即连接，不经网页确认，走的是 `CompleteTelegramLink`。新平台都没有带参数的链接，用的是私聊发码，两者没有共用逻辑，所以留在 `bot.go` 的 `handleStart`。
- **命令解析**：Telegram 的解析规则留在它自己的 `tgInbound` 里：命令必须以 / 开头，带 @机器人名时要核对名字，大小写敏感，只认两个命令。如果改用 `parseText`，Telegram 会开始认中文指令和不带 / 的词，行为就变了。
- **文案**：仍然分成 `notify.tg.*` 和 `notify.dingtalk.*` 两组，没有合并。两组文案里写死了各自的格式（Telegram 是 HTML，钉钉是 Markdown）和平台名称（“连接 Telegram”“连接钉钉”）；Telegram 的“我是谁”还会先说用户名和编号。合并就得改现有文案，违反“行为不变”。新平台加自己的一组文案键，在各自的 `xxReplyText` 里对应过去，一共七八个键。
- **审批按钮**：本来就已经共用 `Hub.Click`，这次没动。

## 细微差异（用户看不到）

- 收件处理遇到内部错误时，日志从 `DingTalk bot failed to handle …` 变成 `dingtalk bot failed to handle …`，开头改用通讯工具的编号。只影响日志。
- 钉钉群里出现账号绑定码时，“已作废”这句提示现在也会经过钉钉的转义。这句中英文里都没有会被转义的字符，输出完全一样。
- Telegram 有业务层、但消息没有发送者时（平台上极少见），`/whoami` 会多查一次账号，回复照旧为空。

## 接 Slack 时怎么用这一层

1. 实现 `Channel`，把收件循环的在线状态接到 `StatusReporter`。
2. 把收到的 @机器人消息、私聊消息、斜杠命令翻译成 `Inbound`。文字消息用 `parseText` 拆，斜杠命令直接填 `Cmd` 和 `Args`。
3. 每收到一条消息，调用 `Inbox{Hub, Codes: svc, Caps: 三个开关全开, Logf}.Handle`。
4. 写 `slackReplyText`，用 `notify.slack.*` 文案键加 mrkdwn，按 `Reply.Kind` 写出回复。

## 接 Slack 时还要动的地方（本次没动，不在 notify 包里）

| 位置 | 现状 | 要改成 |
|---|---|---|
| 迁移 0011 的 `chat_identities.provider`、`workspace_chats.provider` 取值约束 | 只允许 telegram、dingtalk | 新迁移放开，加 slack（以后加飞书、Lark、Discord 时也一样） |
| 审计记录 `admin_events.via` 取值约束 | 只允许 web、telegram、dingtalk 等 | 同上 |
| `store` 的 provider 常量、`core` 里的同名常量 | 只有两个 | 加 slack |
| `core.StartLink` | 按 provider 分支，钉钉生成绑定码 | slack 也走绑定码分支 |
| `core.StartChatBind`、`core.BindChat` | 只认钉钉（错误键 `core.err.bind_by_code_dingtalk_only`） | 改成“用码绑群的通讯工具”这一类 |
| 审计动作 `ActDingTalkLink` / `ActDingTalkUnlink`、`audit.go` 里按 provider 的分支、`providerKey`、`notify.providerLabel` | 按通讯工具枚举 | 各加 slack |
| `httpapi` 的 `providerEnabled` 判断、`server.go` 里的 `dtLinked` | 写死钉钉 | 按通讯工具泛化 |

这些都是枚举式的小改动。建议在 Slack 那一步里一次改完，并顺手把“用码绑定的通讯工具”收成一个判断函数，免得每接一个平台都改一遍。
