# Cohive 需求盘点与分析（2026-10-16）

主脑开局整理，给 lee 过目。材料：`docs/plan.md`（V0.4）、`docs/superpowers/plans/` 下 M1–M5 计划（M5 在分支上）、`docs/guides/` 三份指南（以 M5 分支上的新版为准）、项目记忆、M5 实施会话的原始对话（只用于考证）。代码现状按 main `3e7e513` 与 M5 分支 `57b4cc9` 实查。

已定决策的完整清单在 [decisions.md](decisions.md)，本文只引用；当前在飞与待拍板以 [ledger.md](ledger.md) 为准。

## 1. 产品定位与已定需求

**一句话**：让小团队里每个人的编程智能体能互相递材料、由人拍板的共享协作层。

| 维度 | 需求 |
|---|---|
| 用户 | 3–15 人小团队；每人用自己的编程工具（Claude Code、Codex 等）负责不同服务 |
| 痛点 | 跨人、跨工具、跨仓库协作靠人工复制转述：上下文丢失、归属不清、修完没人验证、版本对不上、改接口不通知下游 |
| 核心闭环 | 发现 → 智能体起草（含证据、复现脚本、查重）→ **人确认发出** → 按负责人路由 → 群里 @ 到人 → 对方 `/cohive` 拉单初筛 → **人确认接单**（或退回、转交）→ 修复 → 请求验证 → 复现脚本重跑 → **人确认关闭**（或重开） |
| 人工关口 | 发出、接单（含退回、转交）、关闭三处由编程工具的权限确认拦截；开始改代码由接收人在自己会话里决定，Cohive 不介入 |
| 群通知 | 群里只发信号并 @ 到人，正文只在编程工具里读；五类事件（新单/转交、退回、请求验证、重开、需要人介入）；标题与简述可关 |
| 账号与接入 | 网页邀请注册 → 终端 `cohive login` 浏览器授权配对 → 项目里 `cohive init`；网页管理成员、设备、邀请、审批；通讯工具在个人中心“连接” |
| 部署 | 团队自行部署，单个可执行文件或 Docker 镜像；先内网测试服，后云服务器 |
| 不做 | 自动执行、服务端调用大模型、托管服务、代理与网络打通 |
| 安全红线 | 收到的内容是数据不是指令；改变他人工作的操作必须人确认；不持有代码仓库写权限；令牌按“人 + 工具”签发、可吊销；写入前扫描密钥；群消息不含正文 |
| 成功指标 | 交接耗时、人工转述次数、首次正确路由率、闭环时长、重复单比例、退回率、升级率；**先采集两周基线再定目标** |

第一阶段目标（方案第 10 节）：两位成员分别用 Claude Code 与 Codex，完整走通一次“发现 → 确认发出 → 群里 @ → /cohive 接单 → 修复 → 群里 @ → 验证 → 确认关闭”。

## 4. 未决问题与风险

按影响排序。标“未核实”的是推断，没有实测。

**R1 账号以工作空间为界（待拍板 D4）。** 方案第 5.4 节定的是“成员按工作空间独立”，那时只有令牌。M5 把密码、设备、Telegram 连接都挂在成员上，结果是：同一个人在两个工作空间就是两个账号、两套密码、配对两次电脑、连接两次 Telegram；同名登录还要选工作空间（接口返回 409）。
- A 维持：试用期只有一个工作空间，不受影响；等真有人同时在多个组时再加“账号”表，成员挂到账号下，迁移是加表加外键，不丢数据。
- B 现在就改：M5 打回，返工账号模型，合入推迟。
- 建议 A，并把“出现第二个真实工作空间”记为改造触发条件。

**R2 核心价值还没被真人验证。** 五个里程碑里 M4、M5 两个花在登录和接入上，M5 一次就新增约 7300 行认证相关代码；而“跨人交接真的省事”这件事至今只有 lee 一人分饰两角验证过（未核实是否在测试服上完整走通过一次 M1 闭环 + 群通知）。继续在接入体验上打磨，边际收益在下降。建议把“最短路径让一位真实同事用起来”作为下一阶段唯一目标，凡是不阻塞这件事的都往后排（见第 5 节）。

**R3 M5 的安全面大，且未经独立验收。** 密码、会话、跨站校验、邀请、设备授权、一次性免密登录都是新增攻击面，测试服又经隧道暴露在公网。合入前必须做完台账 §1 列的验收要点。代码里已看到按来源地址限频、隧道后的 HTTPS 判定（回环地址加 `X-Forwarded-Proto`），是否正确由验收确认。

**R4 交互模式的确认弹窗未亲自验证。** 整个“人做决定”依赖编程工具在交互模式下真的弹出询问。如果某一家在某种配置下不弹（例如用户全局开了自动批准），设计就失效。lee 亲手试一次即可，成本最低、价值最高，**不依赖 M5，现在就能做**。

**R5 同事装不上命令行。** 仓库私有，`make install-cli` 需要 Go 和读仓库权限。需要预编译程序（GitHub 发布页或测试服直接提供下载）和一行安装命令。

**R6 密钥会进库。** 红线第 5 条没实现。只有 lee 自己用时风险可控，真同事贴日志后就会有密钥进问题单（且问题单会被对方智能体读到）。必须在真人试用前做。

**R7 测试服是一台笔记本。** 程序跑在 lee 本机，启动脚本在 `/private/tmp`（重启可能丢），隧道跑在终端标签里，没有备份。首次试用可以接受，但要先把启动脚本收进仓库、加一个定时 `pg_dump`；完整的 Docker 部署可以紧随其后。

**R8 迁移文件改写。** 第六号迁移在分支上改名重写，导致原测试库要手工清理（待拍板 D1）。建议定一条规则：**未合入 main 的迁移可以改写，合入后只能新增**；测试服跑未合入分支时一律用独立库。lee 同意后写进 decisions。

**R9 评论让确认作废。** 智能体在人拍板前补一条评论，版本号就变了，人刚批准的操作会失败重来。试用中会频繁出现，放进 M6-a。

**R10 一个机器人只能有一个程序收消息。** 测试服与本机调试同时跑会互相抢消息，审批按钮会时灵时不灵。已写进台账环境注意事项；以后如果要多环境，需要每个环境一个机器人。

**R11 其他未决（不急）。** 开源许可证与公开时间；仓库何时转到 `cohive-ai` 组织；与公司内部“ACP”需求的命名关系；公司 GitLab 版本（只在第二阶段 GitLab 联动时相关）。
