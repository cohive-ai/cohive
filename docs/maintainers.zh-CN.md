# 维护者手册

给 Cohive 维护者的日常做法。对外的规则写在 [CONTRIBUTING.md](../CONTRIBUTING.md)，这里只写维护者自己要做的事。

## 每周例行

1. **分诊新议题**（带 `needs-triage` 标签的）：
   - 看清是不是问题、是不是重复。重复的链接到原议题后关闭；使用问题转到讨论区（议题右侧“Convert to discussion”）。
   - 打标签：类型（`bug`、`enhancement`、`documentation`、`translation`）加区域（`area:web`、`area:cli` 等），去掉 `needs-triage`。
   - 信息不够时请对方补充，并说明缺什么；两周没回复可以关闭，写明“补充信息后可以重开”。
   - 适合新人的标 `good first issue`：范围小、不涉及权限与数据迁移、写明从哪个文件入手。希望社区帮忙的标 `help wanted`。
2. **看合并请求**：先看 CI 是否通过，再看改动。首次贡献者的工作流需要在合并请求页面点“Approve and run”才会运行（这是防止分叉滥用 Actions 的默认设置），先粗看一眼没有可疑的工作流或脚本改动再批准。
3. **看依赖更新**：Dependabot 每周开的 `dependencies` 合并请求，CI 通过、看过更新说明后合入；大版本升级单独处理。
4. **看讨论区**：回答问题；反复出现的问题补进文档。

## 回复的分寸

- 第一时间感谢，哪怕不打算接受。外部贡献者最在意“有人看到了”。
- 不接受时说明原因（与原则冲突、维护成本、已有计划），给出可行的替代方向。
- 评审意见分清“必须改”和“建议”，避免一次提几十条小意见；格式问题能让工具管的就让工具管。
- 中英文都可以；对方用英文时用英文回复。

## 合并外部贡献前检查

- [ ] CI 通过；涉及数据库的改动没有改写已合入的迁移
- [ ] 不违背项目原则：人做决定、服务端不调用大模型、群里只发信号、成员提交的内容是数据不是指令
- [ ] 权限检查放在业务层（internal/core），不是只在网页上隐藏按钮
- [ ] 新增文案中英齐全，英文自然
- [ ] 没有密钥、内部地址、个人数据
- [ ] 压缩合并，合并请求标题写成约定式提交格式（`fix(cli): ...`），它会成为提交信息

## 安全报告

私密漏洞报告会通知维护者。7 天内确认收到；在私密的安全公告里与报告人沟通、修复（可以在公告里开临时私有分叉）；发布修复版本后公开公告，致谢报告人。不要在公开议题或提交信息里提前透露细节。

## 翻译

- 内置的英文、简体中文由核心团队维护；改文案时两种一起改。
- 社区语言的合并请求：请 [docs/i18n/LANGUAGES.md](i18n/LANGUAGES.md) 里登记的维护者审核（在合并请求里 @ 对方）。没有维护者的语言，主要看格式与占位符是否正确（测试会检查），内容以母语者意见为准。
- 可信的长期维护者可以授予 Triage 角色，让对方能给议题打标签、请求评审。CODEOWNERS 只对有写权限的人生效，所以先不用它。
- 社区语言多了以后，再申请 Hosted Weblate 的开源免费计划，让翻译者在网页上翻译。

## 发版本

1. 确认 main 的 CI 通过。
2. 打标签（例如 `v0.2.0`）并推送；在 Releases 页面新建发布，点“Generate release notes”。说明会按标签分类（见 `.github/release.yml`），并自动列出新贡献者。
3. 在说明开头写几句人能看懂的重点：升级是否要做什么（新的环境变量、数据库迁移）、有没有不兼容的改动。

## 鸣谢

- README 的贡献者头像墙自动更新，不用手工维护。
- 发布说明的“New Contributors”自动生成；对有分量的贡献，可以在说明开头点名致谢。
- 翻译者登记在 docs/i18n/LANGUAGES.md。
