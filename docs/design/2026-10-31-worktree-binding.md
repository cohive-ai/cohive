- 编号：WT-1

---

## 1. 现状与根因

### 1.1 现在怎么接入

`cohive init`（`cmd/cohive/init.go`、`cmd/cohive/init_opencode.go`）在**执行它的那个目录**里写下面这些文件，服务地址与工作空间名以命令行参数的形式写死在里面：

| 工具 | 写入的文件 | 写进去的绑定 |
| --- | --- | --- |
| Claude Code | `.mcp.json`（`mcpServers.cohive`）、`.claude/settings.json`（确认规则、`enabledMcpjsonServers`、`hooks` 里会话开始与提交提示词各一组）、`.claude/skills/cohive/SKILL.md` | `cohive mcp-proxy --server … --workspace … --tool claude-code`；钩子命令 `cohive hook --server … --workspace … --tool claude-code` |
| Codex | `.codex/config.toml` 里一段 `# >>> cohive … # <<< cohive`（MCP、按工具确认、两条钩子）、`.agents/skills/cohive/SKILL.md` | 同上，`--tool codex` |
| opencode | `opencode.json`（`mcp.cohive`、`permission`）、`.opencode/plugins/cohive.ts`（每次提示词调 `cohive hook`）、共用 `.agents/skills/cohive/SKILL.md` | 同上，`--tool opencode`；参数列表嵌在插件源码里 |

运行时：

- `cohive mcp-proxy`（`cmd/cohive/proxy.go`）**只认命令行参数**：缺 `--server`、`--workspace`、`--tool` 任一项直接报错退出。令牌按（服务, 工作空间, 工具）从 `~/.config/cohive/credentials.json` 取，没有时用设备密钥现签。
- `cohive hook`（`cmd/cohive/hook.go`）也**只认命令行参数**：缺参数时静默退出；整个钩子 2 秒封顶，网络请求 1.5 秒，同一会话 20 秒内最多联网一次，游标存在用户缓存目录。
- `cohive login` 的 `findRepoDir` 会从当前目录往上找含 cohive 条目的配置文件，遇到 `.git` 停止——这是现在唯一“从目录推断绑定”的地方，而且推断的依据仍是项目里的配置文件。

### 1.2 根因

**工作空间绑定和“这个目录里有没有那几份文件”是同一件事。** 绑定没有独立存放的地方，只能跟着文件走，所以：

1. **文件提交进仓库**（产品原本的默认做法，新成员指南第 150 行“可以放心提交进仓库，团队共用”）：工作树、新克隆都有，没问题。
2. **文件不提交**：任何新的检出目录都拿不到——Claude Code 的工作树、Codex 的工作树、手动 `git worktree add`、同一仓库的第二个克隆都一样。

需要更正一点：`cohive init` **本身不写** `.git/info/exclude`。本仓库把这三项放进 `.git/info/exclude`，是自用时手工做的（主脑台账 2026-10-18 一条有记录）。但“不提交”恰恰是开源之后很常见的情形，不是个例：

- **给别人的仓库干活**：团队用 Cohive 协作，但仓库是上游开源项目或客户的仓库，不能往里提交自己团队的服务地址和工作空间名。
- **公开仓库自用**：像 Cohive 自己，服务地址与工作空间名属于团队内部信息，不该进公开仓库。
- **同一仓库多个团队**：两个团队用不同工作空间，提交的那份只能是其中一个。
- **个人习惯**：不想让协作工具的配置混进仓库的人。

还有两处不提交以外的毛病，同一个根因：

- **非 git 目录**（例如一个放脚本的文件夹）：每个目录都要单独执行一次 `init`，子目录里打开编程工具也找不到上层的配置（Claude Code 读的是会话启动目录的 `.mcp.json`）。
- **换服务地址或工作空间**要改仓库里的文件；Codex 的钩子信任按条目内容算哈希，改了就要每人每个克隆重新信任一次。

### 1.3 第 0 步实测（2026-10-31，桌面应用新建工作树）

主检出目录放了本机的 `.worktreeinclude`（`.mcp.json`、`.claude/settings.json`、`.claude/skills/` 三行，自身未提交），然后由桌面应用新建工作树会话：

| 检查项 | 结果 |
| --- | --- |
| 工作树根目录 `.mcp.json` | 存在，内容与主检出一致（cohive 条目，`--tool claude-code`） |
| 工作树 `.claude/settings.json` | 存在，含确认规则、`enabledMcpjsonServers`、两组 `cohive hook` 钩子 |
| 工作树 `.claude/skills/cohive/SKILL.md` | 存在 |
| `/cohive` 技能 | 会话技能列表里有 |
| `mcp__cohive__*` 工具 | 有；调用 `cohive_inbox` 成功，返回空列表 |
| `cohive hook --check` | 找到登录，服务可用（338 毫秒），待处理 0 张 |

结论：**桌面应用新建工作树时会按 `.worktreeinclude` 复制被 git 忽略的文件**，短期方案可用。

附带发现（对方案乙有用）：这次工作树会话里的 `cohive mcp-proxy` 进程，**当前目录是主检出目录**，环境变量 `CLAUDE_PROJECT_DIR` 也指向主检出目录，而不是工作树。也就是说，桌面应用的工作树会话里，转发器“站在哪”不一定是会话所在的工作树。所以上表“工具可用”不能证明读的是工作树里那份 `.mcp.json`，也可能是主检出的那份；能确定的只有“文件复制过来了”。这也说明：运行时按目录识别绑定时，**必须用两处目录都相同的键**——`git rev-parse --git-common-dir`（主检出与所有工作树相同），不能用工作树自己的路径。

## 2. 方案比较

### 2.1 方案甲：`init` 顺带写复制清单

`cohive init` 在写完配置后，把自己写的那几个文件追加进复制清单：

- Claude Code：仓库根的 `.worktreeinclude`（gitignore 语法，只复制“既被清单匹配、又被 git 忽略”的文件）。桌面应用与 `claude --worktree` 都认（桌面应用第 0 步已实测）。
- Codex：没有对应的复制清单。Codex 桌面应用的工作树有“本地环境”的初始化脚本，可以在里面写复制命令，但格式与是否可由 `init` 生成**需实测**。
- opencode：没有工作树功能，也没有复制清单。

实现量：约半天（写清单、去重、已有清单不破坏、测试）。

### 2.2 方案乙：绑定挪到仓库层面，配置装到用户级

把“这个目录属于哪个工作空间”从项目文件里拿出来，存到本机：

- **绑定表**：`~/.config/cohive/bindings.json`（跟凭据文件同一目录，`COHIVE_CONFIG_DIR` 可覆盖）。键是仓库的公共 git 目录（`git rev-parse --git-common-dir` 解析成真实绝对路径），值是服务地址与工作空间名。主检出、它的所有工作树（不论谁建的）键都相同。非 git 目录以目录真实路径为键，对它的子目录同样生效（取最长前缀）。
- **用户级配置**：三种工具的 MCP 条目、确认规则、钩子、技能都装到用户级，**命令里不带服务地址和工作空间**：`cohive mcp-proxy --tool claude-code`、`cohive hook --tool claude-code`。
- **运行时识别**：转发器和钩子启动时自己找到所在仓库，查绑定表。
  - 钩子：优先用编程工具传进标准输入的 `cwd` 字段，其次用进程当前目录。
  - 转发器：用进程当前目录；Claude Code 下再参考 `CLAUDE_PROJECT_DIR`。第 1.3 节已实测桌面应用里这两者都是主检出目录，用公共 git 目录做键正好对得上。
- **没绑定时**：钩子立刻静默退出；转发器照常启动，工具列表里只露一个说明工具，调用时返回“本项目未绑定 Cohive 工作空间，请在项目目录执行 cohive init”（复用现有 `Proxy.Unavailable` 机制）。
- **兼容**：命令行带了 `--server`、`--workspace` 时照旧以参数为准。已提交进仓库的旧配置继续可用。

#### 识别仓库不调 git 命令

钩子每次提交提示词都要跑，不能每次起一个 `git` 子进程。做法是只读文件：从起点目录往上找 `.git`；是目录就是公共 git 目录；是文件（工作树、子模块）就读里面的 `gitdir:`，再读那个目录下的 `commondir` 得到公共目录。全部是几次 `stat` 和小文件读取，毫秒以内。只在遇到 `GIT_DIR` 环境变量之类的少见情况时才退回执行 `git rev-parse`，并给它 300 毫秒上限。

### 2.3 三种工具逐项对比

配置位置：

| 工具 | 方案甲：放在哪 | 方案乙：放在哪 |
| --- | --- | --- |
| Claude Code | 项目内同现状，另加 `.worktreeinclude` | MCP：用户级（`claude mcp add-json --scope user` 写进 `~/.claude.json`，不手工改这个文件，它由 Claude Code 频繁改写）；确认规则与钩子：`~/.claude/settings.json`；技能：`~/.claude/skills/cohive/SKILL.md` |
| Codex | 项目内同现状；复制清单无现成机制 | `~/.codex/config.toml` 里同样的 `# >>> cohive` 段（MCP、按工具确认、钩子）；技能：用户级技能目录（`~/.agents/skills/cohive/`，**需实测** Codex 是否读用户级的这个目录） |
| opencode | 项目内同现状；无复制清单 | `~/.config/opencode/opencode.json`（`mcp`、`permission`）；插件：`~/.config/opencode/plugins/cohive.ts`；技能：用户级技能目录（**需实测** opencode 读哪几个用户级目录） |

能否覆盖：

| 场景 | 方案甲 | 方案乙 |
| --- | --- | --- |
| Claude Code 工作树（桌面应用、`claude --worktree`） | 能（已实测）；但只是建树那一刻的快照，之后在主检出重新 `init` 不会同步到已有工作树 | 能，且不依赖复制；主检出改绑定，所有工作树下次启动即生效 |
| Codex 工作树 | 钩子能：Codex 在工作树里本来就读**主检出目录**的 `.codex` 钩子配置（M6e 调研，源码 `root_checkout_hooks_folder_for_dir`），主检出有文件即可，不必提交；MCP 与技能能否从主检出读**需实测**，不能则无解 | 能。前提是 Codex 启动转发器时的当前目录在仓库内（**需实测**，Codex 的 MCP 条目支持写 `cwd`，但用户级配置里没法写死） |
| 手动 `git worktree add` | 不能（没有任何工具读复制清单） | 能（公共 git 目录相同） |
| 非 git 目录 | 不能；每个目录各执行一次 `init`，子目录也不行 | 能；按目录前缀绑定，子目录继承 |
| 同一仓库第二个克隆 | 不能 | 要在新克隆执行一次 `cohive init`（公共 git 目录不同）；见 3.4 的改进建议 |
| 不让配置进仓库 | 能（靠忽略 + 复制） | 能（仓库里根本没有文件） |

### 2.4 小结

| | 方案甲 | 方案乙 |
| --- | --- | --- |
| 解决的范围 | 只有 Claude Code 工作树 | 全部场景 |
| 实现量 | 约半天 | 约 4～5 天（含实测与迁移） |
| 仓库里的文件 | 还多一份 `.worktreeinclude` | 一份都没有（团队想共享时可选，见 4.1 第 2 条） |
| Codex 钩子信任 | 每台电脑、每个克隆目录、每次换工作空间都要信任 | 用户级钩子条目固定不变（不含工作空间），信任一次（**需实测**用户级钩子是否也要信任） |
| 主要代价 | 快照会过期；复制清单本身也要忽略或提交 | 所有项目都多出 cohive 工具；运行时多一步识别 |

## 3. 方案乙的风险与对策

### 3.1 所有项目都多出一组工具

用户级 MCP 意味着每个项目、每个会话都启动一个转发器，模型上下文里多出十几个工具说明。

对策：

- **没绑定时只露一个工具**：`tools/list` 只返回一个 `cohive_status`，说明“本项目未绑定，请执行 cohive init”。不发起任何网络请求。上下文开销降到一个工具。
- 转发器在没绑定时不联网、不读令牌，空转成本只是一个闲置进程。
- 技能同理：用户级技能对所有项目可见，但技能说明很短，正文第一步先查绑定，没绑定就告诉用户怎么绑。
- 用户级确认规则（放行只读工具）对未绑定项目无害：调用只会拿到那句说明。
- 不想要的人：`cohive init --project` 走旧的项目级模式；用户级配置可按快速开始文档里列出的路径手工删除。（`cohive uninstall` 首期不做。）

### 3.2 没绑定时钩子的耗时上限

钩子每次提交提示词都执行，所有项目都会执行。

- 目标：没绑定时 **10 毫秒内退出**（找仓库只读文件，读一份几 KB 的绑定表，不联网、不读凭据、不写游标）。
- 硬上限：沿用现在整个钩子 2 秒封顶；退回调用 `git rev-parse` 的少见路径给 300 毫秒。
- 验收要测：没绑定的仓库、非 git 目录、家目录、很深的目录、网络盘上的目录各跑 100 次，看 P99。
- 编程工具外层超时仍是 5 秒，不变。

### 3.3 同一仓库不同目录想绑不同工作空间

例如大仓库里 `services/pay` 归支付团队、`services/risk` 归风控团队。

- 绑定表允许在仓库条目下挂**子目录覆盖**：`{仓库键, 子目录（相对仓库根）, 工作空间}`，按最长前缀匹配。在子目录里执行 `cohive init --here`（名字待定）就记成子目录覆盖。
- 子目录用的是相对路径，所以对所有工作树同样生效。
- **限制**：识别以会话的起点目录为准。第 1.3 节实测桌面应用里转发器的当前目录是主检出根目录，不是会话真正工作的子目录，所以会话从仓库根打开时只会匹配到仓库级绑定。钩子有 `cwd` 字段，能更准一些，但钩子和转发器可能会认成不同的工作空间。首期建议**只做仓库级**，数据结构预留子目录覆盖，等有真实需求再开（4.1 第 5 条）。

### 3.4 一台机器绑多个工作空间

- 凭据文件本来就按（服务, 工作空间, 工具）存多份令牌，转发器按绑定取对应令牌，不需要改。
- 不同仓库绑不同服务（例如公司测试服和个人服）也一样。
- 同一仓库的第二个克隆公共 git 目录不同，要单独绑。改进建议：`init` 时发现另一个克隆（远程地址相同）已经绑过，提示“沿用 X 工作空间？”，用户确认后写入。**不自动沿用**：远程地址是仓库内容可以伪造的，不能让它悄悄决定连哪个工作空间。
- 仓库目录被移走或删除后绑定表里会留下失效条目：`cohive status` 列出并提示清理；`init` 时顺手清掉指向不存在目录的条目。
- 绑定表多个进程同时改：沿用凭据文件“先重读再写、临时文件改名”的做法，另加文件锁。

### 3.5 已安装用户的迁移

目标：**新版本里重新执行一次 `cohive init` 就完成迁移**，不用记别的命令。

`init` 的新流程：

1. **装用户级配置**（三种工具各一份，内容固定，重复执行结果一样）。
2. **记绑定**：本次指定了 `--workspace` 就用它；否则从当前项目里的旧配置读出服务地址和工作空间（复用 `login.go` 的 `readRepoTarget`）；都没有就按现在 `pickTarget` 的规则挑。
3. **处理项目里的旧文件**，先用 git 判断每个文件是否被跟踪：
   - **已提交的**（团队共用）：默认不动，提示“仓库里已有团队共享的 cohive 配置，团队成员都升级后可执行 `cohive init --remove-project-config` 移除”。原因：团队里还有旧版本的人，删了他们就断了。
   - **未提交的**（被忽略或从未添加）：移除 cohive 自己写的部分——`.mcp.json` 的 `cohive` 条目、`settings.json` 里 cohive 的确认规则与钩子组（复用现有 `isCohiveGroup`）、Codex 配置里 `# >>> cohive` 那一段、opencode 插件（认第一行标记）、技能文件（内容是我们生成的才删）。用户自己的其他内容一律不动。删完变成空对象的文件整个删掉。
   - `.git/info/exclude`、`.worktreeinclude` 里的行是用户手工写的，**不改**，只打印提示：可以删掉这几行。
4. **防重复提醒**：迁移期间，同一项目里可能同时有项目级旧钩子（带参数）和用户级新钩子（不带参数），两者都会执行，会提醒两次。规则：**不带参数的钩子发现项目里有带参数的 cohive 钩子配置时直接退出**，让旧的那条处理。MCP 方面，Claude Code 的同名服务器项目级优先于用户级，不会出现两个 `cohive`；Codex、opencode 的同名覆盖规则**需实测**。
5. 旧版转发器、钩子的命令行参数**永久保留**，旧配置一直能用。

## 4. 推荐方案与实施计划

### 4.1 推荐

**推荐方案乙**，以项目级旧模式作为兼容与可选项保留；方案甲**不做进代码**。

理由：

- 方案甲只修 Claude Code 工作树一种情形，而开源后的主流情形（给别人的仓库干活、公开仓库自用、多个工作树工具混用）它都修不了；短期需要的效果，手工放一份 `.worktreeinclude` 已经实测可用，写进快速开始文档即可，不必花代码。
- 方案乙还顺带解决两个老问题：换工作空间不用改仓库文件；Codex 钩子不用每个克隆重新信任（待实测确认）。
- 安全上更好：现在克隆下来的仓库内容可以决定转发器连哪个服务、哪个工作空间（虽然只会用本机已有的凭据）；改成本机绑定后，仓库内容不再参与这个决定。

已定（lee 2026-11-01，6 条全按推荐）：

1. **默认模式**：`init` 默认装用户级配置并记本机绑定；要团队共享项目级文件时加 `--project`（写旧的项目级文件，行为不变）。
2. **`.cohive.toml`**：首期就做，只写服务地址与工作空间名两行，用 `cohive init --share` 在仓库根生成，可提交。**附加条件**：只有本机已经登录过该服务、该工作空间时才生效；没登录过就当没绑定，并提示执行 `cohive init`。这样仓库内容不能再单方面决定转发器连哪个工作空间。优先级：命令行参数 > 本机绑定 > `.cohive.toml` > 项目旧配置。
3. **没绑定时**：工具列表只露出 `cohive_status` 一个工具。
4. **迁移**：自动清理未提交的旧文件里 cohive 写的部分；已提交的不动，只给提示（加 `--remove-project-config` 才移除）。
5. **子目录各绑各的**：首期只做仓库级，绑定表的数据结构预留子目录覆盖字段，不实现匹配。
6. **第二个克隆**：发现同一远程地址的仓库已有绑定时，提示是否沿用，用户确认后才写入，不自动沿用。

### 4.3 验收要点

1. 主检出执行一次 `cohive init` 后，不复制任何文件：Claude Code 桌面应用新建工作树、`claude --worktree`、Codex 工作树、手动 `git worktree add` 的目录里打开编程工具，`/cohive`（Codex 为 `$cohive`）可用，`cohive_inbox` 返回本工作空间的待办，会话开始有提醒。
2. 未绑定的仓库和非 git 目录：工具列表只有 `cohive_status`；调用得到“请执行 cohive init”；钩子没有任何输出，P99 耗时小于 10 毫秒（网络断开时同样）。
3. 两个仓库绑两个不同工作空间，同时开会话，各自只看到自己的待办。
4. 非 git 目录绑定后，在其子目录打开编程工具也能用。
5. 迁移：旧版用户（未提交配置）执行一次新版 `init`，项目里 cohive 写的内容被移除、自己的配置不变、提醒不重复；已提交配置的仓库不被改动，且新旧版本成员同时使用不出现重复提醒。
6. 带 `--server`、`--workspace` 参数的旧命令行为不变（现有测试全部通过）。
7. 仓库里不出现本机绝对路径、令牌；绑定表只在本机配置目录。

### 4.4 快速开始“工作树与多目录”一节大纲

1. **一句话结论**：`cohive init` 记住的是“这个仓库属于哪个工作空间”，同一仓库的所有工作树自动生效，不用再复制任何文件。
2. **哪些地方自动生效**：Claude Code、Codex 的工作树，手动 `git worktree add`，绑定过的普通文件夹及其子文件夹。
3. **哪些地方要再执行一次 `init`**：同一仓库的另一个克隆；想换工作空间时。
4. **一台电脑多个工作空间**：不同仓库各自 `init --workspace 名字`；`cohive status` 查看当前目录绑了谁；`cohive unbind` 解除。
5. **团队共享**：要不要把绑定提交进仓库、怎么提交（按 4.1 第 1、2 条拍板结果写）。
6. **没绑定时会看到什么**：工具列表里只有一个说明工具，提示执行 `cohive init`；没有任何提醒。
7. **从旧版本升级**：重新执行一次 `cohive init`；仓库里已提交的旧配置什么时候可以删。
8. **旧版本的临时办法**：在主检出目录放一份 `.worktreeinclude`，写上 `.mcp.json`、`.claude/settings.json`、`.claude/skills/` 三行，只对 Claude Code 的工作树有效。
9. **排查**：`cohive hook --check` 会打印起点目录、识别出的仓库和命中的绑定。

补充（验收后）：

- **“已登录”的定义**：运行时判断 `.cohive.toml` 是否生效，只看本机有没有这个服务、这个工作空间的令牌记录。只有设备密钥、还没有该工作空间令牌的电脑（包括刚加入的工作空间）算“没登录”，`.cohive.toml` 在运行时被忽略；不联网核对成员身份，是为了让钩子保持毫秒级。这类电脑的出路是执行 `cohive init`：它把 `.cohive.toml` 当默认目标，用设备密钥向服务端核对成员身份、补签令牌并写入本机绑定，之后不再依赖 `.cohive.toml`。未绑定的提示文案已写明这一步（旧版配对且只有旧令牌的电脑，其令牌记录本来就在登录列表里，按已登录处理）。
- **查找范围**：git 仓库里查找 `.cohive.toml` 到仓库根为止，不会用上层目录里的那份；非 git 目录才向上找。已有用例保护。
- **测试隔离**：`cmd/cohive` 的测试入口把主目录、配置目录、缓存目录指向临时目录并切换当前目录，不再读到开发者本机的 `.mcp.json` 或真实绑定。
