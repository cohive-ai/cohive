# 群通知与公网访问

Cohive 的群通知是“群里敲门，客户端开门”：问题单轮到谁处理，工作空间的群里就出现一条只含信号的消息并 @ 到人；被 @ 的人在自己的编程工具里用 `/cohive 12`（Claude Code）或 `$cohive 12`（Codex）拉取完整内容、初筛、拍板。复现脚本、证据、日志从不发到群里。

本文以 Telegram 为例。用钉钉的看 [在自己的钉钉企业里接入 Cohive](dingtalk.md)：钉钉群用群绑定码绑定，成员在单聊里发绑定码、回网页确认后连接，审批按钮经 Stream 长连接回到服务端，同样只需出站访问。两种通讯工具可以在一台服务器上同时启用，每个工作空间第一期只绑一个群。

## 1. 准备机器人

1. 在 Telegram 里找 @BotFather 创建机器人，拿到机器人令牌（形如 `123456789:AAH…`，冒号两边都是令牌的一部分）。
2. 在运行协作服务的机器上保存令牌，输入时不显示、不进命令历史：

   ```bash
   bash scripts/set-telegram-token.sh
   ```

   令牌写入 `~/.config/cohive/telegram.env`（仅本人可读）。用启动脚本运行服务，令牌只在服务进程里加载：

   ```bash
   scripts/run-server.sh
   ```

   不要在交互终端里 `source` 这个文件：那样之后从这个终端启动的所有程序（包括 AI 编程工具）都能读到机器人令牌。

   用 Docker 部署时，把令牌写进 `deploy/.env` 的 `COHIVE_TELEGRAM_BOT_TOKEN`，再 `docker compose up -d`（见 [用 Docker 部署](deploy-docker.md)）。

3. 把机器人拉进工作空间对应的群。机器人只需要普通成员身份；设成管理员后它能收到群里所有消息（Cohive 会直接丢弃非命令消息，不存储）。

## 2. 配置工作空间

一个项目一个群，对应一个工作空间；**一个群只能绑一个工作空间**（群里点审批按钮时，由群反查工作空间）。服务器管理员在网页“服务器管理 → 工作空间”里新建，也可以在运行协作服务的机器上执行：

```bash
./bin/cohive-server workspace add --name payments --admin <首位管理员的登录名>
```

服务启动后，在群里发 `/chatid`，机器人回复群编号。工作空间管理员在网页“管理 → 工作空间”里填入群编号，选择群消息是否显示标题与简述，保存即可。也可以在服务器上用命令配置：

```bash
./bin/cohive-server workspace notify --workspace payments --telegram-chat -1001234567890
```

**群消息里的链接**用服务器级的“对外地址”拼成 `对外地址/w/路径/issues/编号`（例如 `https://cohive.example.com/w/payments/issues/12`）。对外地址整个服务器只设一个，由服务器管理员在“服务器管理 → 设置”里填写，或在服务器上执行 `./bin/cohive-server server set --external-url https://cohive.example.com`。也可以用环境变量 `COHIVE_EXTERNAL_URL` 锁定，锁定后网页和命令行都不能改。没设对外地址时，群消息不带链接，其余照常。工作空间设置页只读显示拼出来的链接。旧的 `workspace notify --public-url` 已废弃，使用时会报错并提示改用 `server set`。

群消息与审批消息里的工作空间名用**显示名**（“管理 → 工作空间”里可随时改）；链接与项目配置里用**路径**（建工作空间时定的名字，不能改）。

- `--show-title=false`、`--show-brief=false`：不在群里显示标题、群通知简述（默认都显示）。
- `--off`：关闭这个工作空间的群通知。

成员在网页“个人中心”点“连接 Telegram”，在 Telegram 里打开机器人即完成连接；连接属于账号，在他所在的全部工作空间通用，之后群通知就能 @ 到人（见 [新成员接入](onboarding.md)）。配好群后：

- 本工作空间的注册与加入申请发到本群；
- 设备申请发到申请人所在、配了群的每个工作空间群（批准后那台电脑可用于他全部的工作空间，消息里会写明）；
- 已连接 Telegram 的管理员可以直接点按钮审批：只对本群对应的工作空间有效，设备申请还要求申请人在本工作空间在册；在任一处处理后，各群里的审批消息都会改成结果；
- 有人加入工作空间时，群里会说一声并 @ 他；
- 在群里发 `/whoami` 可以查看自己连接的账号和在本群工作空间的角色。

确认接通：

```bash
./bin/cohive-server notify test --workspace payments
```

## 3. 哪些事件会发到群里

| 事件 | @ 谁 |
|---|---|
| 新单交给某人（发出、转交，或管理员在移出成员时改派） | 负责人 |
| 管理员在移出成员时把待验证的单改派给新发起人 | 新发起人 |
| 已接单 | 发起人 |
| 被退回 | 发起人 |
| 已修复，请验证 | 发起人 |
| 验证通过，已关闭 | 负责人 |
| 验证未通过，已重开 | 负责人 |
| 多次重开，需要人介入 | 发起人与负责人 |
| 待接单超时（催办） | 负责人；再过一个周期同时 @ 工作空间管理员 |
| 待验证超时（催办） | 发起人；再过一个周期同时 @ 工作空间管理员 |

开始修复、评论不通知。

**超时催办**：时长在网页“管理 → 工作空间 → 超时催办”里设（默认待接单 4 小时、待验证 24 小时，0 表示关闭），服务器上也可以用 `cohive-server workspace set --name <路径> --remind-open-hours 4 --remind-verify-hours 24`。
- 到点在群里再 @ 当事人一次；再过同样时长仍没有动作，同时 @ 工作空间管理员，之后不再催。
- 按自然时间计算（夜里、周末也算）；“修复中”不计时；状态一变、负责人或发起人一换就重新计时。
- 催办是要动手的通知：写入后、发出前单子已经被接、被验证，就不再发。
- 当事人在编程工具里同时收到一条会话内提醒；工作空间没配群时只有这条提醒。
- 升级到带催办的版本时，现有的单子从升级时刻开始计时，不会一下子补发一批。接单与关单只是告知对方（指引写“查看”），投递前单子再往前走也照样发出，群里能看到完整的经过；接单、关单时写的说明文字不发到群里。发起人和负责人是同一个人时也照常发。

怎么 @ 到人：
- 连接了 Telegram 的成员按**用户编号**提到（消息里是一个指向他的链接，文字是他的名字）。不需要设置 Telegram 用户名，之后改了用户名也照样能通知到。
- 只有用户名、没有用户编号的旧数据（例如早期用命令行登记的）退回 `@用户名`；在网页“个人中心”重新连接一次即可改为按编号提到。
- 都没有时只写名字，不会通知到他。
- **不 @ 操作者本人**，只写名字：自己发单给自己、发起人和负责人是同一人、本人凭邀请加入等，都不会被自己的操作提醒；去掉本人后一个都 @ 不到时照常发消息。超时催办没有操作者，照常 @ 当事人；第 2 档 @ 管理员时，当事人本身是管理员也只列一次。
- 被提到的人要在这个群里才会收到提醒（群设了免打扰也会提醒）。不在群里的人，Telegram 只在他私聊过机器人（连接 Telegram 时已私聊过）、且没对机器人开启“转发消息”隐私限制时保证这个提及有效。

投递规则：
- 发送失败自动重试，间隔逐步拉长，共 7 次、约 8.5 小时；群编号错误或机器人被移出群时直接放弃。
- 机器人令牌错误、被限流时暂停投递，通知保留，不计失败次数。
- 群升级为超级群后，自动改用新的群编号。
- 投递前核对问题单：已有新进展（例如已转交给别人、已关闭）的通知不再发送，超过 24 小时未送达的也不再发送，避免群里出现过时的提醒。
- 没设置机器人令牌时，待发通知会保留，设置后重启服务即补发。
- `workspace list` 显示每个工作空间的待发与失败条数；修好问题后用 `notify retry --workspace <名称>` 重发失败的通知。
- 至少送达一次：服务恰好在发出后、记录前崩溃时，可能重复发一条。

## 4. 让异地成员访问（Cloudflare 隧道示例）

网络打通由团队自行选择方式，这里以 Cloudflare 隧道为例。要点只有两个：

1. 把公网域名转发到协作服务，例如 `https://cohive.example.com` → `http://127.0.0.1:8787`。
2. 把这个地址设为**对外地址**（“服务器管理 → 设置”，或 `cohive-server server set --external-url https://cohive.example.com`）。对外地址的主机名会自动加入 MCP 的主机名白名单，改了立即生效，不用重启；否则 MCP 会以 403 拒绝（DNS 重绑定防护）。

   同一台服务器还要用别的域名访问时，再把它们写进 `COHIVE_ALLOWED_HOSTS`（逗号分隔，只写域名，不带 `https://` 或路径；写错时服务拒绝启动并提示）：

   ```bash
   COHIVE_ALLOWED_HOSTS=other.example.com scripts/run-server.sh
   ```

用 Docker 部署时可以直接用 compose 里的可选隧道服务（`docker compose --profile tunnel up -d`，见 [用 Docker 部署](deploy-docker.md) 第 4 节）。

隧道令牌建议用 `--token-file` 从文件读取，不要写在启动参数里（启动参数对本机所有用户可见）：

```bash
cloudflared tunnel --protocol http2 run --token-file ~/.config/cohive/cf-tunnel-token
```

异地成员的编程工具把 MCP 地址设为 `https://cohive.example.com/mcp`；令牌仍是访问的唯一凭据，丢失时用 `token revoke` 吊销。
